## 2. Главная проблема — прочитать обязательно

Своя клавиатура имеет смысл, только если **системная не всплывает**. Иначе на iPhone
вылезут две сразу.

Разведка по внешним источникам (18.08.2026, лежит в базе знаний, датасет
«Ресёрч и документация», документ `taskflow__wkwebview-podavlenie-sistemnoy-klaviatury-ios`)
дала неутешительную картину для WKWebView:

| Способ                | Вердикт                                                                                                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inputmode="none"`    | формально работает с iOS 13 (WebKit #188896 RESOLVED FIXED), но независимые тесты 2020-2021 показывали обратное; свежих подтверждений на iOS 17/18/26 нет |
| `readonly`            | системную гасит надёжно, **но на WebKit не рисуется каретка**                                                                                             |
| `@capacitor/keyboard` | подавлять не умеет вовсе — только скрыть уже показанную                                                                                                   |
| VirtualKeyboard API   | в WebKit не реализован (баг #230225 открыт с 2021, статус NEW)                                                                                            |
| swizzling `inputView` | рабочих примеров нет + приватный API = риск по App Store 2.5.1                                                                                            |

**Что это значит для работы:** ни один способ не даёт одновременно «системной нет» и
«каретка нативная». Выбор придётся делать, и он ниже.

### Решение, согласованное с владельцем

Владелец сказал (18.08.2026): **«в нашем приложении вообще мы не пользуемся никакими
выделениями, это в очень исключительных случаях»**. Значит потерять нативное выделение
и нативную каретку — приемлемо.

**Берём `readonly` + своя каретка.** Это единственный путь с предсказуемым поведением
на всех версиях iOS.

⚠️ **Перед тем как писать всё остальное — проверить `inputmode="none"` на симуляторе.**
Это 20 минут работы, и если он на актуальной iOS гасит клавиатуру, сохранив каретку, —
решение сильно упрощается (не нужна своя каретка вовсе). Порядок проверки — в §6.
Не пропускать этот шаг: гадать по чужим блогам 2020 года мы уже пробовали.

## 3. Что нужно сделать

### Шаг 1. Вынести клавиатуру из демо в общий компонент

Создать `src/components/AppKeyboard.tsx` — то, что сейчас лежит внутри
`KeyboardDemoScreen.tsx` (раскладки `LAYOUTS`, подписи `DISPLAY`, обработчик
`onKeyPress`, разметка `<Keyboard>`), но как самостоятельный компонент.

Требования:

- рендерится через `createPortal` в `document.body`, `position: fixed`, прижат к низу,
  `z-index` выше нижней навигации (у неё `z-[35]`, у FAB `z-30` — взять `z-[45]`);
- пропсы: `value`, `onChange(next)`, `onEnter?`, `onClose?`;
- микрофон остаётся клавишей внутри клавиатуры (владелец: «не надо, чтобы она висела,
  надо чтобы она была в клавиатуре»), логика записи — `useMicRecorder` + `useTranscribeAudio`,
  оверлей `MicOverlay` — всё уже написано в демо-экране, переносится как есть;
- CSS не дублировать: класс контейнера остаётся `kb-demo` либо блок в `index.css`
  переименовывается в `.app-keyboard` — но тогда переименовать во ВСЕХ местах разом.

### Шаг 2. Контекст, чтобы клавиатура была одна на всё приложение

Создать `src/lib/keyboardContext.tsx`:

- `KeyboardProvider` — оборачивает приложение в `App.tsx` (внутри `RequireAuth`, чтобы
  на экранах логина клавиатура не появлялась — там нужна обычная системная, иначе
  пароль не ввести до готовности своей);
- хранит: какое поле сейчас активно (`ref` на элемент), его текущее значение, видимость;
- `useKeyboardField()` — хук, который поле вызывает, чтобы зарегистрироваться;
- клавиатура рендерится **один раз** на уровне провайдера, а не в каждом поле.

Почему так, а не по компоненту на поле: иначе при переходе фокуса между полями
клавиатура будет размонтироваться и монтироваться заново — визуально дёрганье, плюс
потеря состояния раскладки (Shift, цифры).

### Шаг 3. Подключить к общему полю

`src/components/UI.tsx:912` — компонент `TextField`, через него идут почти все поля.
Добавить в него:

```tsx
readOnly              // системная клавиатура не всплывает
inputMode="none"      // подстраховка на платформах, где это работает
onFocus={...}         // зарегистрировать себя в контексте, показать клавиатуру
```

Значение приходит от контекста через существующий `onChange` — интерфейс компонента
менять не нужно, он уже `ComponentPropsWithoutRef<"input">`.

**Обязательно предусмотреть отключение.** Некоторым полям своя клавиатура не нужна:

- поля пароля и email на `/login`, `/register` (там `LoginScreen`/`RegisterScreen`,
  вне провайдера — вопрос снимается сам);
- числовые поля, если такие появятся.

Проп `systemKeyboard?: boolean` — при `true` компонент ведёт себя как раньше.

### Шаг 4. Textarea

В проекте 4 `<textarea>` (`TaskFormScreen`, `TaskDetailScreen`, `SubtaskFeed`,
`TaskJournal` — проверить `grep -rn "<textarea" src/`). Для них нужен тот же механизм
плюс клавиша переноса строки: сейчас `{enter}` в раскладке ничего не делает, для
многострочных полей он должен вставлять `\n`, а для однострочных — закрывать клавиатуру
или отправлять форму.

Пробросить в `AppKeyboard` признак `multiline`.

### Шаг 5. Своя каретка

Если проверка из §6 покажет, что `inputmode="none"` не работает и остаётся `readonly`:

- нативной каретки в readonly-поле на WebKit нет — нарисовать свою;
- простейший рабочий вариант: мигающий псевдоэлемент в конце текста
  (`animation: blink 1s step-end infinite`), позиция — конец строки;
- перемещение каретки внутри строки владельцу не нужно (сказал прямо), поэтому
  вставка идёт всегда в конец, `setCaretPosition` из библиотеки не используется —
  её поведение с выделением по итогам разведки осталось неподтверждённым.

### Шаг 6. Убрать временное

- пункт «Своя клавиатура (проба)» из `SettingsScreen.tsx` (помечен комментарием);
- решить судьбу `/kb-demo` — можно оставить как стенд для замеров, но тогда убрать
  из навигации.

## 4. Грабли, уже пойманные на демо

Все три стоили по заходу правок. Не наступать заново.

**1. Библиотека складывает свои отступы с твоими.** `hg-theme-default` держит
`margin-right: 5px` на кнопках и `margin-bottom: 5px` на рядах. Твой `gap: 6px`
даст в сумме 11px. Родные отступы обнулены в `index.css` — не убирать это обнуление.

**2. Ширина клавиш считается от содержимого.** Кнопки идут `flex-grow: 1` при базисе
`auto`, поэтому ряд с shift и backspace растаскивает колонки — получается «лесенка»,
третий ряд не совпадает с первыми двумя. Лечится `flex: 1 1 0; min-width: 0`.

**3. Специфичность библиотеки перебивает.** `.hg-theme-default button.hg-button`
(0,2,1) сильнее `.kb-demo .hg-button` (0,2,0) — из-за этого `font-size` молча
наследовался (в CSS стояло 33px, применялось 16px). Кегль задан отдельным правилом
с повышенной специфичностью. Если что-то в CSS «не применяется» — проверять
`getComputedStyle` на живой странице, а не читать исходник.

**4. Пустая подпись клавиши возвращает сырое имя.** `display: {"{space}": ""}`
рисует на клавише текст `{space}`. Подпись должна быть непустой — пробел.

**5. SVG-иконки сохраняют пропорции.** Поднять высоту рисунка, не подняв ширину,
нельзя. Если пропорции не сходятся с эталоном — перерисовать SVG с viewBox, плотно
облегающим рисунок, и задавать `mask-size` прямо в замеренных величинах.

## 5. Чего в клавиатуре пока нет

Это не баги, это несделанное — решить, нужно ли:

- **строка автодополнения** над клавиатурой (у системной есть, у нас нет);
- **долгое нажатие** для дополнительных символов — в русской раскладке iOS «ъ»
  вводится долгим нажатием на «ь», у нас «ъ» недоступен вообще;
- **английская раскладка и переключение языков** — сейчас только русская и цифры;
- **буфер обмена** (вставить/скопировать) — системного меню на readonly-поле не будет;
- **squircle-скругление** углов: у Apple непрерывная кривая, у нас дуга окружности,
  CSS так не умеет. Возможные пути — свойство `corner-shape` (поддержка в Safari
  не проверена) или SVG-маска на каждую клавишу.

## 7. Риск, который стоит назвать владельцу до начала

Если проверка из §6 покажет, что системная клавиатура всё равно всплывает поверх
нашей на реальном устройстве (не на симуляторе — там поведение может отличаться),
то весь замысел упирается в платформу, и остаются только два выхода: нативное
приложение либо отказ от своей клавиатуры в пользу панели над системной
(`inputAccessoryView` — этот путь протоптан, рабочие примеры есть).

Поэтому проверка на **реальном iPhone**, а не только на симуляторе, — не
формальность, а условие, при котором вообще имеет смысл делать шаги 2-5.
