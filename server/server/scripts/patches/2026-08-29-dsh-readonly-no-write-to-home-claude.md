# DSH-сессия: read-only корень, правки вне песочницы идут патчем

## Суть

В DSH-сессии контейнер с `overlayfs` смонтирован read-only: корень `/` идёт
`ro,relatime`, в том числе `/home/maksim/`, а значит и `~/.claude/`, и
`~/.claude/skills/taskflow/`. Песочница DSH при этом пропускает только
записи в каталог сессии (`/home/maksim/Проекты/New-Todoist/server/scripts`
или что задано в `workspace-write`). Любая попытка `write`/`sed`/`python` к
файлам вне workspace падает с `EROFS: read-only file system`.

## Симптом

Карточка на доске требует правки файла вне песочницы — например,
`~/.claude/skills/taskflow/server.ts` (Bun-MCP, канал координации между
агентами). Агент отчитывается «сделал», правка в git не видна (это и не
git), в `git status` тоже не видна. Проверка фактом: `git show`, `grep`,
`cat` — файлы не изменились. Тихий провал, который не отличить от
успешного коммита.

## Как проверить сразу

```bash
mount | grep ' / '
# /dev/nvme1n1p2 / ext4 ro,nosuid,nodev,relatime,errors=remount-ro 0 0
```

Если `ro` в строке корня — запись за пределы workspace запрещена на уровне
ядра. `sandbox_permissions: workspace-write` это не расширит: оно
разрешает писать в каталог сессии, а не отключает `ro` на файловой
системе.

## Что делать вместо правки

1. Приготовить патч в песочнице — `server/scripts/patches/<id>.patch`
   (или любой путь внутри workspace).
2. Проверить логику патча Node-тестом (`node -e '...'`) до сохранения —
   единственное, что можно прогнать без read-only обхода.
3. В карточке описать, что правка НЕ применена, и дать путь к патчу.
4. Попросить владельца или другую сессию с правами применить. Другой
   исполнитель на той же машине, не через DSH-сессию, обычно может
   `cd ~/.claude/skills/taskflow && patch -p0 < …patch` — если у него
   сессия не read-only.

## Что НЕ помогает

- `sudo mount -o remount,rw /` — нет sudo (контейнер `no-new-privileges`),
  даже если бы был, поверх `ro` overlayfs обычно ничего не даст.
- Эскалация песочницы `workspace-write → danger-full-access` — песочница
  DSH проверяет путь, а не флаг ФС; read-only корня остаётся.
- `touch`, `echo >`, `tee`, `python open(..., 'w')` — все три способа
  падают одинаково с `EROFS`.
- Включить файл в коммит (`git add`) — репозиторий проекта
  (`~/Проекты/...`) внутри workspace, а `~/.claude/...` — нет.

## Связанное

- Не путать с «DSH запрещает писать куда-то по своей политике»: песочница
  `workspace-write` — это политика поверх read-only mount, обе вместе.
- Коммиты в `~/Проекты/...` (git-репозиторий) проходят нормально: они
  внутри workspace, ФС там writeable.
- `/tmp/` пишется, это tmpfs поверх root — годится для черновиков,
  но не для «применённой правки», потому что до оригинала не добраться.
