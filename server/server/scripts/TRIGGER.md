## Что запускается

Исполнитель — **`pi_runtime`**: бинарь `pi`, запускаемый с моделью
(`trigger.py`, таблица моделей: `fable` → MiniMax-M3, `opus` → MiniMax-M2.7,
`sonnet` → MiniMax-M2.7-highspeed).

Отдельной сущности «Pi-агент» не существует — это имя осталось в старых
текстах. В коде каноническое имя `pi_runtime`, а `agent_pi` помечен как
legacy-alias (`trigger.py`, раздел `SHELL_AGENT_ALIASES`).

Для ролевого запуска передаётся профиль:
`pi --mcp-config ~/.pi/agent/taskflow-profiles/<role>.json`. Обычный `pi`
без этого флага роль не получает.

## Ручной запуск — единственный рабочий путь сегодня

```bash
~/Проекты/New-Todoist/server/scripts/manual_run.sh --once <task-id> [--review]
```

Скрипт сам достаёт из хранилища токены всех восьми ролей
(`TASKFLOW_AGENT_TOKEN_<ROLE>`) через `vault-run.py` и передаёт их
`trigger.py` в окружении. На диск токены не ложатся и в вывод не попадают.

Карточка должна быть **назначена на исполнителя** и иметь поднятый флаг
готовности — иначе заход отменится ещё до старта.

## Тумблер: за что берётся, а за что нет

Ровно один признак — **задача назначена на агента**.

Пропускаются: задачи не в статусе `active`, уже взятые (`in_progress`),
ждущие проверки (`review`), заблокированные (`blocked`), а также
собственные действия агента — иначе отчёт разбудил бы сам себя.

### Исключение: комментарий по сданной задаче

Задача в `review` — тема закрытая, кроме случая, когда по ней написали
комментарий. Тогда исполнитель приходит в режиме ответа (`REPLY_ONLY`):

- без `claim` и без аренды — карточка остаётся на проверке у владельца;
- ровно один заход, состояние менять запрещено;
- отказ захода тоже не меняет состояние — только записка в ленту.

Забрать сданную работу обратно агент не может по матрице переходов
(`AGENT-PROTOCOL.md`) — это дверь владельца.

Отвечаем только на **чужой** комментарий (`actor_id != assignee_id`). Без
этой проверки получается петля: ответ агента порождает уведомление, оно
будит агента снова. Поймано живьём 27.08.2026 — исполнитель ответил четыре
раза подряд на один вопрос.

## Почему не вебхуки

У TaskFlow канал лучше: **WebSocket** (`ws://localhost:3001/ws?token=…`) —
живой поток событий, и **уведомления хранятся в базе**
(`GET /api/notifications`), поэтому пришедшее за время простоя не теряется.
Побочная польза: пока сокет открыт, исполнитель показан онлайн на экране
агентов (`server/src/ws.ts` пишет `users.status`).

## Как пойдёт заход, если службу включить

1. `POST /api/tasks/:id/claim` — задача взята в работу.
2. Аренда продлевается каждые 4 минуты (`/heartbeat`), пока процесс жив:
   15-минутный срок не должен истекать под работающим исполнителем.
3. Запуск `pi` с промптом: задача, шаги, лента, правила из
   `AGENT-PROTOCOL.md`.
4. Ушёл, не закрыв задачу, или превысил час — служба переводит задачу в
   `blocked` с объяснением. Молча висеть «в работе» задача не остаётся.

Принять задачу (`completed`) может только владелец — исполнитель доводит до
`review`.

## Журналы и сухой прогон

Журнал службы: `~/.local/state/taskflow-trigger/trigger.log`, вывод заходов
— `task-<id>.log` там же.

Проверить, что служба видит события и правильно решает, кого будить, ничего
не запуская и не меняя:

```bash
TASKFLOW_TRIGGER_DRY=1 python3 ~/.claude/vault-run.py \
  --secret TASKFLOW_TOKEN=TASKFLOW_PI_AGENT_TOKEN -- python3 trigger.py
```

Нужен, когда над той же задачей уже идёт живая сессия: два исполнителя на
одной карточке — гарантированная каша.

## Если будете включать

Учесть расхождение: юнит передаёт **один** токен
(`TASKFLOW_PI_AGENT_TOKEN`), а `manual_run.sh` — все восемь ролевых. То
есть при автозапуске работа всех ролей будет записана на общую учётку, и
ролевые следы в ленте пропадут.
