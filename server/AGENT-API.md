# AGENT-API — TaskFlow API для агентов (Claude / Hermes / …)

Справочник для ИИ-агентов, работающих с задачами через HTTP API и WebSocket.
Сервер: Fastify + SQLite (better-sqlite3), исходники в `server/src/`.

Базовый URL в примерах — `http://localhost:3001` (порт задаётся `PORT`, по
умолчанию 3001). Подставьте свой адрес и порт.

## 1. Получение токена агента

У агента есть постоянный `api_token`, привязанный к учётной записи
пользователя (человека или ИИ-агента) в таблице `users`. Получить его можно
только через обычный логин-поток (JWT), это сознательное ограничение
безопасности: `api_token` не может перевыпустить сам себя.

Шаги:

1. Зарегистрируйте учётку агента (один раз) или используйте существующую:

```bash
curl -sS -X POST http://localhost:3001/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"name":"Claude_Bot","email":"claude@taskflow.local","password":"<пароль>","role":"agent","type":"ai"}'
```

Ответ: `{"token": "<JWT>", "user": {...}}`. Если учётка уже есть — получите
JWT через логин:

```bash
curl -sS -X POST http://localhost:3001/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"claude@taskflow.local","password":"<пароль>"}'
```

2. По JWT выпустите (или перевыпустите) `api_token`:

```bash
curl -sS -X POST http://localhost:3001/api/auth/api-token \
  -H "Authorization: Bearer <JWT>"
```

Ответ: `{"api_token": "tf_xxxxxxxx..."}`. **Значение показывается один раз** —
сохраните его у себя (переменная окружения, секрет-хранилище). Повторный
вызов этого эндпоинта сгенерирует новый токен и инвалидирует старый
(в базе хранится только последний).

3. Все дальнейшие запросы — с этим токеном:

```bash
curl -sS http://localhost:3001/api/tasks \
  -H "Authorization: Bearer tf_xxxxxxxx..."
```

## 2. Аутентификация

Заголовок `Authorization: Bearer <token>` принимается на всех маршрутах (кроме
`/api/auth/register`, `/api/auth/login`, `/api/health`) в одном из двух видов:

- **JWT** — тот, что получает веб-фронт при логине/регистрации (30 дней
  жизни). Основной поток для людей.
- **api_token** — статический токен агента из `/api/auth/api-token`. Основной
  поток для ИИ-агентов.

Сервер сам определяет тип токена: сначала пробует проверить как JWT, если не
получилось — ищет совпадение в `users.api_token`. Оба типа равноправны на
всех эндпоинтах данных (`/api/tasks`, `/api/projects`, `/api/labels`,
`/api/notifications`, `/ws`), **кроме** `POST /api/auth/api-token` — туда
пускает только настоящий JWT (иначе украденный `api_token` мог бы сам себя
перевыпускать).

Без токена или с невалидным токеном — `401`.

## 3. Модель владения (кто что видит и может менять)

Правило зависит от роли вызывающего — три круга (`server/src/access.ts`,
формулировка владельца от 18.08.2026):

| Круг                                | Видит                                  | Меняет                                          |
| ----------------------------------- | -------------------------------------- | ----------------------------------------------- |
| **Владелец** (`users.role='owner'`) | всё — задачи, проекты, метки           | всё, включая удаление чужой задачи              |
| **Агент** (`users.type='ai'`)       | все задачи; проекты и метки владельца  | только задачи, где он создатель ИЛИ исполнитель |
| **Прочий человек** (регистрация)    | своё: создал / назначено / свой проект | то же, что видит                                |

Смысл среднего круга — «назначен не ты, туда не лезть»: чужая задача агенту
видна (чтобы понимать контекст и не заводить дубли), но неизменяема — ни
`PATCH`, ни `claim`, ни подзадачи, ни комментарии, ни вложения.

Третий круг узкий намеренно: регистрация на сервере (`POST
/api/auth/register`) открыта всем, кто дотянулся до порта в локальной сети,
поэтому «видно всё» на самостоятельно заведённые учётки не
распространяется. По-хорошему у трекера один владелец и его агенты — этот
круг существует только как страховка на случай лишней учётки.

- **Задача (task)**: до 18.08.2026 правило было одним для всех — создатель
  ИЛИ исполнитель ИЛИ владелец проекта, в котором она лежит. Из-за этого
  задача, которую агент завёл сам (без проекта и без исполнителя), не
  показывалась владельцу вообще. **Удалять** может владелец — любую,
  остальные — только свою созданную.
- **Проект / метка (label)**: правит и удаляет владелец объекта (`owner_id`),
  а владелец трекера — любые. Нельзя привязать задачу к метке, которой у вас
  нет права пользоваться (`400 invalid label_ids`), и, по общему правилу, к
  чужому проекту (`400 invalid project_id`).
- **Исключение для агентов**: учётка с `type = 'ai'` может положить задачу в
  проект человека, если задача этому же человеку и адресована —
  `assignee_id` равен `owner_id` проекта. Иначе агенту пришлось бы работать
  под учёткой владельца: колонки на доске «Входящие» строятся из проектов
  текущего пользователя, поэтому задача в собственном проекте агента у
  человека не показывается ни в одной колонке. Правило одно и то же на
  создании и на изменении задачи (при `PATCH` без `assignee_id` в теле берётся
  исполнитель уже сохранённой задачи). Ни видеть чужие проекты, ни трогать
  чужие задачи это агенту по-прежнему не даёт.
- **Подзадачи / комментарии**: читает тот, кому видна родительская задача;
  пишет тот, кому она доступна на изменение (см. таблицу выше).
- **Уведомления**: видит и помечает прочитанными только их получатель
  (`user_id`).
- Обращение к чужому объекту → `404` (не `403`, чтобы не подтверждать факт
  существования чужого объекта).

### Tasks

| Метод  | Путь             | Описание                                        |
| ------ | ---------------- | ----------------------------------------------- |
| GET    | `/api/tasks`     | Список своих задач (создатель или исполнитель). |
| GET    | `/api/tasks/:id` | Одна задача + метки, подзадачи, комментарии.    |
| POST   | `/api/tasks`     | Создать задачу.                                 |
| PATCH  | `/api/tasks/:id` | Изменить задачу (частично).                     |
| DELETE | `/api/tasks/:id` | Удалить задачу (только создатель).              |

Создание:

```bash
curl -sS -X POST http://localhost:3001/api/tasks \
  -H "Authorization: Bearer <token>" -H 'Content-Type: application/json' \
  -d '{
    "title": "Оплатить ипотеку",
    "description": "Ежемесячный платёж",
    "due_date": "2026-09-01",
    "project_id": "p1",
    "priority": 2,
    "assignee_id": "u2",
    "label_ids": ["l1"],
    "subtasks": ["Написать письмо", "Отправить квитанцию", {"title": "Проверить статус"}]
  }'
```

Поля тела: `title` (обязательно, не пустое), `description`, `due_date` (строка
`YYYY-MM-DD` в формате `ГГГГ-ММ-ДД`, иначе 400), `project_id` (должен принадлежать вам),
`priority` (1–4), `assignee_id` (id любого существующего пользователя — так задача
делегируется агенту), `label_ids` (все метки должны принадлежать вам),
`subtasks` (опционально; массив строк или объектов `{title: "..."}` — создаёт подзадачи
атомарно в одной транзакции с задачей).

Изменение (только перечисленные ниже поля когда-либо попадают в SQL — прочие
ключи в теле запроса игнорируются):

```bash
curl -sS -X PATCH http://localhost:3001/api/tasks/<id> \
  -H "Authorization: Bearer <token>" -H 'Content-Type: application/json' \
  -d '{"status": "completed"}'
```

Разрешённые поля PATCH: `title` (обязательное, не пустое при отправке), `description`, `due_date` (формат
`YYYY-MM-DD` или null), `project_id`, `priority` (1–4), `assignee_id`, `status` (`active` | `completed`),
`label_ids`.

Завершить задачу — это `PATCH` со `status: "completed"`, отдельного
эндпоинта `/complete` нет.

Объект задачи (в ответах GET/POST/PATCH и в WS-событиях `task:*`) содержит,
среди прочего, поле `completed_at` — момент перехода в `completed`
(`YYYY-MM-DD HH:MM:SS`, UTC) или `null`, если задача активна. В отличие от
`updated_at` (обновляется при любом изменении задачи), `completed_at`
трогается только при смене статуса: выставляется при переходе
`active → completed`, обнуляется обратно в `null` при возврате
`completed → active`. Повторный `PATCH {"status":"completed"}` у уже
завершённой задачи (например, попутно с правкой описания) `completed_at`
не переписывает — так экран истории выполненных задач может группировать
их по дню, не съезжая от последующих правок.

Удаление:

```bash
curl -sS -X DELETE http://localhost:3001/api/tasks/<id> \
  -H "Authorization: Bearer <token>"
```

может любая аутентифицированная роль; операции управления каталогом, если они

| Метод | Путь | Описание |
| --- | --- | --- |

### Chat (канал координации)

| Метод | Путь                     | Описание                                                       |
| ----- | ------------------------ | -------------------------------------------------------------- |
| GET   | `/api/chat`              | История. `task_id`, `before`, `limit` (≤50), `channel` — необязательные. |
| POST  | `/api/chat`              | Отправить сообщение. **`to_user_id` обязателен.**               |
| GET   | `/api/chat/participants` | Кому можно адресовать: все участники канала, а не только свои.  |
| GET   | `/api/chat/stats`        | Сводка «кого озадачивают чаще всего» по служебной ленте.        |
| GET   | `/api/chat/unread`       | Сколько сообщений пропущено с последнего прочтения.             |
| POST  | `/api/chat/read`         | Отметить прочитанным.                                           |

**Каналов два с 28.08.2026.** У сообщения есть `channel`: `owner` — разговор владельца с
оркестратором, `agents` — рабочая переписка исполнителей. Значение выводит СЕРВЕР из ролей
отправителя и адресата; в теле `POST` поле `channel` слушается только у владельца (он один вправе
написать в служебную ленту, если захочет). Правила доступа:

- `GET /api/chat` без `channel` отдаёт всё, что видно вызывающему: исполнителю — только `agents`,
  владельцу и оркестратору — обе ленты. Дефолт именно такой, потому что резидент читает канал
  инструментом без аргументов, и «по умолчанию только рабочий» ослепил бы его на владельца.
- `GET /api/chat?channel=owner` от исполнителя — `403`; неизвестное значение — `400`.
- `POST /api/chat` с `to_user_id` владельца от кого угодно, кроме оркестратора, — `400`
  `{ error, адресуй, ваш_текст }`: отказ возвращает написанное, чтобы агент не потерял текст.
  ИСКЛЮЧЕНИЕ (28.08.2026, карточка 4caa266f) — ответ на его же сообщение: если владелец в
  последние 24 часа писал ЛИЧНО этому отправителю в `agents` (рассылка «всем» не считается),
  сообщение проходит и ложится в `agents` с `to_user_id` владельца — отвечают там же, где
  спросили. Окно продлевает только новое слово владельца, ответы исполнителя — нет; когда оно
  истекло, отказ приходит с другим текстом («разговор закончился»), чтобы отличать его от
  «он тебе вообще не писал».
- Владелец пишет исполнителю напрямую (`channel: "agents"`, `to_user_id` исполнителя) — сообщение
  уходит как есть, а оркестратору создаётся уведомление `chat_direct`: «работа роздана мимо тебя».
  Не чаще раза в час на одного исполнителя. Ничего при этом не гейтится и никуда не сворачивается.
- `GET /api/chat/unread` считает владельцу только его канал плюс сообщения из `agents`,
  адресованные лично ему (то есть ответы на его же вопросы): чужая служебная переписка бейджем его
  не дёргает — ради этого разделение и делалось, — но ответ на свой вопрос он видит.
- Событие `chat:new` уходит участникам КАНАЛА: сообщение из `owner` видят только владелец и
  оркестратор.

**Адресат обязателен с 28.08.2026.** `to_user_id` — либо id участника, либо
строка `"all"` («всем»; синонимы `всем`, `*`). Пропуск поля или пустая строка —
`400` с подсказкой, чем его заполнить; неизвестный адресат — `404`, а не тихая
рассылка всем. Повод — владелец: «как я должен догадаться, что ты мне написал,
не упомянув ни слова обо мне». В базе «всем» по-прежнему хранится как `NULL`,
схема ради этого не менялась.

```bash
curl -sS -X POST http://localhost:3001/api/chat \
  -H "Authorization: Bearer $TASKFLOW_AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"text":"нужен ревью","to_user_id":"u3","task_id":"...","kind":"совещание"}'
```

Ответ `GET /api/chat/stats` — три разреза по служебной ленте (`channel='agents'`):
`кому` (кого нагружают), `от_кого` (кто пишет), `пары` (кто именно к кому ходит);
у «всем» в разрезах `id: null` и имя `Всем`.

## 5. WebSocket — real-time события

Подключение:

```
ws://localhost:3001/ws?token=<JWT-или-api_token>
```

Токен обязателен и передаётся в query-параметре `?token=` (сокет — не HTTP
запрос, заголовок `Authorization` тут не поставить). userId сервер определяет
сам по токену — подписаться на чужой поток нельзя. Без токена или с неверным
токеном сервер шлёт `{"type":"error","error":"unauthorized"}` и закрывает
соединение.

При успешном подключении приходит `{"type":"connected"}`.

Проверка соединения: отправьте `{"type":"ping"}`, в ответ придёт
`{"type":"pong"}`.

### События, которые приходят на ваш сокет

Каждое событие приходит на сокеты обеих сторон задачи (создателя и
исполнителя, если они разные и оба подключены):

| Событие            | Когда                                                                      | Payload                                                                   |
| ------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `task:created`     | Задача создана                                                             | `{ "type":"task:created", "task": {...} }`                                |
| `task:updated`     | Задача изменена (кроме перехода в completed), либо изменилась её подзадача | `{ "type":"task:updated", "task": {...} }`                                |
| `task:completed`   | `status` стал `completed`                                                  | `{ "type":"task:completed", "task": {...} }`                              |
| `task:deleted`     | Задача удалена                                                             | `{ "type":"task:deleted", "id": "..." }`                                  |
| `notification:new` | Вам назначили задачу или её прокомментировали                              | `{ "type":"notification:new", "notificationId": "...", "taskId": "..." }` |

События чата координации приходят иначе — не сторонам задачи, а участникам
КАНАЛА, в который легло сообщение (рабочая лента — всем, разговор владельца с
оркестратором — им двоим):

| Событие       | Когда                                  | Payload                                                                                            |
| ------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `chat:new`    | В канал отправлено сообщение           | `{ "type":"chat:new", "message": {...} }`                                                          |
| `chat:typing` | Участник начал или перестал «печатать» | `{ "type":"chat:typing", "user_id":"...", "name":"...", "state":"typing\|stop", "ttl_ms": 60000 }` |

`chat:typing` зажигается запросом `POST /api/chat/typing` (тело пустое —
«печатаю», `{"state":"stop"}` — «перестал»; у агентов для этого есть
инструмент `taskflow_chat_typing`). Отметка гаснет сама: по сроку `ttl_ms`
(агенту минута, человеку 8 секунд), на отправленном им сообщении и при
закрытии его последнего сокета. Текущий список печатающих — `GET
/api/chat/typing`, он нужен экрану, открытому уже посреди чужого набора.

Пример клиента (Node.js, встроенный `WebSocket`):

```js
const ws = new WebSocket(`ws://localhost:3001/ws?token=${apiToken}`);
ws.onmessage = (ev) => {
  const event = JSON.parse(ev.data.toString());
  console.log(event.type, event);
};
```

## 8. Протокол работы агента с задачей

Задача может находиться в одном из нескольких состояний, и агент может управлять ими через
специальный API. Полное описание протокола — в документе `AGENT-PROTOCOL.md`; этот раздел —
краткий справочник для написания кода.

### 8.1. Два независимых поля состояния

**Важно:** у задачи два разных поля, и они работают независимо:

- **`status`**: `active` или `completed`. Это основной статус: активна ли задача вообще.
  Меняется через обычный `PATCH /api/tasks/:id` с `{"status":"completed"}`.
- **`agent_state`**: `null` / `in_progress` / `blocked` / `review`. Это состояние работы агента,
  если задача назначена на агента.

| `status`    | `agent_state` | Что это означает                                          |
| ----------- | ------------- | --------------------------------------------------------- |
| `active`    | `null`        | Никто не взял — задача в очереди                          |
| `active`    | `in_progress` | Агент работает; есть аренда, требуется периодический pинг |
| `active`    | `blocked`     | Агент упёрся и ждёт действия владельца (с комментарием)   |
| `active`    | `review`      | Агент закончил работу, ждёт проверку владельца            |
| `completed` | `null`        | Задача завершена (принята владельцем)                     |

Задача с агентом **остаётся активной** (`status='active'`) и видна во всех списках. Видимые для
фронта поля `agent_state`, `agent_heartbeat_at`, и производное `agent_stale` показывают текущее
состояние работы.

### 8.2. Аренда: почему агент должен отправлять пинги

Агент берёт задачу **на срок, а не навсегда**. Когда находится в `in_progress`, он обязан
периодически продлевать аренду через **heartbeat**. Срок аренды — **5 минут**. Если агент
молчит дольше — аренда истекает, и владелец видит, что задача брошена.

**Почему это важно:** агент может упасть, потерять сеть, зациклиться — и ничего не скажет.
Молчание неотличимо от работы. Поэтому система не верит агенту на слово: по умолчанию считается,
что работа прекратилась, и только регулярный сигнал (heartbeat) доказывает обратное.

Задача **не возвращается в очередь автоматически** — решение принимает владелец. Но она сразу
помечается как брошенная и требует внимания.

### 8.3. Шесть эндпоинтов работы агента: claim, heartbeat, state, stop, retry, consultation

#### 8.3.1. Взять задачу в работу — `POST /api/tasks/:id/claim`

Агент отправляет пустое тело запроса.

```bash
curl -sS -X POST http://localhost:3001/api/tasks/<task_id>/claim \
  -H "Authorization: Bearer tf_xxxxxxxx..." \
  -H 'Content-Type: application/json' \
  -d '{}'
```

**Что происходит:**

- Задача переводится в `agent_state='in_progress'`.
- Запускается аренда: `agent_heartbeat_at` устанавливается на текущий момент.
- Если никто не был назначен исполнителем (`assignee_id` пуст), текущий пользователь становится исполнителем.
- В журнал пишутся два события: `claimed` и `state_changed`.

**Допустимые исходные состояния:**

- `agent_state = null` (никто не брал);
- `agent_state = 'blocked'` (возобновление работы);
- `agent_state = 'in_progress'` с истёкшей арендой (перезахват своей задачи).

**Ответ при успехе (200):**

```json
{
  "task": {
    "id": "t123",
    "status": "active",
    "agent_state": "in_progress",
    "agent_heartbeat_at": "2026-08-11 14:30:45",
    "agent_stale": false,
    "title": "Написать письмо",
    ...
  }
}
```

**Ошибки:**

| Код | Когда                                                                 | Текст ошибки                                                          |
| --- | --------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 404 | Задача не найдена или не принадлежит вам (создатель или исполнитель). |                                                                       |
| 400 | Задача неактивна (уже завершена).                                     | `задачу можно взять в работу, только пока она активна`                |
| 400 | Задача на проверке у владельца.                                       | `задача на проверке у владельца, вернуть её в работу может только он` |
| 409 | Её уже держит другой агент, и его аренда ещё не истекла.              | `задачу уже держит другой исполнитель — аренда ещё не истекла`        |

#### 8.3.2. Продлить аренду — `POST /api/tasks/:id/heartbeat`

Агент отправляет пустое тело. Только исполнитель задачи, и только если она в `in_progress`.

```bash
curl -sS -X POST http://localhost:3001/api/tasks/<task_id>/heartbeat \
  -H "Authorization: Bearer tf_xxxxxxxx..." \
  -H 'Content-Type: application/json' \
  -d '{}'
```

**Что происходит:**

- Обновляется `agent_heartbeat_at` на текущий момент.
- Аренда продлевается на 5 минут от этого момента.
- **Heartbeat НЕ трогает** `updated_at` и не пишет в журнал — регулярные пинги не должны
  пересортировывать список задач и не должны загрязнять историю.

**Ответ при успехе (200):**

```json
{
  "lease_expires_at": "2026-08-11 14:45:45"
}
```

Поле `lease_expires_at` — это время, до которого действует текущая аренда. **Аренда — 5 минут,
поэтому интервал heartbeat должен быть заметно короче**, иначе она истечёт раньше следующего
сигнала. Служба-будильник Максима шлёт heartbeat каждые 90 секунд — берите этот порядок величины
как ориентир (раз в 1–2 минуты), а не «5–10 минут», которые гарантированно выходят за срок аренды.

**Ошибки:**

| Код | Когда                                     | Текст ошибки                                                       |
| --- | ----------------------------------------- | ------------------------------------------------------------------ |
| 404 | Задача не найдена.                        |                                                                    |
| 400 | Вы не исполнитель ИЛИ задача не в работе. | `продлить аренду может только исполнитель задачи, взятой в работу` |

#### 8.3.3. Изменить состояние — `POST /api/tasks/:id/state`

Агент переводит задачу в новое состояние. Обязательно тело запроса:

```bash
curl -sS -X POST http://localhost:3001/api/tasks/<task_id>/state \
  -H "Authorization: Bearer tf_xxxxxxxx..." \
  -H 'Content-Type: application/json' \
  -d '{
    "state": "blocked",
    "comment": "Нужен доступ к корпоративной почте, без него письмо не отправить"
  }'
```

Поля тела:

- **`state`** (обязательно): одно из `"in_progress"`, `"blocked"`, `"review"`, или `null` (снять с агента,
  только для владельца).
- **`comment`** (опционально, но см. ниже): текстовое объяснение. Если задача переводится в
  `blocked` или `review`, комментарий обязателен.

**Матрица допустимых переходов** (агентское подмножество — полная таблица, включая переходы
`status` вроде приёмки, и колонка «через какой эндпоинт», — в `AGENT-PROTOCOL.md`, раздел
«Матрица переходов»; эта копия должна оставаться её точным подмножеством, не отдельной версией):

| Из            | В             | Кто может          | Условие                                                                  |
| ------------- | ------------- | ------------------ | ------------------------------------------------------------------------ |
| `null`        | `in_progress` | исполнитель        | то же, что `claim`                                                       |
| `in_progress` | `blocked`     | исполнитель        | комментарий обязателен                                                   |
| `in_progress` | `review`      | исполнитель        | комментарий обязателен                                                   |
| `blocked`     | `in_progress` | исполнитель        | берётся новая аренда                                                     |
| `in_progress` | `in_progress` | тот же исполнитель | **только через `claim`** — перезахват своей задачи после истёкшей аренды |
| `review`      | `in_progress` | владелец           | **только через `/state`**, комментарий обязателен                        |
| любое         | `null`        | владелец           | снять с агента                                                           |

Переход из `review` в `in_progress` выполняет только владелец (при возврате на доработку).
Агент не может сам себя вернуть из `review` — это гарантирует, что приёмка остаётся на владельце.
Строка `in_progress → in_progress` — не «ничего не происходит»: это то, как исполнитель забирает
обратно свою же задачу после истечения аренды (через `claim`, не через `/state`), не дожидаясь,
пока владелец снимет её вручную.

**Что происходит:**

- Если указан комментарий, он добавляется как обычный комментарий к задаче.
- Если переход в `in_progress`, берётся новая аренда (`agent_heartbeat_at` = now).
- Состояние обновляется атомарно с комментарием (в одной транзакции).
- В журнал пишется событие `state_changed`.

**Ответ при успехе (200):**

```json
{
  "task": {
    "id": "t123",
    "status": "active",
    "agent_state": "review",
    "agent_heartbeat_at": "2026-08-11 14:30:45",
    "agent_stale": false,
    "title": "Написать письмо",
    ...
  }
}
```

**Ошибки:**

| Код | Когда                                                                                 | Текст ошибки                                                        |
| --- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 404 | Задача не найдена.                                                                    |                                                                     |
| 400 | Невалидный `state`.                                                                   | `state должно быть одним из: in_progress, blocked, review, null`    |
| 400 | Требуется комментарий при переводе в `blocked`.                                       | `нужен комментарий: что мешает и какие действия ждёте от владельца` |
| 400 | Требуется комментарий при переводе в `review`.                                        | `нужен комментарий: что сделано`                                    |
| 400 | Требуется комментарий при переводе из `review` в `in_progress` (вернул на доработку). | `нужен комментарий: что не так и что нужно доработать`              |
| 400 | Переход не разрешён матрицей или вы не имеете прав (не владелец/исполнитель).         | `invalid transition`                                                |

#### 8.3.4. Структурированная остановка — `POST /api/tasks/:id/stop`

Агент сообщает причину, по которой закрывает текущую попытку, и сервер возвращает
политику восстановления. Спек 1.2 (1.2.2) добавил `next_attempt_template` —
следующую ступень лесенки моделей, которую агент может подтвердить через
`/retry` (см. 8.3.5).

```bash
curl -sS -X POST http://localhost:3001/api/tasks/<task_id>/stop \
  -H "Authorization: Bearer tf_xxxxxxxx..." \
  -H 'Content-Type: application/json' \
  -d '{ "reason_code": "insufficient_capability", "comment": "модель не тянет" }'
```

Поля тела:

- **`reason_code`** (обязательно): один из закрытого списка —
  `insufficient_capability`, `different_competence`, `result_feedback`,
  `technical_failure`, `provider_limit`, `permission_or_owner`, `lease_expired`,
  `budget_exhausted`. Каждый reason_code сопоставлен с действием сервера
  (`escalate_capability`, `retry_technical`, `wait_owner` и т.п.; см.
  `src/stopReasons.ts`).
- **`comment`** (опционально): объяснение для владельца. Обязателен для reason_code,
  которые переводят задачу в `blocked` (`permission_or_owner`, `different_competence`,
  `result_feedback`, `lease_expired`, `budget_exhausted`) — на стороне сервера это
  требование матрицы переходов.

**Что происходит (по reason_code):**

- `insufficient_capability` — попытка закрывается, задача уходит в `blocked`,
  `current_attempt_id` обнуляется. В ответе приходит `next_attempt_template`
  с моделью следующей ступени (`haiku → sonnet → opus`). Если лесенка исчерпана
  (потолок или attempts_count ≥ 3) — `next_attempt_template: null`, агент не
  может retry, задача остаётся в `blocked` владельцу.
- `technical_failure` — попытка не закрывается, пишется строка в
  `attempt_retries` со счётчиком. До 3 автоматических retry с задержкой
  `delay_seconds`; после — `409` «лимит технических повторов исчерпан».
- `provider_limit` — попытка закрывается, открывается новая на фолбэк-провайдере
  роли (спек 1.1).
- остальные reason_code — попытка закрывается, задача в `blocked`.

Заголовок `X-Agent-Attempt-Id` обязателен для агентского клиента: сервер
сверяет его с `tasks.current_attempt_id` и отвечает `400 attempt_id_mismatch`,
если попытка уже сменилась.

**Ответ при успехе (200):**

```json
{
  "task": { "id": "t123", "agent_state": "blocked", ... },
  "reason_code": "insufficient_capability",
  "action": "escalate_capability",
  "retry_count": 0,
  "retry_delay_seconds": null,
  "fallback": null,
  "next_attempt_template": { "model": "opus", "runner": "claude" },
  "substantive_attempts": 1
}
```

**Ошибки:**

| Код | Когда                                                            | Текст ошибки                                                       |
| --- | ---------------------------------------------------------------- | ------------------------------------------------------------------ |
| 404 | Задача не найдена.                                               |                                                                    |
| 400 | Невалидный `reason_code`.                                        | `reason_code должен быть одним из: ...`                           |
| 400 | `attempt_id` в `X-Agent-Attempt-Id` не совпал с текущим.         | `attempt_id: attempt_id_mismatch`                                  |
| 409 | Исчерпаны автоматические retry для `technical_failure`.          | `лимит технических повторов исчерпан — нужно решение владельца`    |

#### 8.3.5. Подтвердить retry на следующей ступени — `POST /api/tasks/:id/retry`

Спек 1.2 (1.2.3). После `/stop` с `reason_code='insufficient_capability'`,
который вернул `next_attempt_template`, агент вызывает `/retry` чтобы открыть
новую попытку на предложенной модели. Если агент не согласен с лесенкой или
не хочет продолжать — задача остаётся в `blocked`, владелец решает.

```bash
curl -sS -X POST http://localhost:3001/api/tasks/<task_id>/retry \
  -H "Authorization: Bearer tf_xxxxxxxx..." \
  -H 'Content-Type: application/json' \
  -d '{
    "attempt_id": "att-uuid-from-prior-attempt",
    "template": { "model": "opus", "runner": "claude" }
  }'
```

Поля тела:

- **`attempt_id`** (обязательно): id попытки, которую агент только что закрыл
  через `/stop`. Сервер сверяет с последней попыткой задачи.
- **`template.model`** (обязательно): имя модели, на которой агент просит
  открыть новую попытку.
- **`template.runner`** (опционально): runner провайдера; если не указан,
  используется runner предыдущей попытки.

**Что происходит (атомарно, в одной транзакции):**

1. Старый attempt переводится в `outcome='needs_escalation'` (перезаписывая
   `escalate_capability` от `/stop` — финальное состояние с точки зрения retry).
2. Открывается новый attempt с присланной моделью и runner'ом.
3. Задача возвращается в `in_progress`, `current_attempt_id` указывает на новый
   attempt, `agent_heartbeat_at` обновляется.

**Ответ при успехе (200):**

```json
{
  "task": { "id": "t123", "agent_state": "in_progress", ... },
  "attempt_id": "new-attempt-uuid",
  "model": "opus",
  "runner": "claude"
}
```

**Ошибки:**

| Код | Когда                                                                                  | Текст ошибки                                                       |
| --- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 404 | Задача не найдена или недоступна.                                                      |                                                                    |
| 400 | Не переданы `attempt_id` или `template.model`.                                         | `body должен содержать attempt_id и template.model`               |
| 400 | `attempt_id` не совпадает с последней попыткой задачи (чужой или replay старого).     | `attempt_id_mismatch: ожидается …, прислан …`                      |
| 400 | Последняя попытка ещё активна (`ended_at IS NULL`).                                    | `попытка … ещё активна — retry применим только к закрытой попытке` |
| 400 | Последняя попытка закрыта не с `insufficient_capability`.                              | `… retry применим только после reason_code='insufficient_capability'` |
| 400 | Лесенка исчерпана (`attempts_count ≥ 3` или модель не в лесенке).                      | `потолок лесенки: … попыток …`                                     |
| 400 | Присланный `template` не совпадает с серверным `next_attempt_template`.                 | `template_mismatch: сервер предлагает …, прислан …`                |

#### 8.3.6. Консультация B+ — `POST /api/tasks/:id/consultation`

Спек 1.2 (1.2.4). В рамках одной попытки агент чувствует неуверенность
и хочет второе мнение от более думающей модели. Сервер собирает
контекст (задача + attempts.history + текущее состояние), вызывает
консультанта через общий `callUnifiedAi`, логирует в
`consultation_log` и возвращает ответ агенту.

```bash
curl -sS -X POST http://localhost:3001/api/tasks/<task_id>/consultation \
  -H "Authorization: Bearer tf_xxxxxxxx..." \
  -H 'Content-Type: application/json' \
  -d '{
    "attempt_id": "att-uuid",
    "consultant_model": "opus",
    "question": "Не уверен в выборе между X и Y, на что опереться?",
    "context": { "git_diff_lines": 312 },
    "triggered_by": "auto:diff_size"
  }'
```

Поля тела:

- **`attempt_id`** (обязательно): id текущей активной попытки.
- **`consultant_model`** (обязательно): короткий алиас (`opus`/`sonnet`/`haiku`)
  или явное имя модели. Алиасы маршрутизируются на:
  - `opus` → `claude-opus-4-6-thinking`
  - `sonnet` → `claude-sonnet-4-6`
  - `haiku` → `qwen3.6-27b-iq4-16k:latest` (локальная Ollama)
  Любое другое имя уходит в провайдер `claude` как есть.
- **`question`** (обязательно): конкретный вопрос ассистенту, предел 4000 символов.
- **`context`** (опционально): свободный JSON, до 64 КБ. Кладётся в
  `consultation_log.context_json` и в system prompt не идёт — модель видит
  его как `agent_context` внутри `contextPayload`.
- **`triggered_by`** (опционально): метка причины обращения — `manual` по умолчанию,
  или `auto:diff_size`/`auto:test_failures` если сработал триггер R7 спеки 1.2.

**Что происходит (атомарно с точки зрения лимита):**

1. Сервер читает текущую попытку (`attempts WHERE id = ? AND task_id = ?`).
2. Если `attempts.consultation_count >= 1` — `400 limit_exceeded`. Лимит
   R6 спеки 1.2 §3.2: одна консультация на попытку.
3. Собирается `contextPayload`: задача + история попыток + текущая попытка +
   `agent_context` + `question`.
4. Вызов `callUnifiedAi(provider, aiModel/localModel, temperature=0.2,
   predictTokens=1500)`.
5. В `consultation_log` пишется строка со всеми 9 полями (включая
   `duration_ms`, `triggered_by`, `answer`). При ошибке провайдера `answer=NULL`,
   `triggered_by` префиксуется `error:` — чтобы видно было в логе.
6. `attempts.consultation_count` инкрементируется **только при успешном
   вызове**. Если провайдер упал, счётчик не растёт — повторная попытка
   после восстановления сети пройдёт без 400.

**Ответ при успехе (200):**

```json
{
  "consultation_id": "clg-uuid",
  "answer": "Ответ консультанта (свободный текст)...",
  "duration_ms": 1340,
  "model": "opus",
  "consultation_count": 1
}
```

**Ошибки:**

| Код | Когда                                                          | Текст ошибки                                       |
| --- | -------------------------------------------------------------- | -------------------------------------------------- |
| 404 | Задача не найдена.                                             |                                                    |
| 400 | Не переданы `attempt_id`/`consultant_model`/`question`.        | `attempt_id, consultant_model и question обязательны` |
| 400 | `attempt_id` не принадлежит этой задаче.                       | `attempt_id_mismatch: у задачи ... нет попытки ...` |
| 400 | На этой попытке уже была консультация.                         | `limit_exceeded: на попытке ... уже N консультаций; лимит 1` |
| 400 | `question` длиннее 4000 символов или `context` больше 64 КБ.   | `вопрос слишком длинный (N символов, предел ...)`  |
| 502 | Провайдер модели упал; счётчик не инкрементирован.             | `consultant model error: ...`                      |

### 8.4. Жёсткие правила, на которых можно споткнуться

1. **Комментарий обязателен для `blocked` и `review`, а также при переводе из `review` в `in_progress`.** Без него запрос вернёт `400` —
   это техническое ограничение, не рекомендация. Агент физически не может скрыть причину блокировки, и владелец не может вернуть задачу на доработку без объяснения, что нужно переделать.

2. **Аренда не хранится явно.** Окончание аренды вычисляется как `agent_heartbeat_at + 5 минут`.
   После истечения аренды исполнитель может захватить задачу заново через `claim` или
   `state` с переходом `blocked → in_progress`.

3. **Завершить задачу может и агент.** `PATCH /api/tasks/:id` с `{"status":"completed"}`
   принимается от любой учётки, имеющей доступ к задаче, — с 20.08.2026 обязательная приёмка
   владельцем отменена. Прежний `403` для `type="ai"` снят; недовольство результатом владелец
   выражает комментарием или новой задачей, а не отказом закрыть старую.

4. **Захват из `review` запрещён.** Если задача в `review` (ждёт приёмки), агент не может
   взять её себе через `claim` (вернётся `400`: "задача на проверке у владельца, вернуть её в работу может только он")
   или перейти `review → in_progress` самостоятельно. Только владелец может вернуть из `review` обратно
   через `/state` (с обязательным комментарием: почему на доработку).

5. **Переход в `null` (снять с агента) выполняет только владелец.** Если агент застрял в
   `in_progress` и захотел уйти, правильно сделать это через `state: "blocked"` с объяснением,
   а не молча исчезнуть. Молчание всё равно будет видно (через 5 минут), но с объяснением
   владельцу будет понятнее, что произошло.

### 8.5. Рабочие примеры: полный цикл

#### Сценарий: агент взял задачу, продлил аренду, упёрся, потом сдал на проверку

Предположим:

- Базовый URL: `http://localhost:3001`
- Токен агента: `tf_abc123...` (берётся из `/api/auth/api-token`)
- ID задачи: `t_xyz789`
- ID владельца: `user_owner_id`

**Шаг 1: Взять задачу в работу**

```bash
curl -sS -X POST http://localhost:3001/api/tasks/t_xyz789/claim \
  -H "Authorization: Bearer tf_abc123..." \
  -H 'Content-Type: application/json' \
  -d '{}'
```

Ответ: `200`, задача теперь в `in_progress`, `agent_heartbeat_at` = `2026-08-11 14:30:45`,
аренда действует до `14:35:45`.

**Шаг 2: Через пару минут продлить аренду** (заведомо раньше `14:35:45`, а не впритык к нему —
опоздание превращает задачу в «брошенную»)

```bash
curl -sS -X POST http://localhost:3001/api/tasks/t_xyz789/heartbeat \
  -H "Authorization: Bearer tf_abc123..." \
  -H 'Content-Type: application/json' \
  -d '{}'
```

Ответ (отправлено в 14:32:45, поэтому новый срок — 14:32:45 + 5 минут):

```json
{
  "lease_expires_at": "2026-08-11 14:37:45"
}
```

Аренда продлена на следующие 5 минут от момента звонка, а не от предыдущего дедлайна.

**Шаг 3: Агент упёрся, нужна помощь**

```bash
curl -sS -X POST http://localhost:3001/api/tasks/t_xyz789/state \
  -H "Authorization: Bearer tf_abc123..." \
  -H 'Content-Type: application/json' \
  -d '{
    "state": "blocked",
    "comment": "Не удаётся подключиться к API третьей стороны (timeout). Требуется разрешить IP сервера в firewall."
  }'
```

Ответ: `200`, задача переводится в `blocked`, комментарий добавляется, владелец получает уведомление.

**Шаг 4: Владелец разрешил доступ; агент берётся заново**

```bash
curl -sS -X POST http://localhost:3001/api/tasks/t_xyz789/state \
  -H "Authorization: Bearer tf_abc123..." \
  -H 'Content-Type: application/json' \
  -d '{
    "state": "in_progress"
  }'
```

Ответ: `200`, задача переводится в `in_progress` с новой арендой, агент продолжает работу.

**Шаг 5: Агент закончил, сдаёт на проверку**

```bash
curl -sS -X POST http://localhost:3001/api/tasks/t_xyz789/state \
  -H "Authorization: Bearer tf_abc123..." \
  -H 'Content-Type: application/json' \
  -d '{
    "state": "review",
    "comment": "Выполнено: письмо отправлено, подтверждение получено, баланс обновлён в учётной записи."
  }'
```

Ответ: `200`, задача переводится в `review`, владелец видит результат и может принять или вернуть
на доработку.

**Шаг 6: Владелец принимает (вне API — через UI PATCH /api/tasks/:id)**

Владелец в интерфейсе нажимает кнопку «Принять», которая отправляет:

```bash
curl -sS -X PATCH http://localhost:3001/api/tasks/t_xyz789 \
  -H "Authorization: Bearer <jwt_owner>..." \
  -H 'Content-Type: application/json' \
  -d '{
    "status": "completed"
  }'
```

Ответ: `200`, задача завершена (`status='completed'`, `agent_state=null`).

### 8.6. Памятка агенту

1. **Всегда объясняйте через комментарий.** Если упираетесь — `blocked` с описанием. Если кончили
   — `review` с итогом. Молчание расходует время владельца.

2. **Продлевайте аренду, пока работаете.** Аренда — 5 минут, значит heartbeat реже, чем раз в
   5 минут, гарантированно её просрочит. Раз в 1–2 минуты — разумный интервал (служба-будильник
   Максима шлёт каждые 90 секунд). Не отправляйте слишком часто (это шум), но и не тяните до
   границы срока.

3. **Никогда не оставляйте задачу в `in_progress`, уходя.** Если работа прервана — перейдите
   в `blocked` с объяснением. Молча брошенная задача всплывёт как брошенная (через 5 минут),
   но владелец потеряет время, разбираясь, что произошло.

4. **Приёмка за человеком.** Вы доводите до `review`, остальное — за владельцем. Это не
   недоверие, это гарантия: если автоматизация спотыкается, человек это видит и решает сам.

5. **Из `review` не возвращайтесь в `in_progress` самостоятельно.** Если владелец вернул на
   доработку, он отправит вас туда сам через `state: "in_progress"` с комментарием. Это гарантирует,
   что вы не обойдёте приёмку.
