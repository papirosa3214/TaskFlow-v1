# File Format — сводка уведомления и маркеры тревог

Это формат, который пишет rendezvous при приёме уведомления и который
должен разбирать notifications-api и/или iOS-приложение. **Не менять без
согласования** — поле блока «По результатам диагностики» и «Итог по
устранению» дописываются writer'ом.

## Структура .md файла (с верху вниз)

```markdown
# <Заголовок уведомления>

- **когда:** 2026-09-27T01:11:33            ← ISO timestamp без зоны
- **от кого:** autonomy-110                ← имя эмиттера
- **уровень:** error                        ← info | warning | error
- **тревога:** да                          ← да | нет
- **приёмка:** rendezvous.py v1            ← статичная строка

## Сводка (для отображения в приложении)

\`\`\`                                       ← markdown-блок
Сводка уведомлений от 27.09.26

**Работают в штатном режиме:**
- <пункт>
- <пункт>

**Не отработали в штатном режиме:**
- <пункт с маркером тревоги>
\`\`\`

## Сырые строки (для парсинга)

**Работают в штатном режиме:**
- <пункт>
...

(если есть тревога)

**Не отработали в штатном режиме:**
- <пункт с маркером тревоги>
...

(по завершении диагностики — дописывается)

## Карточка диагностики

Создана задача на диагностику: [карточка #88a18485](tf://task/88a18485-...)
_диспетчер inbox-triage-dispatcher, <ts>_                      ← опционально

## По результатам диагностики

Подтвердилось: <текст комментария исполнителя>

По подтверждённым проблемам создана карточка на устранение:
[карточка #a78314b4](tf://task/a78314b4-...)
<!-- results-writer: 88a18485 diag-review -->

(по завершении устранения — дописывается)

## Итог по устранению

- <проблема> — (исправлено)                                       ← неактивная серая ссылка
- <проблема> — (не исправлено: нет доступов у исполнителя)          ← активная (модальное окно)
- <проблема> — (не исправлено, нужно ваше решение...)
    1) <предложение 1>
    2) <предложение 2>
    3) <предложение 3>
    4) свой вариант (свободный текст)
<!-- results-writer: a78314b4 fix-review -->
```

## Маркеры тревог

Список в `rendezvous.py:TRIAGE_MARKERS`. **Может расширяться**, но
согласовываться с Maksim.

| Маркер | Смысл |
|---|---|
| `🚨` | Маркер эмиттера |
| `НЕ УШЛО` | канал доставки сорвался |
| `ВИДНО НЕ ВСЁ` | данные неполные |
| `ПРОПАЛА` | что-то пропало (обрезка, потеря файла) |
| `СБОЙ ПОДМЕНЫ` | модель не та, пошла на дефолте |
| `СЛУЖБА МОЛЧИТ` | сервис не отвечает |
| `НЕ УДАЛАСЬ` | операция не прошла |

## Поведение строк-сносок в UI

| Текст | Состояние |
|---|---|
| `<problem> — (исправлено)` | неактивная серая ссылка. Тап → открыть карточку в TaskFlow |
| `<problem> — (не исправлено: ...)` | активная красная. Тап → модальный диалог с 4 вариантами + «свой вариант» |
| `<problem> — (не исправлено, нужно ваше решение...)` | то же |

### Модальный диалог с 4 вариантами

```
Варианты решений:
  1) <предложение 1>
  2) <предложение 2>
  3) <предложение 3>
  4) свой вариант (поле ввода с дефолтом = вариант 1)
```

Submit → `POST /api/tasks/:id/comments` → TaskFlow переводит карточку в
работу автоматически.

### Откуда берутся 3 подсказки (важно для приложения)

**Backend-only. Не пишутся ни эмиттером, ни исполнителем.**

`inboxResultsWriter.ts` дописывает в `.md` 3 фиксированных варианта по
своей эвристике (на основе текста комментария исполнителя, маркера
проблемы и заголовка карточки). Например:

```
- Прокладка Ollama (:11500) — (не исправлено, нужно ваше решение...)
    1) перезапустить ollama-shim.service
    2) отключить ollama в пользу прямой Ollama
    3) принять деградацию и обновить требования
    4) свой вариант (свободный текст)
```

Приложение **не парсит** содержимое 4 пунктов из файла для UI-сценариев —
оно только **отображает то, что есть**, и открывает модалку со всем
текстом строки-сноски как одним полем для ввода.

В UI:
- в карточке строка-сноска остаётся как **plain-text** (с переносами)
- при тапе: открывается модалка, в ней 4 radio-button (3 текста из файла +
  «свой вариант»), ввод свободного текста с дефолтом = вариант 1
- submit: `POST /api/tasks/<fix-id>/comments` с выбранным текстом

## HTML-комментарии в качестве маркеров идемпотентности

Writer использует:
```
<!-- results-writer: <task_id> diag-review -->
<!-- results-writer: <task_id> fix-review -->
```

При наличии такого комментария в файле блок не дописывается повторно.

## Чего в файле НЕ должно быть

- ❌ `<details>` / `<summary>` — оригинальный render на iOS их не любит
- ❌ `<style>` / inline-CSS — стили в приложении
- ❌ YAML front-matter — приложение не парсит
- ❌ изображения (хотя бы просто `[](data:...)`) — могут сломать iOS
