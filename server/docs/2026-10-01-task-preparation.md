# Единая подготовка задач — 01.10.2026

## Одобренный контракт

Владелец одобрил общий серверный механизм, к которому обращаются все входы. Разработка в основном Mac checkout; live .110 не меняется.

Один вызов модели возвращает намерение, карточку и предложение исполнения. Общий модуль taskPreparation владеет промптом, нормализацией метаданных, выбором представления и проверкой графа. Без записи и запуска: POST /api/task-preparation/prepare. Существующие structure-task, ownerDraft (чат, голос и импорт текста) и MCP preparation используют тот же механизм.

Представления: checklist, role_plan, child_cards. Результаты в role_plan становятся узлами существующего draft collaboration plan, привязанными к тем же subtasks через source_subtask_id. Утверждение и исполнение остаются в существующем runtime. Неизвестная совместимость не запрещает отдельную карточку, но требует уточнения перед автоматическим запуском. Роли сверяются с живым каталогом.

Неисполняемая реплика возвращает intent и вопрос без карточки. Адаптеры создания не должны записывать карточку из такого результата. Неправильный граф, цикл, неизвестная роль и несовпадение результатов дают ошибку до записи. В одном запросе максимум 12 результатов; рекурсивной серии вызовов нет. Общий сервис не пишет БД, поэтому повторный анализ не создаёт дубли. Chat intake сохраняет существующий claim по ID сообщения.

## План выполнения

1. Зафиксировать тестами контракт, отказ от карточки для вопроса, последовательную работу, роли, циклы и неизвестную совместимость.
2. Вынести существующую подготовку карточек из маршрута ai в единый модуль; добавить строгий контракт анализа.
3. Подключить REST/MCP и адаптеры создания; сохранять role_plan внутри транзакции создания карточки.
4. Проверить API, отсутствие дублей при approve и отсутствие запуска draft. Прогнать TypeScript и серверные тесты; записать фактические ограничения.

## Реализовано и проверено

- `server/src/lib/taskPreparation.ts` — единая подготовка, без записи и запуска. Ключи ролей из живого реестра; проверка ID результатов, циклов, транзитивных зависимостей и взаимной совместимости. Неизвестная совместимость допускает разбиение, но формирует уточнение.
- `aiClient.ts` — вынесен существующий общий транспорт модели, без зависимости от HTTP-маршрутов. `ai.ts` сохраняет совместимые экспорты; отдельный старый разборщик structureTask удалён.
- REST `POST /api/task-preparation/prepare`: text, context, source_record_id; schema_version=1, status=recommendation_only, intent, question, card. Проекты ограничены существующим visibleScope; ввод до 12000 символов, контекст до 6000.
- Чат, голос, импорт файла/текста и structure-task используют общий анализ. Для неисполняемой реплики карточки не пишутся; API создания возвращают 422, чистый анализ — card=null. ID сообщения чата передаётся анализатору; дедупликация chat_task_drafts сохранена.
- MCP taskflow_structure_dictation — тонкий клиент нового REST. taskflow_create_task принимает preparation; карточка и draft plan сохраняются в одной транзакции, с проверкой совпадения subtasks. Checklist сохраняет выбранную роль, критерий результата и уточнение.
- taskPreparationPersistence — отдельный адаптер записи. Role plan использует обычные subtasks и source_subtask_id; при approve не плодятся дубли. Автоматический intake не запускает role_plan до owner approve. Если вопрос не разрешён, approve отдаёт 409.
- CLI `python3 server/scripts/task_prepare.py --text 'Поручение'` или `--input файл --context 'Контекст' --source-record-id ID`; использует адрес и авторизацию существующего mcp_server.py. Ни бизнес-логики, ни копии конфигурации провайдера в CLI нет.

Верификация: серверный TypeScript build PASS; **754/754 vitest, 103 файла PASS**; **5/5 Python tests PASS** (4 MCP-проверки и существующая проверка снимка инструкций); Python syntax и git diff --check PASS. Новых серверных тестов 17. Для полного набора понадобился Python 3.14 в PATH: системный 3.9 падает на уже существующей аннотации `str | None` в scheduler.py. Продуктовый код расписания не менялся.

На реальном Ollama qwen3.6-27b-iq4-16k:latest выполнены три синтетических анализа с временной SQLite-базой: вопрос → informational_question/card=null (37.9 с), простая инструкция → checklist (9.8 с), правка iPhone + QA → role_plan builder→qa (13.0 с). Рабочие карточки, инструкции владельца и запуски ролей не затрагивались. Полные результаты: [task-preparation-eval.json](2026-10-01-task-preparation-eval.json). Это проверка трёх сценариев, не доказательство точности на произвольной речи.

## Границы результата

Код готов в Mac checkout; live .110 **не обновлён**. Миграция БД не нужна. Для применения нужен обычный серверный деплой с обновлением MCP-скрипта; CLI обращается к API уже обновлённого сервера.

Существующая нативная форма получает совместимый плоский ответ structure-task. Сам анализ общий, но старый клиент, не передающий preparation при сохранении, ещё не сохраняет предложенный граф автоматически: полный перенос контракта в iOS — отдельный интерфейсный шаг. Через ownerDraft и MCP граф сохраняется сейчас.

Произвольный POST /api/tasks с готовыми полями не запускает повторную смысловую декомпозицию: это операция записи, а не ещё одна точка анализа. Роли и скрипты вызывают prepare заранее и передают preparation при записи. Не запрошенные refinement-инструменты (извлечение нескольких задач из дневника, предложение шагов существующей карточки) не переопределены.

Граф role_plan поддерживает произвольный DAG. Зависимости между дочерними карточками пока используют существующее одиночное after: множественная/обратная связь блокирует автоматический запуск с уточнением. Новая очередь зависимостей между tasks не реализована. Повторный анализ ничего не пишет; дедупликация голосовой записи/произвольного POST создания новым ключом источника не добавлялась.

Запись отчёта в раздел документов TaskFlow не выполнена: taskflow_docs вернул 401 Invalid token. Локальный отчёт и JSON сохранены в репозитории.
