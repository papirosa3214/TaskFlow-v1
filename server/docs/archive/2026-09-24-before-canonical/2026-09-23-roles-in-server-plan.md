## 1. Цель одной фразой

Агент-исполнитель — неотъемлемая часть TaskFlow, как профили у Гермеса: роль — это запись в
таблице, агент работает **внутри сервера** через встроенный движок Pi, его действия в трекере —
внутренние вызовы сервера, **без ключей**. Добавить или отключить роль — одним действием в
приложении, без правки кода, хранилища секретов и запуска служб.

## 2. От чего уходим (старая схема)

- **Роли зашиты в код.** Список из восьми ролей — константа в `server/src/roleRouting.ts`, плюс
  ручные копии (учётка роли, русское название) в диспетчере, чатах, Секретаре, будильнике, вебе,
  iOS, каталоге команды, посеве. Убрать одну роль (Синтезатор) потребовало правки ~20 файлов.
- **Агент — посторонняя программа.** Будильник `server/scripts/trigger.py` (служба
  `taskflow-trigger`, ~3 100 строк) сам решает, кого будить, и запускает Pi отдельным процессом
  (`~/.local/bin/pi --mcp-config <профиль роли> -p`). Pi ходит в трекер по сети через
  `server/scripts/mcp_server.py` — как чужой клиент.
- **Отсюда ключи.** У каждой роли свой постоянный ключ в хранилище (`TASKFLOW_AGENT_TOKEN_<РОЛЬ>`),
  строка `--secret` в запуске будильника, свой файл подключения
  (`~/.pi/agent/taskflow-profiles/<роль>.json`) и отдельное постоянное WS-подключение будильника на
  каждую роль. Новую роль из приложения завести невозможно.
- **Встроенный запуск в сервере был, но не подключён** (`PiRuntimeAdapter.startRun`) и не давал
  агенту инструментов трекера. Ответы ролей в чатах уже шли через сервер (`startChatRun`) — без ключей.

## 3. К чему приходим

1. Роли — таблица `roles` (ключ, название, «чем занимается», включена, порядок). Весь код берёт
   список оттуда. ✅
2. Агент роли работает внутри сервера: `createAgentSession` из `@earendil-works/pi-coding-agent`,
   встроенные инструменты Pi (read/bash/edit/write/grep/find/ls) + инструменты трекера как
   внутренние вызовы маршрутов (`app.inject`) от имени учётки роли. ✅
3. Кого и когда будить — решает сервер (он видит каждое изменение карточки). Будильник ролями не
   занимается. ✅
4. Разговор агента помнится между заходами; повтор захода; папка и справка проекта. ✅
5. Уборка старого: ключи ролей, профили, `--secret`, временные пропуска шага A. ⏳
6. Экран «Команда» в приложении: добавить / отключить / поправить роль (название, «чем занимается»,
   модель). ⏳
7. Дальше (по желанию): остальная логика будильника переезжает в сервер, будильник становится
   простым расписанием или исчезает. ⏳

## 4. Почему так решили (решения владельца)

- Владелец выбирал движок среди многих: Pi взят именно потому, что он встраивается в свою программу
  (SDK, свои инструменты, модель из кода). Пользоваться им как отдельной программой — не по назначению.
- «Внутри одной программы никто ключами не обменивается» (сравнение с Гермесом и ChatGPT): ключ нужен
  только на границе с чужой программой. Ключи ролей — следствие того, что агента сделали отдельной
  программой, а не необходимость.
- Отвергнутые варианты: (а) пометка «действую как роль X» для служебного ключа и (б) временные
  пропуска для будильника — это заплатки, сохраняющие «агент — посторонний». Владелец выбрал
  «как у Гермеса, без ключей».
- Сервер оставлен в режиме `tsx watch`. Перезапуск обрывает текущую Pi-сессию,
  но её durable job после истечения lease возвращается в очередь; событие запуска
  больше не теряется вместе с памятью процесса.
- Роль не удаляется, а **отключается** — чтобы не терялась история её задач.

## 6. Как это работает сейчас (карта кода)

- `server/src/roleRouting.ts` — реестр ролей: `ROLE_NAMES` (живой массив), `refreshRoles()`
  (вызывается в конце `runMigrations`), `allRoles()`, `roleTitle()`, `roleUserId()` = `role_<ключ>`,
  `rolesPromptBlock()`. Модели ролей — в `server/scripts/role-routing.yaml` (новой роли — модель по
  умолчанию, самая частая).
- `server/src/runtime/inProcessRun.ts`:
  - `setInProcessApp(app)` — из `index.ts`;
  - `asRole(role, method, url, body)` — `app.inject` с JWT роли на 5 минут, в памяти;
  - `taskflowTools(role, model)` — инструменты: `taskflow_my_tasks, task, claim, heartbeat, state,
    review, comment, subtask_add, subtask_work, subtask_done, rules, projects, docs, doc_read,
    doc_write, kb_search`;
  - `runRoleInProcess({taskId, role, prompt?, cwd?, model?, mode?})` — один заход в фоне; аренда —
    сервер раз в 90 с; действия встроенных инструментов → `/api/tasks/:id/activity`; сбой →
    карточка `blocked` с причиной; `completion` сообщает worker технический сбой;
  - `kickRoleTaskStrict(taskId, reason, actorId?)` — решения «кого будить» (аналог `decide` будильника);
    работает только при включённой «Системе» (`unitState().active`); в тестах выключен
    (`VITEST` без `TASKFLOW_KICK_IN_TESTS=1`);
  - `continueOrHandOff` — повтор захода до трёх раз; worker-путь сохраняет chain depth в БД.
- `server/src/runtime/roleRunQueue.ts`, `roleRunWorker.ts` — durable очередь,
  idempotency, один running job на задачу, lease heartbeat, retry/backoff/dead,
  restart recovery и последовательный worker.
- Transactional enqueue: `routes/dispatch.ts` (успешная раздача), `routes/tasks.ts`
  (флаг при уже назначенном исполнителе), `routes/subtasks.ts` (внешний комментарий),
  `routes/agent-state.ts` (сдача). Owner API: `routes/role-run-jobs.ts`.
- `routes/manual-run.ts` — ручные «Запустить исполнителя/проверку» → внутри сервера.
- `scripts/trigger.py` — с `ROLES_IN_SERVER` не держит WS на ключах ролей, пропускает карточки ролей
  в `handle_task`, не зовёт `wake_reviewer`. Всё остальное (Гермес и пр.) — как было.
