# План: чаты TaskFlow с ролями-агентами (онлайн, Пи-рантайм)

Дата: 21.09.2026. Проекты: `New-Todoist` (сервер + веб) и iOS `TaskFlowNativeBuild`.
Повод — постановка владельца: чат должен быть **живым разговором с агентами-ролями**,
а не автоматизацией карточек. И владелец хочет **сам создавать чаты** с конкретными
ролями — **персональные** (одна роль) и **групповые** (несколько ролей).

## Целевое поведение

1. **Чаты как сущность.** Пользователь создаёт чат и выбирает участников —
   роли-агенты (Researcher, Architect, Builder, QA, Designer, Analyst, Synthesizer,
   Critic/Verifier). Чат бывает:
   - **персональный** — один агент (1:1), как личка;
   - **групповой** — несколько ролей.
   Участников можно добавлять/убирать.
2. **Онлайн-разговор.** Пишешь сообщение — отвечает **рантайм Пи** живой сессией:
   без карточки, без claim, без будильника. У агента его инструменты
   (`taskflow_*`, у исследователя — web/ocr/локальная модель и т.д.).
3. **Кто отвечает в группе** (ключевое решение): по умолчанию — **адресно**
   (@роль или выбор «кому» перед отправкой), а без адреса — «Авто» (подбор одного
   по смыслу, как диспетчер). Никогда не «отвечают все сразу» — это шум и деньги.
4. **Работа с задачами из чата.** Агент умеет читать/создавать задачи, дочерние и
   родительские, комментировать, двигать статусы — своими инструментами. Плюс чат
   можно привязать к задаче: в контекст кладётся дерево (родитель + дочерние).
5. **Автоматика выключена.** В онлайн-чате ничего не запускается само: ни
   диспетчер, ни будильник, ни авторазбор. Агент действует только по сообщению.
6. **Секретарь — отдельно.** Кнопка/команда «Собрать задачу» (`/задача`) запускает
   прежний разбор надиктовки в карточку. Обычное сообщение задачу НЕ создаёт.
7. **Клода нет, канала `agents` нет.** Убираем из работы `taskflow-chat.service`,
   `chat_resident_watch.py`, канал-плагин `plugin:taskflow` И общий канал `agents`.
   Вместо него — инструменты общения самих агентов (см. ниже): групповой чат и
   личные сообщения.
8. **Инструменты общения агентов.** У роли-агента есть:
   - **групповой чат** — писать в чат, где он участник (`chat_post`);
   - **личные сообщения** другому агенту/роли (`dm_send`) — тому, кто участвует в
     работе над задачей, либо тому, кого стоит задействовать по его компетенциям;
   - **подсказка адресата** (`suggest_agents`) — кто из ролей релевантен задаче или
     вопросу (по компетенциям/эмбеддингам), чтобы выбрать, кому писать.
   Общий «коридор» `agents` не нужен: общение идёт адресно (чат или личка), а не в
   одну общую ленту.

## Как ложится на код

- **Рантайм Пи живой.** `PiRuntimeAdapter.startRun` поднимает Pi через `RpcClient`,
  шлёт `prompt`, держит `sessionId`, стримит события. Вход сейчас привязан к
  `taskId`/`attempts` — нужен режим **без задачи** (сессия на чат).
- **Профили ролей есть.** `~/.pi/agent/taskflow-profiles/<role>.json` — MCP и
  allowlist на роль; промпт — `server/scripts/role-prompts/<role>.md`.
- **Транспорт чата есть.** `chat_messages`, `chat:new` по WS, «печатает…»
  (`chatTyping.ts`). Ответ кладём от имени роли-юзера (`role_researcher` и т.п.).
- **Секретарь есть.** `ownerDraft.startDraftFromChat` + `structureDictationToCards`
  — выносим за отдельную кнопку/эндпоинт, не удаляем.

## Ориентир: как это сделано у Microsoft (Agent Framework)

Владелец 21.09.2026: «ориентироваться на результаты работы в среде агентов
Microsoft — у них продуманы чаты и общение агентов». По документации
Microsoft Agent Framework (обновление 21.09.2026) есть пять оркестраций:

| Паттерн | Суть | Что берём |
| --- | --- | --- |
| Sequential | агенты по очереди в заданном порядке | позже (конвейер уже есть в ролях) |
| Concurrent | параллельно | позже |
| **Handoff** | агенты **передают управление** друг другу по контексту (mesh, без оркестратора); принимающий получает весь контекст | **берём** — это `dm_send`/передача роли |
| **Group Chat** | общий разговор, **оркестратор выбирает говорящего** (round-robin / селектор по промпту / агент-оркестратор); общий синхронизированный контекст; лимит итераций; промежуточные ответы каждого | **берём** — основа группового чата |
| Magentic | менеджер с планом динамически раздаёт специалистам | позже (для сложных задач) |

Что из их модели переносим напрямую:
1. **Оркестратор + выбор говорящего.** Групповой чат — звезда с оркестратором в
   центре. Ручная адресация (@роль) = явный выбор говорящего; «Авто» = селектор
   по промпту/агенту. Никогда не «говорят все» (у них тоже так).
2. **Синхронизация контекста.** Все участники видят историю: перед ходом каждой
   роли её сессия досинхронизируется историей чата, ответ вещается остальным.
   У нас это значит: контекст чата общий, а не по одному сообщению.
3. **Handoff.** Агент может **передать разговор** другой роли по контексту, и та
   получает весь контекст. Это и есть «личное сообщение агенту, участвующему в
   задаче или подходящему по компетенции».
4. **Human-in-the-loop.** Опасные/необратимые действия — через подтверждение
   владельца (у них `ApprovalRequiredAIFunction` → пауза и запрос). У нас:
   создание задач, запуск автоматики, отправка наружу — спрашивают.
5. **Лимиты.** Ограничение числа ходов/итераций и условие остановки — чтобы
   групповой чат не жёг токены бесконечно.
6. **Промежуточные ответы + стриминг.** Показывать ответ каждого участника и
   стримить обновления (у нас — «думает»/поток текста).
7. **Autonomous mode** (их опция) — это ровно будущая «точечная автоматика»:
   агент продолжает без человека до условия/лимита. Отдельным заходом.

Персонифицированно-групповой UX (личка + группа, @-упоминание, добавление/
удаление агента) — это модель агентов в чатах Microsoft 365/Teams; берём как
образец взаимодействия.

Источники (Microsoft Learn, прочитано 21.09.2026):
`agent-framework/workflows/orchestrations/` (обзор), `.../group-chat`, `.../handoff`.

## Этапы

### Этап 1. Чаты как сущность (сервер)
- Миграция: `chats` (id, title, created_by, kind: direct|group, task_id nullable,
  created_at), `chat_members` (chat_id, member_id — роль-юзер или человек,
  добавлен_at), `chat_messages.chat_id` (nullable, старые каналы не ломаем).
- Эндпоинты: создать чат, список чатов, добавить/убрать участника, история чата.
- Существующие каналы `owner`/`agents` остаются работать (миграция совместимости),
  новые чаты — отдельная ось.

### Этап 2. Живая сессия Пи без задачи
- `chatSession.ts`: на чат (или на пару чат+роль) — живая сессия Пи через адаптер.
  `startChatRun({ role, prompt, sessionId })`: та же машинерия, `taskId` не нужен,
  аренда/попытки не трогаются.
- Ответ роли → `chat_messages` (от имени роли-юзера) + `chat:new`.
- Контекст держится: следующее сообщение продолжает `pi_session_id`.

### Этап 3. Адресация и «Авто» в группе
- В группе сообщение адресуется роли (@роль / выбор «кому»). Без адреса — «Авто»:
  подбор одной роли существующим семантическим матчингом (`pickRole`).
- Смена/добавление роли в группе = её сессия поднимается по её профилю.

### Этап 4. Секретарь отдельной кнопкой/командой
- `POST /api/chats/:id/draft` (или команда `/задача`) → прежний
  `startDraftFromChat`. В `owner`-канале авторазбор на каждое сообщение убираем.

### Этап 5. Работа с задачами из чата
- Инструменты роли уже дают CRUD задач и дочерних. Ничего нового не изобретаем.
- «Чат по задаче»: `chats.task_id`; в контекст кладётся дерево задачи.

### Этап 6. Общение агентов в модели Microsoft: групповой чат + handoff
- **Групповой чат** (Group Chat): оркестратор выбирает говорящего. Ручная
  адресация @роль — явный выбор; без адреса — «Авто» (селектор по промпту/
  агенту, как `pickRole`). Общий синхронизированный контекст, лимит ходов.
- **Handoff**: агент может передать разговор другой роли, та получает весь
  контекст. Инструменты: `chat_post` (в групповой чат), `handoff(to, text)`
  (передать/написать лично агенту), `suggest_agents(task_id | query)` (кого
  позвать по компетенции/участию в задаче).
- **HITL**: подтверждение владельца на необратимое (создание задач, запуск
  автоматики, внешние отправки) — пауза и запрос.
- Общий канал `agents` выводим из работы; старые сообщения не удаляем (аддитивно).

### Этап 7. Убрать Клода
- Остановить и снять `taskflow-chat.service` (+ сторожей), вывести из обихода
  `chat_resident_watch.py`, отключить `plugin:taskflow`. Обратимо, без удаления с диска.

### Этап 8. iOS/веб
- iOS: список чатов, «+ создать чат» с выбором ролей (одна/несколько), экран чата,
  адресация @роль в группе, «онлайн/думает», кнопка «Собрать задачу», история.
- Веб — по мере необходимости (владелец в основном на телефоне).

### Этап 9. Проверка
- Персональный чат: вопрос → ответ роли, контекст держится.
- Групповой: адресно отвечает выбранная роль; без адреса — «Авто» подбирает одну.
- Инструменты: попросить агента завести дочернюю задачу/комментарий — появляется.
- Общение агентов: агент пишет в групповой чат и лично другому агенту; `suggest_agents`
  подсказывает релевантную роль.
- Секретарь: кнопка собирает карточку, обычное сообщение — нет.
- Автоматика выключена; Клод и канал `agents` не задействованы.

## Изоляция от текущей автоматизации (жёсткое требование)

Новая доработка НЕ должна менять поведение карточек и автоматики. Гарантии:

- **Отдельная ось.** Чаты — новые таблицы (`chats`, `chat_members`,
  `chat_messages.chat_id`), всё аддитивно. Существующие каналы `owner`/`agents`,
  окно постановки, диспетчер, будильник, claim/аренда/`agent_state` — не трогаются.
- **Онлайн-сессия Пи не касается задачи.** `startChatRun` работает без `taskId`:
  не создаёт attempt, не берёт claim, не двигает `agent_state`, не пишет в аренду.
  Значит, онлайн-разговор не может «занять» или «сломать» карточку.
- **Тумблер автоматики как был.** Включаешь автоматику — задачи идут ровно как
  сейчас (флаг готовности → диспетчер → будильник → исполнитель). Выключаешь —
  ничего не стартует само. Онлайн-чат живёт независимо от этого тумблера.
- **Секретарь не удаляем.** Авторазбор в `owner`-канале переезжает за кнопку, но
  сам разбор (`structureDictationToCards`) остаётся тем же кодом.
- **Клод только выключается**, не вырезается — обратимо.

Проверка изоляции — отдельный пункт приёмки: при включённой автоматике задача
проходит весь путь как прежде; при выключенной — онлайн-чат всё равно работает.

## Будущее (вне этого плана): будильник точечно на задачи

Владелец 21.09.2026: «в дальнейшем стоит настроить будильник не в общем на систему,
а точечно на задачи». Идея — на карточке признак «запускать автоматически» (или
набор правил), чтобы одни задачи стартовали сами без контроля, а другие жили в
онлайн-режиме. Сейчас будильник/автоматика — общий рубильник; точечность —
отдельная задача, после чатов.

## Решения, которые нужны от владельца

1. **Групповой чат — кто отвечает?** ✅ РЕШЕНО (владелец 21.09.2026):
   **адресно (@роль / выбор «кому») + «Авто»** без адреса. Все сразу — никогда.
2. **Участники** — роли-агенты. Люди/сервисные учётки — позже (MVP: только роли).
3. **Ответ** — целиком после генерации + индикатор «думает» (стрим по буквам —
   позже, если понадобится).
4. **Модель онлайн-чата** — как у роли (MiniMax-M3), с видимым расходом; выбор
   локальной модели — позже.
5. **Секретарь** — кнопка «Собрать задачу» в чате (команда `/задача` — позже).
6. **Канал `agents`** — ✅ РЕШЕНО (владелец 21.09.2026): убираем. Вместо него —
   инструменты общения агентов: групповой чат (`chat_post`) и личные сообщения
   (`dm_send`) участникам задачи или подходящим по компетенции (`suggest_agents`).

## Риски

- **Расход.** Онлайн-разговор тратит облачные токены на каждый ход — нужен видимый
  расход или дешёвая локальная опция.
- **Параллельность.** Много живых сессий (группа × роли) — нагрузка; ограничить
  число одновременных.
- **Совместимость.** `chat_messages` используется окном постановки и координацией;
  новые поля только аддитивно.
- **Клод-канал** завязан на экспериментальный флаг CLI — только выключаем, не удаляем.

## Что НЕ в этом плане

- Автозапуск ролей по карточкам (существующая автоматизация) — не трогаем.
- Серверный конвейер исследования (`POST /research`) — отдельная история.

## Голос в чат (как в прототипе VoiceMessageLab)

Владелец 21.09.2026: голосовое сообщение — **как в прототипе** (аудио `.m4a` + расшифровка), визуал записи — **утверждённый** элемент диктовки, новую кнопку не рисуем.

- **Формат сообщения:** аудио-пузырь (плей + длительность) и расшифровка под ним; состояния расшифровки `pending → ready/failed` (аудио доступно сразу, текст догоняет).
- **Визуал записи — утверждённый** (см. `TaskFormScreen.taskKeyboardDictationButton`): покой `mic.fill`; идёт запись — `waveform` с `symbolEffect(.variableColor.iterative)`; распознавание — `ProgressView`. Новую кнопку не вводим — существующий микрофон в `ChatComposer` заводим на этот визуал.
- **Движок записи/расшифровки** — из прототипа `VoiceMessageLab`: `VoiceRecorder` (AAC `.m4a`) + `VoiceTranscriber` (Parakeet, локально).

Этапы:
1. **Сервер** — вложения в новых чатах (`chats.ts`): `attachment_ids` в сообщении, привязка `attachments.chat_message_id`, отдача вложений в истории. *(воркер chat-attach)*
2. **iOS** — микрофон в `ChatComposer` (утверждённый визуал) → запись `.m4a` + локальная расшифровка → загрузка файла вложением → отправка сообщения; рендер пузыря с аудио и расшифровкой (переиспользовать пузырь прототипа).
3. **Постепенность** — аудио уходит сразу, расшифровка догоняет.
