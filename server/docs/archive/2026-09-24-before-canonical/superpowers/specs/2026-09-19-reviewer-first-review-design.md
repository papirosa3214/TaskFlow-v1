# Reviewer-first ревью для TaskFlow

**Дата:** 2026-09-19
**Статус:** в работе; правило про владельца уточнено владельцем 19.09.2026

## Главное правило: владелец вне процесса

Любые маршруты, гейты и ограничения касаются **только агентов**. Владелец
вне процесса и не ограничен ничем: закрывает, возвращает, удаляет, правит и
отменяет карточку в любой момент, и для его действий **не нужно** одобрение
Reviewer. Гейты существуют ровно затем, чтобы **агент** не обошёл ревьюера, а
не чтобы ограничивать владельца. Это правило общее для всей маршрутизации в
системе, а не только для этой фичи.

## Цель

Новые задачи по умолчанию сначала проходят Reviewer, чтобы владелец не
разбирал работу агентов вручную. Владелец может отключить это у конкретной
карточки и проверять её сам. Выключение флага — это предпочтение маршрута, а
не снятие ограничения: владелец и со включённым флагом действует сам, когда
захочет.

## Пользовательский поток

```
Исполнитель сдаёт работу → review
  ├─ requires_reviewer_review = 1
  │   └─ Reviewer одобряет (комментарий обязателен) или возвращает (комментарий обязателен)
  │       ├─ одобрил → карточка остаётся active/review, владелец уведомлён
  │       └─ вернул → in_progress, поручение доставляется исполнителю
  └─ requires_reviewer_review = 0
      └─ карточка идёт владельцу, как сегодня

В ЛЮБОЙ момент владелец может сам закрыть, вернуть в работу или удалить
карточку — независимо от флага и вердикта Reviewer.
```

Одобрение Reviewer никогда не закрывает карточку само. Финальное закрытие
остаётся действием владельца — но владелец вправе закрыть и без него.

## Модель данных и совместимость

В `tasks` добавляется `requires_reviewer_review INTEGER NOT NULL DEFAULT 1`.

- Миграция после добавления колонки явно обновляет уже существующие записи до
  `0`: они сохраняют сегодняшний маршрут и не оказываются внезапно в очереди
  Reviewer.
- Новая карточка получает `1`, если клиент не передал явное значение.
- Флаг доступен в API задачи и разрешён владельцу в create/PATCH.
- Вводить отдельное состояние после одобрения не нужно. Задача остаётся в
  `agent_state='review'`; источник истины — актуальная запись в `reviews` для
  текущей версии результата (`hasReviewerApprovedCurrentVersion` — сигнал для
  UI и маршрута, не гейт для владельца).

## Серверные правила

Ограничения ниже адресованы **агентам**. Владелец не подчиняется ни одному из
них.

1. Для `requires_reviewer_review=1` исполнитель **не может сам вернуть**
   карточку из `review` в работу. Возврат доступен Reviewer (с обязательным
   комментарием) и владельцу.
2. Reviewer может записать `approved` только с непустым `findings`. После
   этого сервер уведомляет владельца, карточка остаётся активной. Текст
   показывается в истории ревью как комментарий Reviewer к вердикту.
3. Reviewer выполняет `review → in_progress` с обязательным комментарием;
   существующая доставка `review_return` в inbox исполнителя сохраняется.
4. `PATCH /api/tasks/:id` со `status='completed'` **от владельца проходит
   всегда**, без требования одобрения Reviewer. Владельческое закрытие может
   записать запись-сигнал в `reviews`, но она не требуется и никого не
   блокирует.
5. При выключенном флаге сохраняется сегодняшний сценарий; внешние агенты не
   получают новых полномочий.
6. Вердикт привязан к версии результата: после возврата и повторной сдачи
   старая запись одобрения не переносится на новую версию (для сигнала
   маршрута и UI).

## API

Существующие `POST /api/reviews` и `POST /api/tasks/:id/state` остаются
основными точками входа.

- `POST /api/reviews`, `verdict='approved'`: принимает Reviewer; `findings`
  обязателен. В ответе и событиях фиксируется автор вердикта.
- `POST /api/tasks/:id/state`, `review → in_progress`: для флага `1` запрещает
  переход исполнителю; Reviewer и владелец — разрешены. Владельца не
  ограничивать.
- `POST/PATCH /api/tasks`: принимают `requires_reviewer_review` только от
  владельца. При создании отсутствие поля означает `true`.
- `PATCH /api/tasks/:id` со `status='completed'`: проходит для владельца
  всегда; требование одобрения Reviewer к владельцу не применяется.

## Клиенты

### Web

- В форме задачи — переключатель «Сначала ревьюер», включённый по умолчанию.
- Пока вердикта нет, карточка помечается «На ревью у Reviewer». Кнопки
  закрытия и возврата у владельца **остаются доступны** — подпись лишь
  подсказывает, что карточка ушла ревьюеру.
- Reviewer видит «Одобрить» и «Вернуть на доработку»; обе кнопки открывают
  форму с обязательным комментарием.
- После одобрения Reviewer владелец видит запись Reviewer в журнале.

### iOS

Те же флаг и подписи, что в web. Нативный клиент отправляет переключатель при
создании/редактировании. Владельческие действия (закрыть, вернуть) на iOS
доступны всегда, как и на web.

## Тесты

Серверные интеграционные тесты покрывают:

1. Новый task получает флаг `1`, существующая карточка после миграции — `0`.
2. Reviewer одобряет с комментарием; пустой текст даёт `400`, задача не
   закрывается сама.
3. Владелец закрывает карточку с флагом `1` в любой момент, без одобрения
   Reviewer (не `409`).
4. Reviewer возвращает с текстом, текст попадает в inbox исполнителя;
   пустой текст даёт `400`.
5. Исполнитель не может вернуть такую карточку из `review`; Reviewer и
   владелец могут.
6. При флаге `0` владелец сохраняет прямой маршрут.
7. Повторная сдача создаёт новую версию; старое одобрение не считается
   актуальным для сигнала маршрута.

Web и iOS покрывают сериализацию флага и видимость действий.

## Не входит в эту поставку

- Автоматическое закрытие карточки после Reviewer.
- Выбор произвольного Reviewer на карточку: используется действующая учётная
  запись Reviewer.
- Назначение Reviewer через чат или его включение в исполнительскую очередь.
- Любые ограничения владельца: их нет и не будет.
