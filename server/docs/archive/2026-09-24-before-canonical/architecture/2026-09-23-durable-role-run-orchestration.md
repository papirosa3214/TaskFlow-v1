# Durable-оркестрация запусков ролей

**Дата:** 23 сентября 2026 года.

**Статус:** реализован и проверен в локальной hardening-ветке; production и
удалённый репозиторий не изменялись.

**Автор:** Manus AI.

## Решение

Автоматические поводы запуска роли больше не должны существовать только как `void kickRoleTask(...)` после изменения карточки. Каждый повод записывается в SQLite как `role_run_jobs` **в той же транзакции**, что и породившее его изменение. Встроенный worker атомарно забирает работу, держит lease, продлевает его во время исполнения и завершает job только после окончания запуска. После рестарта просроченный lease возвращается в очередь.

Ручной запуск владельцем остаётся синхронным admission-запросом и не зависит от тумблера автономной системы. Это отдельный пользовательский сценарий.

## Рассмотренные варианты

| Подход | Компромиссы | Эксплуатационная стоимость | Сложность внедрения |
|---|---|---:|---:|
| SQLite outbox и worker внутри текущего сервера | Даёт атомарность с карточкой, recovery и наблюдаемое состояние без новой инфраструктуры. Подходит одному серверу; SQLite остаётся пределом горизонтального масштабирования. | Низкая | Средняя |
| Периодический sweep карточек поверх fire-and-forget | Самый короткий патч, но не сохраняет точный повод, actor и порядок комментариев; возможны повторные или пропущенные ответы. | Низкая | Низкая |
| Внешняя очередь | Хорошо масштабируется и отделяет worker, но вводит новый сервис, секреты, мониторинг и двухфазную проблему между SQLite и broker. | Высокая | Высокая |

Для текущего single-server приложения реализуется первый вариант: он закрывает обнаруженную потерю событий без новой службы.

## Контракт job

Job хранит `task_id`, `reason`, `actor_id`, уникальный `dedupe_key`, состояние, число попыток, время доступности, lease, последнюю ошибку и timestamps. Состояния: `queued`, `running`, `retry_wait`, `succeeded`, `skipped`, `dead`, `cancelled`.

Гарантии:

1. Повод и изменение карточки коммитятся вместе или не коммитятся вовсе.
2. Один `dedupe_key` создаёт не более одного job.
3. На одну задачу одновременно исполняется не более одного job.
4. Claim выполняется условным `UPDATE` внутри SQLite-транзакции.
5. Просроченный `running` возвращается в очередь; после лимита попыток job становится `dead`.
6. Worker всегда повторно проверяет актуальное состояние задачи и роли. Неактуальный повод завершается как `skipped`, а не запускает старую работу.
7. Остановка процесса не считается успешным завершением job.

## Этапы

1. Добавить migration, repository-функции enqueue/claim/renew/complete/fail/recover и тесты инвариантов.
2. Подключить worker к lifecycle реального server process. В тестах worker запускается только явно.
3. Перенести assignment, ready flag, comment, review и after-run enqueue внутрь породивших их транзакций.
4. Добавить owner-visible чтение состояния, retry/cancel и audit events.
5. После полного regression run обновить канонический план. Production-тумблер и live-данные этим этапом не меняются.

## Реализовано

Миграции `059_role_run_jobs` и `060_role_run_job_chain` добавляют durable job,
lease, retry/dead, recovery, глубину C3 и уникальный running job на задачу.
Assignment, ready flag, внешний комментарий и переход в review пишут job в
той же SQLite-транзакции, что и исходное изменение. C3 continuation создаёт
следующий job после подтверждённого прогресса. Собственный комментарий роли
не создаёт wakeup.

Worker стартует только в реальном server process после `listen`, продлевает
lease, ожидает фактическое завершение Pi-сессии и корректно различает
terminal skip, временный defer и технический retry. Выключенная владельцем
«Система» не сжигает попытки. Для владельца добавлены чтение очереди, ручной
retry terminal job и безопасная отмена pending job. Running job намеренно не
отменяется через этот API до появления подтверждённого abort-протокола.

Проверка на Node `22.19.0`: server build прошёл; полный server suite — **65
файлов и 525 тестов**. Live-запуск и production-тумблер не использовались.

## Приёмка

Обязательны тесты атомарного dedupe, конкурентного claim, lease recovery, retry/dead, сериализации jobs одной задачи и отсутствия запуска при устаревшем состоянии. Затем проходят server build, полный server suite, root build и web suite.
