# TaskFlow — руководство пользователя (iOS-натив)

> Актуально на 13.09.2026. Документ собран по живой кодовой базе `~/Проекты/TaskFlowNativeBuild`,
> контракту API (`spec/API.md`) и фактической схеме БД `server/taskflow.db` на .110.
> Написан как чек-ликт «как пользоваться + где грабли», не маркетинг.

---

## 1. Что это за приложение

- **Имя в системе:** «Задачи» (`CFBundleDisplayName`), bundle id **`com.maksim.taskflow.native`**.
- **Код:** только `~/Проекты/TaskFlowNativeBuild` на Mac, отдельный git-репозиторий
  (remote `origin` — Gitea `maksim/taskflow-native-ios`). На .110 копии **нет и быть не должно** —
  любая копия там считается мусором и удаляется.
- **Что дёргает:** бэкенд TaskFlow на `http://192.168.1.110:3001` (Fastify, порт зашит прямо в
  `APIClient.baseURL` — это единственная константа, никакого override через env/bundle нет).
- **WebSocket:** `ws://192.168.1.110:3001/ws?token=<JWT|api_token>` — единственный живой канал
  обновлений. Watchdog 45 сек тишины → реконнект с экспоненциальным backoff до 30 сек.
- **Минимальная iOS:** 18.0. Целевое устройство — iPhone, только portrait, только dark mode.
- **Что внутри:** SwiftUI, `@Observable`-сторы поверх `APIClient` (async/await, URLSession),
  VoiceOver/Live Activity/Dynamic Island, FluidAudio (Parakeet TDT v3, распознавание речи
  локально на устройстве, не облако), SDWebImage для анимированных аватарок агентов.
- **SPM-зависимости в коде:** `FluidAudio ≥ 0.12.4`, `SDWebImageSwiftUI ≥ 3.1.3`,
  `SDWebImageWebPCoder ≥ 0.14.6`, `swift-snapshot-testing ≥ 1.18.0`.

## 2. Главный сценарий: голос → задача → iPhone

### 2.1. Надиктовать задачу

1. На любом экране с полем ввода — тапни в поле. Поднимется **системная клавиатура iOS**
   (своя клавиатура отключена решением от 20.08.2026, см. §6).
2. На accessory-панели над клавиатурой есть **иконка микрофона** (`MarkdownKeyboardAccessoryBar`).
   Тапни её — стартует локальная диктовка через `DictationEngine` + FluidAudio.
3. Говоришь текстом. Движок `DictationEngine.startRecording()` переключается
   в `RecordingState.recording`, модель Parakeet TDT v3 распознаёт on-device, текст
   вставляется в активное поле (без облака, без отправки на сервер).
4. Закончил — тапни «готово» на accessory-панели или стоп-иконку.

**Грабля:** если модель не скачана (`VoiceModelsScreen` → «Расшифровка действий»), секция
показывает «не скачана» и диктовка в редакторе заметок не сработает. Иди в Настройки →
Голосовые модели и дождись скачивания. Быстрый обход — диктовка в других полях работает
через системную клавиатуру (`UITextView` подхватывает её нативно).

### 2.2. Сохранить задачу

1. В быстром добавлении (`QuickAddTaskView`) — это компактная панель над клавиатурой,
   открывается автоматически при тапе на центральную `+` в таббаре (пункт «Задача»).
2. Заполни заголовок. По желанию — описание (тапни «Описание»), срок (тапни «Срок» →
   popover), подзадачи (тапни «+» в подзадачах).
3. Тапни красную кнопку send на accessory-панели над клавиатурой (на iOS 26+ она
   системная, на 18–25 — `ToolbarItemGroup(placement: .keyboard)`).
4. Задача уходит в `POST /api/tasks`, WebSocket пушит `task:created`, сторы обновляются.

**Грабля:** проект при создании из `ProjectTasksScreen` через `+` **НЕ подставляется**
в форму (`AppRoute.taskCreate` не имеет параметра `projectID` — это контрактная дыра,
описанная в коде как «КОНТРАКТНАЯ ДЫРА (не мой файл чинить)»). После создания открой
задачу и выбери проект вручную в форме.

### 2.3. Доступно на iPhone

Через 1–2 секунды после сохранения задача появляется:
- В табе «Обзор» → плитка «В работе» (если назначена агенту) или «Пропали» (если
  не назначена и `agent_heartbeat_at` старше 15 минут).
- В табе «Планирование» → раздел «Сегодня» (если `due_date` равно сегодня в Moscow TZ,
  внимание: **дедлайны считаются строго в Europe/Moscow**, не в локальной таймзоне
  устройства — `TaskDateText.swift` это явно фиксирует).
- В табе «Проекты» → внутри проекта.
- В уведомлениях (`notifications` в таббаре) — если ты назначен исполнителем или автором.

## 3. Экраны и фичи

### 3.1. Обзор (`/overview`)

Стартовый экран. 4 плитки по статусу агентской работы:
- **В работе** — задачи с `agent_state='in_progress'`.
- **На проверке** — `agent_state='review'`.
- **Заблокированы** — `agent_state='blocked'`.
- **Пропали** — `agent_state` заполнен, но `agent_heartbeat_at` старше 15 минут
  (`isStale()` в сервере, derived-поле `agent_stale` в ответе — в БД такой колонки нет).

Тап по плитке → `AgentWorkScreen` со списком и фильтром по `focus`.
Свайп по задаче: «удалить» (подтверждение) и «принять» (если `agent_state='review'`,
сначала `POST /reviews` с verdict, потом `status='completed'`).

### 3.2. Планирование (`/upcoming`, объединено с `/today`)

Четыре режима в одном экране, переключаются через пилюлю в шапке:
- **Сегодня** — список + часовая сетка (`TodayListView` + `TodayHoursView`).
  Задачи без `start_time` идут отдельным блоком вверху, с временем — блоками на шкале
  06:00–23:00 (можно перетаскивать пальцем с привязкой к 15 минутам).
- **Три дня** — `UpcomingListView` в режиме дня, листается горизонтально.
- **Неделя** — `UpcomingWeekView` с day-cell-ами.
- **Месяц** — `UpcomingMonthView` с мини-месяцем.

Выбранный режим сохраняется в `UserDefaults` (`plannerSection`), переживает рестарт.

Свайп по задаче: «удалить» (подтверждение), «срок» (открывает `RescheduleSheet`),
«завершить» — **СЕЙЧАС НЕ РАБОТАЕТ**, в коде TODO без реализации
(`UpcomingListView.swift:312`, `/* TODO: завершить задачу через taskStore */`).
Обход: открой задачу тапом → кнопка «Завершить» в форме.

### 3.3. Задачи (`/task/:id`, `/task/new`)

Одна и та же форма для просмотра, редактирования и создания (`TaskFormScreen`,
вызывается через `.fullScreenCover` чтобы не конфликтовать с клавиатурой).

**Поля формы:**
- Заголовок (обязательно, 1 строка).
- Описание (многострочно, поддерживает голосовую диктовку).
- Срок (`due_date`) — `YYYY-MM-DD`, календарная дата. Кнопки быстрого выбора:
  сегодня / завтра / +3 дня / следующая неделя / без срока.
- Время (`start_time`) + длительность (`duration_min`) — формат `HH:MM`, **локальное**,
  не UTC. Доступно только если задан `due_date` (иначе сервер вернёт 400).
- Проект, метки, приоритет (1=Срочный, 2=Высокий, 3=Средний, 4=Низкий), исполнитель.
- Подзадачи (чеклист) — добавляй/переименовывай/отмечай прямо в форме.
- Прикреплённые файлы (изображения, документы) — до 15 МБ каждый.

**Дополнительно на карточке:**
- Вложенные задачи (`children`) — отдельные карточки, привязанные через `parent_id`.
- Лента событий (`task_events`) — кто когда что поменял, claim/heartbeat/state-переходы.
- Комментарии с возможностью прикреплять файлы.
- Live Activity (Dynamic Island) — стартует автоматически для активных задач с агентом.

**Контракт на parent-child и чек-листы:**
- Чек-лист (subtasks) — отдельная сущность, **у задачи-родителя своих чек-листов быть
  не может** (запрещено на сервере с 10.09.2026). Если нужна декомпозиция — заводи
  дочерние задачи через `parent_id`.
- Дочерние задачи — обычные карточки, отображаются отдельным блоком на родительской.
  Каскадное удаление — `ON DELETE CASCADE` на `parent_id`.

### 3.4. Чат (`/chat`)

Два канала, выбираются сервером по ролям отправителя и адресата:
- **`owner`** — разговор владельца с оркестратором (туда идут надиктовки → Секретарю).
- **`agents`** — переписка между исполнителями (Клод/Hermes/Pi/Antigravity/Reviewer
  и роли-агенты `role_researcher`/`role_analyst`/...).

В UI канал не выбирается явно — он виден как цветовая пометка.

**Команда (`/agents`)** — список исполнителей: online/offline, текущая задача,
`last_action_title`, `activity` («working»/«blocked»/null). Тап на агента →
карточка с деталями (модель, провайдер, base URL, секрет-ссылка, индивидуальный
системный промпт, MCP-серверы, скиллы, права по действиям).

**Работа агентов (`/agent-work`)** — сводка «кто чем занят». Тап по плитке из Обзора
открывает с фильтром.

### 3.5. Заметки (`/notes`, `/notes/:id`)

**Дерево папок** (`journal_folders`) + список заметок (`user_notes`) +
смысловой поиск через Knowledge (RAGFlow на .110). Три параллельные модели
заметок в БД — **это три разных UI-раздела, не один**:
- `/notes` → `user_notes` (полноценные заметки с заголовком, TipTap-JSON, папкой).
- `/journal/folders` → `journal_entries` (по одной записи на дату, формат `YYYY-MM-DD`).
  Один-в-день дневник, не используется для больших текстов.
- `/api/projects/:id/docs` → привязанные к проекту заметки через `notes_folder_id`.

**Редактор заметок** (`NoteEditorScreen`) — блочный редактор на `UITextView`
(`NoteBlockTextView`), каждый блок — отдельный TipTap-JSON-блок. Accessory-панель
над системной клавиатурой даёт форматирование (B/I/U/список/заголовок) и
кнопку диктовки.

Сервер хранит TipTap JSON в `user_notes.content`. Нативный клиент пишет JSON.
При чтении с `?format=markdown` сервер отдаёт готовый markdown (спека §5.9) — но
**клиент пишет JSON по умолчанию**, обратной конвертации в JSON нет.

### 3.6. Настройки (`/settings`)

- Профиль (имя, аватарка, цвет).
- AI: статус хабов (local/Claude/Hermes/Antigravity/DeepSeek), локальные модели
  Ollama, per-user системные промпты (`/api/ai/prompts`).
- Общие: шаблоны задач (только локально, без синка с сервером), выбор иконки приложения.
- Сервер: статусный блок с реальным ping `/api/health` (не показывает URL — он зашит).
- Интеграции: Google Tasks / Calendar / Reminders (через сервер), Apple EventKit
  (локально на устройстве).
- Выход (чистит Keychain и разрывает сокет).

### 3.7. Виджеты и Live Activity

Виджет «TaskFlow» один — `TaskActivityWidget`. Показывает текущую задачу агента
на Lock Screen + Dynamic Island (compact + minimal + expanded). Цвета:
teal (в работе) / blue (review) / orange (blocked) / green (completed).

Запуск: при входе агента в `claim` или `state=in_progress` клиент зовёт
`Activity<>.request(...)` и шлёт токен на `POST /api/live-activity/token`.
Дальше сервер сам двигает карточку через APNs.

**Грабля:** в `live_activity_tokens` сейчас 0 строк (таблица пустая). Если виджет
не появляется — проверь, что в Настройки → AI/Интеграции push-токен зарегистрирован.

## 4. Как аутентифицироваться

### 4.1. Обычный вход

LoginView (`/login`) — email + пароль → JWT. JWT хранится в iOS Keychain
(`KeychainService.shared.token`), читается на КАЖДЫЙ запрос — нет in-memory кэша.
Живёт 30 дней, потом новый логин.

`Authorization: Bearer <JWT>` — единый заголовок для всех REST и для WebSocket
(в WS — query-параметр `token=…`).

### 4.2. Альтернативно — API-токен

Если у тебя есть статичный API-токен вида `tf_...` (выдаётся в Настройки → Команда →
карточка агента), он тоже идёт в `Authorization: Bearer <token>` — сервер сам
разбирает что ему прислали. Значение показывается один раз, хранится в БД хэшем.

### 4.3. На 401

Сервер вернул 401 — токен истёк. Клиент чистит Keychain, шлёт
`Notification.Name.taskFlowUnauthorized`, `RootView` подписан и сразу разрывает сокет →
экран логина. LAN-релогин (как в вебе) **не работает в нативе** — сервер требует
браузерные заголовки `Sec-Fetch-*`/`Origin`/`User-Agent:Mozilla`, которых URLSession
не шлёт.

### 4.4. Debug-обход логина (только в dev-сборке)

Переменная `TASKFLOW_DEBUG_TOKEN` кладётся прямо в Keychain при старте
(`SessionStore.bootstrap()` в `#if DEBUG`). Токен берётся из vault на .110:
ключ `TASKFLOW_AGENT_TOKEN`. Использовать так:
```
TOKEN=$(ssh maksim 'python3 ~/.claude/vault-get.py --raw TASKFLOW_AGENT_TOKEN')
SIMCTL_CHILD_TASKFLOW_DEBUG_TOKEN="$TOKEN" xcrun simctl launch <udid> com.maksim.taskflow.native
```
Никогда не свети токен в чате — `vault-run.py` сам вычищает секрет из вывода.

## 5. Форматы данных — три разных

Нативный клиент использует три разных формата дат — путать нельзя:

| Поле | Формат | TZ | Пример |
|---|---|---|---|
| `created_at`, `updated_at`, `completed_at`, `*_at` | `YYYY-MM-DD HH:MM:SS` | **UTC**, без `Z` | `2026-09-13 14:32:00` |
| `due_date` | `YYYY-MM-DD` | локальная (Москва для отображения) | `2026-09-15` |
| `start_time` | `HH:MM` | **локальная** | `14:30` |

Парсер sqlite-UTC в клиенте: `Sources/Core/Common/DateFormats.swift` —
`sqliteUTC` добавляет `Z` перед `ISO8601DateFormatter`. Если парсишь руками —
делай так же, иначе словишь сдвиг на таймзону.

Аватарки агентов — анимированные GIF/WebP (SDWebImage), не статичные PNG.

## 7. Известные грабли и workaround

### 7.1. Документация врёт — верь коду

- **Аренда задачи — 5 минут**, не 15 (как пишет устаревший `docs/ARCHITECTURE.md` в бэке).
  `LEASE_MINUTES = 5` в `server/src/agentState.ts`.
- **Агент МОЖЕТ закрыть задачу** с 20.08.2026 (раньше не мог). Закрытие — `PATCH /tasks/:id`
  с `status="completed"`. Может сделать любой участник задачи.
- **`agent_stale`** — derived-поле в ответе, **не колонка БД**. Вычисляется в
  `withAgentStale()` на каждом GET. Если видишь `agent_stale=true` — heartbeat старше
  15 минут.
- **`subtasks.agent_state`** — допустимые значения: `NULL`, `in_progress`, `blocked`,
  `review`. **НЕ** `pending`/`running`/`done`/`blocked` (как пишет устаревший
  `docs/TASK-LIFECYCLE-SCENARIOS.md`). `done` — отдельная колонка.
- **`tasks.parent_id` и `users.last_seen_at`** — есть в живой БД на .110, но НЕ
  создаются миграциями (это известная дыра). На свежей БД без дампа полей не будет.
- **`agent_session_id` есть и на задаче, и на подзадаче** — для разделения параллельных
  сессий под одним ботом.
- **`is_system_bot`** у пользователя — числовое `0/1`, не Bool.

### 7.2. Расхождения Core ↔ реальный сервер (уже исправлены обходными путями)

Эти 5 багов уже найдены авторами клиента, починены в `Features/*API.swift`, но
остались висеть в Core как декларации. На работу приложения не влияют —

- `Core/APIClient+Chat.swift` — `chatMessages/sendChatMessage/sendChatTyping/
  markChatRead` бьют по неправильным путям. Рабочий код — `Features/Chat/ChatAPI.swift`.
- `APIClient+Notifications.markNotificationRead` шлёт `PATCH /notifications/:id`
  с телом. Реальный сервер ждёт `PATCH /notifications/:id/read` без тела. Рабочий —
  `directoryMarkNotificationRead` в `Features/Directory/Support/DirectoryAPI.swift`.
- `POST /agents` отдаёт `{agent, api_token}`, не `{user, …}` — Core ждёт не то.
  Рабочий код в `Features/Chat/AgentsAPI.swift`.
- `/avatars` — рабочий путь `/avatars/:userId`, не просто `/avatars`.

### 7.3. Parent-child vs чек-листы — две разные сущности

- **Чек-лист (`subtasks`)** — короткие пункты внутри одной задачи, отмечаются галочкой.
  У задачи-родителя своих чек-листов быть не может.
- **Дочерние задачи (`parent_id`)** — отдельные карточки в БД, со своим сроком,
  приоритетом, агентом. Видны блоком на родительской карточке.

Если нужно «разбить задачу на этапы» — заводи дочерние задачи, не чек-лист.
Если нужно «подпункты для одной задачи» — чек-лист.

### 7.4. Три модели «заметок»

- **`user_notes`** (77 шт.) — основная модель, TipTap-JSON в `content`, заголовок
  отдельно, папка через `folder_id`. Это то, что показывает «Заметки» в таббаре.
- **`journal_entries`** (1 шт.) — дневник по дате, одна запись = один день,
  `id = YYYY-MM-DD`. Не использовать для больших текстов.
- **`notes`** (1 шт., `'main'`) — заброшено миграцией 010, осталось как рудимент.
  Игнорировать.

### 7.5. Чат: каналы vs `to_user_id`

`channel` (`owner`/`agents`) проставляется **сервером** по ролям отправителя и
адресата — клиент не выбирает. `to_user_id` — конкретный получатель; `null` = всем
в канале. Для надиктовки владельца → Секретарю — `channel=owner, to_user_id=u-secretary`.

### 7.6. Агенты: 4 роли + 8 специализаций + 8 системных ботов

В БД у одного пользователя сразу два поля:
- `role` — круг доступа: `owner` / `orchestrator` / `agent` / `viewer` (+ 8 специализаций:
  `researcher` / `analyst` / `synthesizer` / `critic_verifier` / `architect` / `builder`
  / `qa` / `designer`).
- `type` — `human` или `ai`.

Видимость задач зависит от обоих: `agent`+`ai` видит всё; `agent`+`human` — только своё;
`viewer`+`ai` — только чат (Секретарь).

`/api/agents` отдаёт только общий список (owner + system_bot + shared-tasks) —
8 ролевых агентов (`role_researcher`...) туда **не входят**. Они видны через
`/api/roles` или `/api/agents/:id/details`.

### 7.7. `ready_for_pickup` (миграция 026)

Без явной отметки владельца (`ready_for_pickup = true`) **агент не может взять задачу**
через `POST /api/tasks/:id/claim` — сервер вернёт 403/409. По умолчанию у новых задач
`ready_for_pickup = false`. Поменять можно только владелец — в форме задачи отдельный тумблер.

### 7.8. Hardcoded URL сервера

`APIClient.baseURL = http://192.168.1.110:3001` — единственная константа, никакого
override через env, bundle, xcconfig. Если сервер переедет — придётся править код,
пересобирать, перезаливать на телефон. Это known limitation.

## 8. Как разрулить, если что-то сломалось

### 8.1. Виджет не появляется на Lock Screen / Dynamic Island

1. Открой задачу с активным агентом в форме → проверь, что `LiveActivity` запустился.
2. Если «пусто» — проверь таблицу `live_activity_tokens` на .110:
   `ssh maksim 'sqlite3 /home/maksim/Проекты/New-Todoist/server/taskflow.db "SELECT * FROM live_activity_tokens"'`.
3. Если пусто — push-токен не пришёл на сервер. Перезайди в задачу, чтобы клиент
   переотправил.

### 8.2. WebSocket висит, обновления не приходят

1. Сверни приложение и открой снова — клиент сам разорвёт полу-мёртвый сокет по watchdog
   (45 сек тишины) и переподключится.
2. Не помогло — свайпни вниз на любом списке (pull-to-refresh), это заставит стор
   перезапросить REST и подтянуть свежее.
3. Лог клиента: `xcrun simctl spawn <device-udid> log show --last 2m --predicate 'process == "TaskFlow"' --style compact`.
   Если есть `WebSocket disconnected` без последующего `connected` — сокет не поднялся,
   перезапусти приложение.

### 8.3. Задача не создаётся / 400 от сервера

Проверь поля — самые частые 400:
- `start_time` без `due_date` — задаёт время, но не дату.
- `start_time` вне `HH:MM` или `duration_min` вне `1..1440`.
- `priority` вне `1..4` (нет P5, P0).
- `project_id`/`assignee_id` чужой — сервер не даст сохранить.

### 8.4. Голосовая диктовка не работает

1. Открой Настройки → Голосовые модели. Должна быть зелёная «Parakeet TDT v3 готова»
   и скачана локально.
2. Если «не скачана» — тапни «Скачать». Модель ~50 МБ, нужно Wi-Fi.
3. Диктовка в редакторе заметок работает через accessory-панель над системной клавиатурой.
   Если системная клавиатура не поднялась — тапни в поле ещё раз.

### 8.5. Push не приходит, а Live Activity должен быть

Push идёт через APNs (`server/src/apns.ts`). Ключи — на .110, в vault. Проверить,
что credentials не протухли: `ssh maksim 'python3 ~/.claude/vault-get.py --raw APNS_KEY_ID'`
(значение в чат не выводить).
