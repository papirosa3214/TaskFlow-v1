# Handoff: hardening ролей и durable-оркестрация

**Дата:** 23 сентября 2026 года.

**Статус:** локальная реализация завершена и проверена; **push, merge и production не выполнялись**.

**Рабочая ветка:** `manus/roles-hardening-2026-09-23`.
**Автор:** Manus AI.

## Итог

В серверной части закрыты два инженерных блокера, найденные независимым аудитом: P0-эскалация authority через ключ роли и потеря автоматического запуска роли после коммита карточки. Теперь бизнес-роль хранится отдельно от системной authority, а каждый автоматический повод запуска сохраняется в SQLite как durable job в одной транзакции с изменением карточки.

Реализация находится только в локальной ветке `manus/roles-hardening-2026-09-23`. Удалённый Git-сервер, production-база, systemd-службы и реальные модели в этой работе не изменялись. Это означает, что код и документы готовы к обычному ревью и последующему push, но не заявляет, что новая очередь уже исполняется на реальном сервере.

### Поведение очереди

Автоматический повод запуска имеет одно из состояний `queued`, `running`, `retry_wait`, `succeeded`, `skipped`, `dead` или `cancelled`. У job есть `dedupe_key`, счётчик попыток, `available_at`, owner lease и последняя ошибка. Если процесс падает во время исполнения, истёкший lease возвращает job в очередь; после лимита попыток job переходит в `dead`.

Worker последовательный: один server process исполняет **один автоматический role run за раз**. Это намеренная безопасная capacity policy для текущего single-server SQLite-развёртывания. Для одной карточки база дополнительно запрещает два `running` job. Внешний комментарий владельца будит роль, но собственный комментарий роли не создаёт зацикленный wakeup.

Выключенная владельцем автономная «Система» не завершает job успешно и не расходует попытку. Job переходит в `retry_wait`. Ручной запуск владельцем остался отдельным синхронным сценарием, совместимым со старым интерфейсом.

## Что **не** сделано

1. **Не выполнены push, PR, merge и production deploy.** Ветка локальна и чиста. Перед любым внешним действием нужно просмотреть diff и получить доступ на push.
2. **Не проведена живая C3-проба с реальной моделью.** Unit/integration tests покрывают durable C3-chain, но настоящая Pi-сессия не запускалась. Причина: в этой работе не включалась production «Система» и не создавались реальные пробные карточки.
3. **C4 не начат.** Не удалялись legacy role tokens, `roleRunAccess.ts`, временный JWT/MCP-путь, старые Pi-профили, `team_catalog`, embeddings и прочие исторические источники. Это намеренно: удаление требуется проводить только после периода стабильной эксплуатации и отдельной проверки consumers.
4. **Единый Role aggregate не завершён.** Модель и fallback по-прежнему конфигурируются не тем же CRUD-контрактом, что title/summary/prompt роли. YAML, prompt files, legacy-артефакты и части UI ещё нужно постепенно сводить к согласованному контракту.
5. **Web Team CRUD и iOS model flow не реализовывались.** Серверный API ролей существовал до этого этапа; клиентские экраны не расширялись этой работой. iOS build/test не запускались, потому что Ubuntu sandbox не содержит Xcode/macOS toolchain.
6. **У running job нет принудительной отмены.** API отменяет только `queued` и `retry_wait`. Для безопасного cancel живой Pi-сессии сначала нужен отдельный подтверждённый abort-протокол.
7. **Метрики, accounting стоимости и alerting не добавлены.** Очередь имеет видимое состояние и ошибки, но нет агрегированной телеметрии/оповещений.

## Важные ограничения и риски

> Durable queue гарантирует сохранность повода запуска и восстановление job, но не делает внешние действия LLM строго exactly-once. После падения процесс может повторить часть работы, если её инструмент не был идемпотентен. Существующие taskflow route-инварианты и state re-check перед запуском уменьшают риск, но это нужно учитывать при добавлении новых инструментов.

`role_run_jobs` рассчитана на один server process и SQLite. Не нужно запускать несколько независимых server instances на одной базе без отдельной оценки contention и capacity policy. Если масштабирование станет требованием, следующий архитектурный шаг — отдельный worker/broker или формализованный leader lease, а не простое увеличение числа процессов.

API `GET /api/role-run-jobs`, `POST /api/role-run-jobs/:id/retry` и `POST /api/role-run-jobs/:id/cancel` доступны только owner. Retry разрешён для `dead`, `cancelled` и `skipped`; cancel — только для ожидающих job. Операции пишут audit events в ленту карточки.

## Как продолжать работу

### 1. Безопасно опубликовать локальную ветку

Сначала проверить, что удалённая feature-ветка не изменилась и что локальная ветка содержит ожидаемые коммиты:

```bash
git -C /path/to/taskflow-server fetch origin --prune
git -C /path/to/taskflow-server log --oneline origin/feature/reviewer-first-review..manus/roles-hardening-2026-09-23
git -C /path/to/taskflow-server diff --check
```

После этого можно создать обычный push/PR в согласованную ветку. Не нужно переносить изменения вручную по файлам: локальная ветка уже содержит последовательные commits `e56ed70..813b7c1` и должна быть источником merge.

### 2. Провести живую C3-пробу после публикации и deploy

На реальном стенде включить автономную «Систему» обычным владелецким способом. Создать временную карточку, назначить Разработчика, дать ему сделать измеримый первый шаг и перейти в `blocked`. Затем оставить внешний комментарий владельца и вернуть карточку в `in_progress`. Проверить, что:

1. В `role_run_jobs` появился повод `commented` или `assigned`.
2. Job прошёл `queued → running → succeeded` или осмысленный `retry_wait/dead`.
3. Следующий Pi-run использовал сохранённую session directory для пары task+role.
4. Карточка и её event feed показывают последовательный результат.
5. Тестовая карточка удалена после проверки.

Не проводите эту пробу до deploy локальной ветки: иначе она проверит старый fire-and-forget путь, а не durable очередь.

### 3. Наблюдать минимум несколько дней

Перед C4 собрать реальные результаты: число `retry_wait/dead`, причины ошибок, среднее время job, случаи duplicate external actions, количество deferred jobs при выключенной «Системе» и поведение после одного контролируемого рестарта. Если очередь накапливается, сначала найти причину в `last_error`, а не поднимать параллельность.

### 4. Выполнить C4 отдельным обратимым этапом

После стабильной эксплуатации отдельно проинвентаризировать consumers старого `PiRuntimeAdapter.startRun`, `roleRunAccess.ts`, role tokens и профилей. Удалять по одному классу артефактов, с отдельным regression gate и явным решением владельца. Этот этап может менять секреты и рабочие службы, поэтому не должен смешиваться с обычными кодовыми правками.

### 5. Дальнейшие продуктовые задачи

Следующий функциональный пакет должен согласовать единый API-контракт роли с model/fallback/position/revision, затем подключить веб-Team CRUD и iOS model flow к этому контракту. iOS изменения проверять на macOS командой `xcodegen generate && xcodebuild -scheme TaskFlow -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build test` или актуальным destination реального проекта.
