# TaskFlow: каноническое состояние и план развития

**Статус документа:** единственная актуальная точка правды по агентской части TaskFlow  
**Срез состояния:** 24.09.2026  
**Область:** сервер TaskFlow, ролевые агенты, карточки, ролевые чаты, память и дальнейшая интеграция знаний

Старые спецификации, планы, ревью и handoff сохранены неизменными в
`docs/archive/2026-09-24-before-canonical/`. Они нужны как история решений и
доказательств, но не описывают текущее состояние. Если архив расходится с этим
документом и актуальным кодом, приоритет у кода и этого документа.

## 1. Что мы строим

TaskFlow — ядро работы с автономными ролевыми агентами. Пользователь ставит
задачу карточкой, сервер сам будит нужную роль, агент работает с кодом и
TaskFlow, оставляет результат и при необходимости продолжает тот же разговор.
После выполнения пользователь может уточнить результат в чате, не пересказывая
агенту всю историю задачи.

Целевая модель:

1. Роль — постоянный участник команды, а не одноразовый процесс.
2. Карточка — единица управляемой работы, но не обязательное начало каждого
   разговора.
3. Чат — продолжение работы и место для уточнений, а не отдельный агент без
   знания карточки.
4. Документация проекта и база знаний дают агентам долговременный опыт.
5. В будущем один слой контекста позволит подключать локальные, серверные и
   облачные модели, DeepTutor, Obsidian и другие интерфейсы без второго ядра.

## 2. Что сейчас не входит в ближайшую работу

Следующие направления зафиксированы, но отложены до завершения внутреннего
контура TaskFlow:

- объединение RAGFlow, Obsidian, Mnemosyne и файловых источников в универсальную
  базу знаний;
- DeepTutor как исследовательский веб- и мобильный интерфейс;
- автоматический импорт YouTube, ссылок, PDF, изображений и материалов из
  NotebookLM;
- доступ внешних облачных моделей и агентов с других VPS к общей памяти;
- диктовка большой задачи в DeepTutor с передачей Секретарю TaskFlow;
- синхронное отображение хода выполнения в DeepTutor и iOS-приложении.

Это будущий интеграционный слой. Он не должен сейчас менять работающие карточки,
очередь запусков и ролевой runtime.

## 3. Текущее устройство по фактическому коду

### 3.1. Роли

- Источник активных ролей — таблица `roles`.
- Учётка роли имеет id `role_<key>` и системную authority `agent`.
- Business role хранится отдельно в `users.role_key`; зарезервированные ключи
  `owner`, `agent`, `viewer`, `orchestrator`, `service` запрещены.
- Название, краткое описание, инструкция, включённость и порядок находятся в
  БД. Если `roles.prompt` пуст, инструкция читается из
  `server/scripts/role-prompts/<key>.md`.
- Основная модель пока выбирается отдельно через
  `server/scripts/role-routing.yaml` и runtime routing API. Единого агрегата
  роли в одном CRUD-контракте ещё нет.

На 24.09.2026 включены: Researcher, Analyst, Critic/Verifier, Architect,
Builder, QA и Designer.

### 3.2. Выполнение карточки

`server/src/runtime/inProcessRun.ts` создаёт Pi-сессию внутри процесса сервера.
Агент получает:

- полный ролевой промпт;
- рабочую папку проекта;
- ветку Git и список изменённых файлов;
- `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`;
- внутренние инструменты карточек, комментариев, подзадач, review,
  документации проекта и поиска знаний.

TaskFlow-инструменты вызывают сервер через `app.inject` от имени роли. Постоянный
MCP/API-ключ роли для этого пути не нужен.

Системная политика запуска отдельно говорит агенту, что он уже работает на
`.110`: нельзя подключаться SSH обратно на этот же сервер, искать его как
удалённую машину или бесконтрольно обходить NAS и системные каталоги.

### 3.3. Очередь и восстановление

Таблица `role_run_jobs` хранит durable jobs. Реализованы:

- постановка job в одной SQLite-транзакции с изменением карточки;
- dedupe;
- атомарный claim;
- один running job на карточку;
- lease, heartbeat и восстановление после падения процесса;
- retry/backoff, `dead`, `skipped`, `cancelled`;
- продолжение цепочки после подтверждённого прогресса;
- owner API для просмотра, повтора и отмены ожидающих jobs.

Worker намеренно последовательный: один автоматический ролевой запуск на один
server process. Принудительной безопасной отмены уже работающей Pi-сессии нет.

### 3.4. Память запуска по карточке

Сессия хранится по ключу `task + role`:

```text
~/.local/state/taskflow-runs/sessions/<task-id>-<role>/
```

Повторный запуск использует `SessionManager.continueRecent(...)`, поэтому та же
роль в той же карточке продолжает предыдущий разговор.

Живое подтверждение на 24.09.2026: карточка
`c17ef9b6-4c55-49be-98ce-50c1acf7afbb` («ТЗ и план ИИ-агента по тендерам»)
имела два успешных job Researcher, а оба запуска записаны в один общий JSONL
сеанс. Это подтверждает реальное продолжение task-сессии, хотя отдельный
контролируемый сценарий `blocked → ответ владельца → продолжение` ещё следует
провести как регрессионную приёмку.

### 3.5. Обычные ролевые чаты

Чаты используют другой контур: `routes/chats.ts` →
`PiRuntimeAdapter.startChatRun`.

- Контекст сохраняется для пары `chat + role` через `chat_sessions.pi_session_id`.
- В запрос добавляются последние 20 сообщений чата.
- Используется краткий общий промпт роли.
- Полный `rolePromptText`, task-сессия и внутренние `taskflowTools` автоматически
  не подключаются.

Следовательно, память внутри одного чата есть, но работа по карточке и обычный
чат пока не образуют один разговор.

## 4. Матрица фактической непрерывности контекста

| Сценарий | Состояние |
|---|---|
| Повторный запуск той же роли по той же карточке | Работает |
| Автопродолжение после прогресса | Работает, до трёх звеньев цепочки |
| Ответ владельца заблокированной роли через карточку | Исправлен redispatch; нужна отдельная контролируемая приёмка |
| Несколько сообщений одной роли в одном чате | Работает |
| Новый чат с той же ролью | Старый чат автоматически не подключается |
| Новая карточка той же роли | Предыдущая task-сессия автоматически не подключается |
| Чат после выполнения карточки | Task-сессия и результаты автоматически не подключаются |
| Общая память роли между задачами и чатами | Не реализована |
| TaskFlow ↔ DeepTutor/Obsidian/Mnemosyne | Отложено |

## 6. Что делаем дальше

Порядок важен: каждый этап должен давать самостоятельный проверяемый результат.

### Этап 1. Зафиксировать и принять текущий runtime

**Результат:** воспроизводимая базовая линия до новых функций.

- Закоммитить отдельно текущую local-execution policy и её тест, не смешивая с
  документацией.
- Прогнать server build и целевые тесты `inProcessRun`/queue на Node 22.
- Провести контролируемую C3-приёмку:
  `blocked → комментарий владельца → повторный job → тот же session file`.
- Проверить поведение одного контролируемого рестарта во время lease.
- Записать фактические результаты в этот документ, а не создавать новый
  handoff.

### Этап 2. Соединить карточку и чат

**Результат:** пользователь после выполнения карточки задаёт агенту вопрос в
чате, а агент понимает, о какой работе идёт речь.

- Ввести явную привязку чата/сообщения к `task_id` и роли.
- Добавлять в chat run компактный task context: карточка, итог, последние
  значимые комментарии, документы и ссылки на артефакты.
- Не копировать целиком task JSONL в чат. Сессии остаются раздельными, а
  Context Bridge собирает необходимый контекст на входе.
- Использовать полный ролевой промпт и согласованный набор безопасных
  TaskFlow-инструментов в чате.
- Проверить сценарии: уточнение результата, просьба исправить, новый вопрос без
  карточки и переключение между двумя карточками.

### Этап 3. Завершить единый контракт роли

**Результат:** добавить новую роль можно из приложения без ручной правки YAML и
кода.

- Согласовать поля роли: key, title, summary, prompt, enabled, position,
  primary model и revision.
- Перенести model policy под один серверный owner API либо формально закрепить
  отдельный runtime endpoint как часть агрегата.
- Подключить web Team CRUD к этому контракту.
- Удалить оставшиеся ручные словари ролей в вебе и клиентах после проверки их
  consumers.

### Этап 4. C4 — убрать старый внешний контур ролей

**Результат:** у внутренних ролей остаётся один путь выполнения.

- Сначала проинвентаризировать реальные вызовы `PiRuntimeAdapter.startRun`,
  `roleRunAccess.ts`, role tokens и Pi profiles.
- Удалять по одному классу legacy-артефактов с отдельным regression gate.
- Секреты и профили удалять только с явным подтверждением владельца и
  возможностью отката.
- Не удалять внешний MCP/API-контур для действительно внешних агентов: он
  остаётся отдельной границей доверия.

### Этап 5. Довести рабочие возможности

**Результат:** новый внутренний путь покрывает реально нужные сценарии.

Приоритет определяется использованием, а не переносом всего подряд:

1. вложения к комментариям и проектные артефакты;
2. создание задач и проектов, если это действительно нужно ролям;
3. учёт токенов, стоимости и длительности запуска;
4. агрегированные queue-метрики и ошибки;
5. безопасный abort running session;
6. web/search/YouTube/OCR/report — только вместе с будущим исследовательским
   контуром.

## 7. Будущая общая база знаний и несколько точек входа

Это целевая архитектура, но не текущий план реализации.

- **TaskFlow** остаётся ядром задач, ролей, прав доступа, статусов и событий.
- **RAGFlow** может хранить оригиналы и индексировать рабочие документы для
  retrieval; окончательное решение о роли source of truth принимается после
  отдельного аудита экспорта, версий и резервного восстановления.
- **Obsidian** — удобное человеку представление отобранных выводов и заметок,
  а не обязательное место ручного дублирования всех источников.
- **Mnemosyne** — короткие устойчивые факты и состояние между разговорами.
- **DeepTutor** — возможный исследовательский интерфейс: источники, диалог,
  отчёты и мобильный веб-доступ. Он не должен владеть жизненным циклом задач.
- **Context Gateway** в будущем связывает эти хранилища и выдаёт агентам
  контекст по единому контракту с provenance, scope и правами доступа.

Поток будущего исследования:

```text
пользователь / DeepTutor / iOS
        → Секретарь или Researcher TaskFlow
        → карточка и события TaskFlow
        → исследовательские источники
        → отобранный результат в документацию/знания
        → статус и уточнения обратно в TaskFlow/iOS
```

Не каждый разговор обязан создавать карточку. Карточка появляется, когда есть
исполняемая работа, срок, состояние, ответственность или результат, который
нужно принять.

### Единый переключатель «Система» (27.09.2026)

Владелец подтвердил: ВКЛ — автоматические допуск, назначение и запуск новых
задач; ВЫКЛ — только явный запуск выбранной карточки владельцем. Текущий заход
агента заканчивается, новые автоматические продолжения не запускаются.
Отдельное «Автоодобрение задачи» убрано из iOS. «Авторевьюер» задаёт маршрут
проверки, расписание остаётся отдельным индикатором.

Единственное сохранённое значение — `users.task_intake_mode` канонического
владельца: `automatic`/`manual`. `/api/agent-service` читает и сохраняет его;
старый endpoint настроек приёма совместим с тем же значением. Runtime больше
не зависит от `taskflow-trigger.service`. Явный ручной запуск хранится в
`role_run_jobs.manual_start` (миграция 067); право прохода при выключенной
системе проверяется по владельцу и причине `assigned`, обычные задания его
не получают. Диагностические карточки watcher допускаются и назначаются тем
же диспетчером при включённой системе, с повтором отказов без дублей.

Проверка: 72 серверных набора / 562 теста прошли на изолированных БД; отдельно
проверены переключение, сохранение ручного признака и отказ автоматического
запуска при ВЫКЛ. Дополнительные 13 тестов прошли, включая полный ручной заход
с выполнением шага и сдачей в review при выключенной системе. Общую автоматику на production этим изменением не включали.

### Общая постановка задач: сообщения и голосовой Секретарь (27.09.2026)

Голосовой звонок и сообщения владельца используют общий серверный путь
`submitOwnerTaskText → structureDictationToCards → createDraftCards`.
Разбор выполняется с действующим промптом владельца `task_intake`.
Голосовой worker передаёт полную формулировку задачи, включая сроки,
приоритет, метки и исполнителя; отдельно эти поля Gemini не разбирает.

Общий контракт сохраняет дату и время, приоритет P1–P4 и существующие метки.
«Назначь на меня» означает владельца (Максим), в том числе для дочерних
задач. Личные задачи не раздаются агентам даже при включённой системе.
Невозможные даты, время без даты и неизвестные метки дают вопрос для
уточнения; при наличии вопросов карточка остаётся черновиком.
Относительные даты привязаны к текущей дате сервера в TASKFLOW_TIMEZONE
(по умолчанию Europe/Moscow). Исходная формулировка сохраняется вложением.
Режим «Система» фиксируется перед разбором: automatic допускает подходящие
задачи, manual оставляет их для ручного запуска. Дедупликация сообщений
остаётся в существующем chat intake.

Закрытый Unix socket `/run/user/1000/taskflow-secretary/voice.sock`
(каталог 0700, socket 0600) принимает POST /secretary/tasks с `text`
и identity владельца голосовой комнаты. Сервер проверяет канонического
владельца и вызывает общий путь внутри процесса. Старый TASKFLOW_AGENT_TOKEN,
который приводил к 401 Invalid token, не восстанавливался; подпись для
внутреннего /api/tasks больше не нужна. Настройки Gemini/LiveKit сохраняются.

Проверено на живом сервере через функцию голосового worker: карточка
`7a46fff6-7eb5-46a9-a5f9-ebc732a1df0e` «Проверить общий путь постановки»
получила исполнителя Максим, срок 28.09.2026 в 10:00, приоритет P2,
существующую метку Fable, ready_for_pickup=0. Система была manual и не
переключалась. Голосовой сервис перезапущен и работает; разговор через
микрофон после объединения ещё не повторяли.

Проверки: 74 серверных набора / 573 теста, 8 Python-тестов и TypeScript
noEmit прошли. Тестом подтверждён одинаковый результат входов chat и Unix
socket, а также отсутствие автоматического допуска личной задачи.
Исходники перед объединением сохранены в
`/home/maksim/backups/taskflow/unified-voice-intake-20260927-151003`.

### Сводки задач в голосе и чате Секретаря (27.09.2026)

Единый серверный модуль `secretaryTaskSummary.ts` разбирает просьбу и
собирает факты из БД. Голосовой инструмент `task_summary` обращается к
закрытому POST /secretary/summary через тот же Unix socket и проверку
identity владельца. Запросы сводок в чате Секретаря используют тот же
разбор и выборку; обычная переписка продолжает существующую сессию.
Новые MCP-подключения и постоянные ключи не добавлены.

Сводку можно получить по любому исполнителю либо всем сразу. Зависшие —
активные назначенные, но не взятые (`agent_state` пуст), и заблокированные
(`blocked`). Просроченные сроки, будущие сроки, работа, review, завершённые
и задачи без исполнителя — отдельные разделы. Review не считается
завершением. Разделы сроков пересекаются с рабочими статусами: их числа
нельзя складывать. Причины ожидания берутся из очереди, расписания,
допуска и текущего режима системы; отсутствие причины обозначается явно.

Относительные периоды вычисляет сервер в TASKFLOW_TIMEZONE: сегодня,
вчера, завтра, текущая/следующая календарная неделя и месяц, ближайшие
7 дней, ближайший месяц. При смешанной сводке завершённые выбираются по
локальной дате завершения, остальные по сроку. Точный диапазон включителен;
невозможная дата или неизвестный исполнитель не дают произвольной выборки.
Неоднозначность возвращает вопрос. Максимум 30 карточек на раздел, счётчик
учитывает все совпадения и явно показывает число невыведенных карточек.

По умолчанию звонок получает краткий текст для озвучивания и детали.
Только по просьбе «пришли/скинь в чат» worker передаёт send_to_chat=true:
отчёт записывается от u-secretary в chat-secretary и рассылается участникам
обычным chat:new. Подтверждение отправки возможно после получения message_id.
Сводки не создают и не меняют задачи, не переключают систему.

### Уведомления без дублей ленты активности (27.09.2026)

По просьбе владельца действия задач (assigned, commented, reviewed,
agent_state) не дублируются в его уведомлениях. Миграции 068/069
подавляют новые строки этих типов только для users.role=owner, независимо
от писателя (API или служебный скрипт). GET /api/notifications исключает
старые дубли без удаления записей. WebSocket не отправляет владельцу
notification:new для подавленной записи. Лента, комментарии, вердикты,
уведомления о завершении (ранее сохранённые по просьбе владельца), служебные уведомления/сводки и адресные сигналы исполнителям сохраняются.

Миграция отрепетирована на SQLite backup; integrity_check=ok. Резервная
копия: `/home/maksim/backups/taskflow/notification-activity-20260927-161630`.

## 8. Инварианты и ограничения

- `.110` — текущая машина исполнения; агент не подключается SSH к ней самой.
- Сервер запущен из рабочего дерева через `tsx watch`: правка серверного файла
  сразу влияет на production-процесс.
- Не запускать production E2E, создающие карточки, пока автоматика включена.
- Не включать и не выключать пользовательскую «Систему» без прямого указания.
- Не смешивать документационные изменения с чужими незакоммиченными правками.
- Внешнее действие LLM не становится строго exactly-once только из-за durable
  queue; инструменты обязаны повторно проверять состояние и быть идемпотентными.
- Не запускать несколько server processes на одной SQLite-базе без новой
  capacity/leader архитектуры.

## 9. Как поддерживать эту точку правды

- Обновлять этот файл после изменения архитектуры, завершения этапа или
  появления нового подтверждённого ограничения.
- Не создавать рядом новый «финальный план», handoff или альтернативный индекс.
- Сырые исследования и завершённые планы переносить в датированную подпапку
  `docs/archive/`, а не оставлять среди актуальных документов.
- Рецепт повторяемого сбоя хранить в RAGFlow KB; факт о проекте — в памяти;
  итог прикладной задачи — в документации проекта TaskFlow.
- Операционный регламент автономных исполнителей находится рядом:
  `docs/current/taskflow-orchestrator.md`.
- HTML-карта маршрута задачи находится рядом:
  `docs/current/taskflow-task-route-map.html`.
