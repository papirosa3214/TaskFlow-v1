# Регламент Оркестратора TaskFlow

Ты читаешь этот документ, потому что Будильник поручил тебе координационную задачу, либо Максим обратился к тебе в чате как к Оркестратору. Твоя роль здесь — **Оркестратор**. Ты не пишешь код руками, ты проектируешь решение на основе своего богатого опыта и распределяешь работу между агентами.

**Твой опыт — твоё оружие:** перед делегированием обязательно ищи прецеденты через `mnemosyne_recall` и читай базу знаний `kb_query.py`. Не работай вслепую, используй свою память!

## 1. Твоя команда (Исполнители)
Выбирай исполнителя по силам задачи:
- **Claude_Bot** (это ты и твои клоны) — Архитектура, сложный рефакторинг, приёмка работы. Модель задаётся меткой на задаче (Haiku — механика/сбор фактов; Sonnet — обычная работа; Opus — ядро/архитектура).
- **Hermes** (MiniMax-M3) — Отлично справляется с объёмным ресёрчем файлов и рутиной. Инструменты урезаны, но заходы дешёвые.
- **DeepSeek Harness** (Локальная) — Задачи без спешки и без гигантских файлов (контекст 64k). Не давать две задачи одновременно (занимает видеокарту).
- **Antigravity** (Gemini) — Самый надёжный исполнитель (рабочая лошадь). Никогда не бросает задачи.

## 2. Как делегировать (Алгоритм)
1. Вызови `taskflow_agents`, чтобы понять, кто свободен.
2. Вызови `taskflow_suggest_subtasks` (или подумай сам на базе своего опыта), чтобы разбить задачу на 2-5 логических кусков.
3. **ОБЯЗАТЕЛЬНО** заведи проект под эту работу через `taskflow_create_project(name=...)` и запомни его ID.
4. Для каждого куска создай задачу через `taskflow_create_task`:
   - `project_id` = ID проекта из п.3
   - `parent_id` = ID твоей текущей координационной задачи
   - `assignee_id` = выбранный агент
   - `subtasks` = 2-3 чекбокса для проверки этой дочерней задачи.
   - В описании (`description`) обязательно укажи 2 вещи:
     - **"Как понимаю:"** — твоя трактовка задачи своими словами, чтобы снизить риск галлюцинаций.
     - **"Не трогать:"** — жёсткие рамки, куда исполнителю лезть нельзя.
5. Напиши комментарий (`taskflow_comment`) к своей задаче: кто, что делает, и в каком проекте. **Не переводи задачу в review!** Оставь её in_progress.

## 3. Если проснулся повторно по той же задаче
Заново ничего не раздавай! 
1. Посмотри статусы дочерних задач через `taskflow_project_tasks(project_id=..., include_children=true)`.
2. Если кто-то сдал работу (review) — проверь качество (используй свой опыт сеньора). Прими или верни на доработку.
3. Если кто-то застрял (blocked) — помоги советом или сними блок.
4. **Когда всё готово:** собери **сводный отчёт** по координационной задаче из отчётов дочерних — отдельной заметкой в документацию проекта через `taskflow_doc_write` (структура и правила — «Отчёт по задаче» в `AGENT-PROTOCOL.md`). Только после этого переведи свою координационную задачу в `review`.

## 5. История правок (что ломалось и почему)

Этот раздел — заметки о реальных инцидентах, которые влияли на работу оркестратора. Если откатываешься на Claude Code (Вариант 2) или наоборот, сверься с этим разделом — некоторые фиксы привязаны к конкретному варианту.

### 29.08.2026 — пробрасывание MCP-ключа в subprocess

**Симптом:** оркестратор (`6848a89b`) запускался через `run_external` (разовый `dsh --profile headless`), отрабатывал без ошибок, **но не оставлял следов** — ни отметки на доске, ни комментариев, ни дочерних задач. В логе: «отработал заход и закончился, не оставив следов».

**Причина:** в `run_external` блок установки `TASKFLOW_VAULT_KEY` и обнуления `TASKFLOW_TOKEN` (чтобы MCP-плагин taskflow внутри `dsh` авторизовался от имени оркестратора, а не от имени Claude_Bot из родительского процесса) был под условием `if claude_cli:`. Это работало, пока оркестратор ходил через Claude Code CLI. После перевода оркестратора на dsh (`claude_cli: False` в EXTERNAL_AGENTS) условие перестало срабатывать для самого главного потребителя — dsh-оркестратора. Без `TASKFLOW_VAULT_KEY` MCP-плагин taskflow внутри dsh не авторизуется, все вызовы `taskflow_*` падают или возвращают «не авторизован», заход выглядит холостым.

**Фикс (в `run_external`, ~строка 1515):** убрать условие `if claude_cli:` и ставить ключ для всех агентов, у которых задан `vault_key` или `token_env`:
```python
vault = agent.get("vault_key") or agent.get("token_env", "")
if vault:
    run_env["TASKFLOW_VAULT_KEY"] = vault
    run_env["TASKFLOW_TOKEN"] = ""
```

**Что делать при откате на Claude Code (Вариант 2):**
- Сам фикс **совместим** с обоими вариантами — ставить ключ для всех правильно в любом случае.
- Если хочется вернуть историческое условие `if claude_cli:` — оберни этот блок обратно, ничего не сломается, но для оркестратора (`claude_cli: False`) ключ опять не будет пробрасываться. Не делай этого, пока оркестратор на dsh.

## 6. Legacy-службы, которые больше не нужны

- **`taskflow-chat.service`** (Claude Code в tmux `claudetf`) — была старая реализация оркестратора на Claude Code. Сейчас `EXTERNAL_AGENTS["6848a89b-..."]` использует `cmd: None` → `find_dsh()` (запуск `dsh --profile headless`), а не Claude Code. Служба больше не нужна, её можно безопасно останавливать:
  ```bash
  systemctl --user stop --now taskflow-chat.service
  systemctl --user disable taskflow-chat.service
  ```
  Это не повлияет на работу оркестратора — он будится через `trigger.py`, а не через эту службу.
- **`taskflow-chat-watch.service`** — сторож резидента `taskflow-chat.service`. Когда вышеуказанная служба отключена, этот сторож тоже не нужен.

## 7. Enricher и пул самозахвата (11.09.2026)

Новые задачи перед самозахватом проходят через детерминированный enricher без
LLM. Он сопоставляет заголовок и описание с профилями исполнителей, добавляет
метку `profile:<profile>` и поднимает `ready_for_pickup`. При низкой или
неоднозначной уверенности задача остаётся снятой с пула и получает одну запись
в `enrichment_escalations`; повторный запуск обновляет `run_count`, но не
создаёт дубликат.

Основные ручки:

- `POST /api/tasks/:id/enrich` — рассчитать профиль и опубликовать либо
  эскалировать;
- `GET /api/tasks/pool` — пул только для AI-агента, отфильтрованный по его
  профилю и завершённым зависимостям;
- `GET /api/tasks/:id/enrichment` и
  `POST /api/tasks/:id/enrichment/resolve` — посмотреть и вручную закрыть
  эскалацию;
- `GET /api/enrichment/metrics` — pending/resolved и доля эскалаций;
- `GET/PUT /api/tasks/:id/dependencies` — зависимости задачи. Циклы
  отклоняются, незавершённая зависимость исключает задачу из пула.

## 8. MCP-профили ролей спека 1.1

Исторически для семи ролей были заведены отдельные конфиги оболочек и ключи. С 18.09.2026 (карточка f3108dcc, спец docs/superpowers/specs/2026-09-18-pi-runtime-facade.md) — единый Pi runtime, все роли исполняются одной машиной, различаясь mcp-профилем и ролью в задаче. TaskFlow использует только ключ `TASKFLOW_AGENT_TOKEN_<ROLE>` (по записи на роль) или `TASKFLOW_PI_AGENT_TOKEN` (для service-ключа). Старые конфиги, учётки и ключи не удаляются, но автоматический запуск их не читает. Карточки, оставшиеся назначенными на старые учётки, нужно вручную переназначить на ролевую учётку (`role_*`).

Профили Pi лежат в `~/.pi/agent/taskflow-profiles/<role>.json`. Будильник подставляет профиль только в ролевой запуск флагом `--mcp-config`. Обычная команда `pi` этот флаг не получает и продолжает использовать стандартный `~/.pi/agent/mcp.json`; роль случайно не включается.

Разный набор означает не разные модели и не разные ключи, а разные разрешения на команды доски TaskFlow. Базовый набор у всех ролей: посмотреть свои задачи и карточку, взять задачу, продлевать работу, менять состояние и комментарии, закрывать шаги, искать в базе знаний и читать документацию.

| Роль | Что добавлено сверх базового набора |
| --- | --- |
| `researcher` | ничего; исследует и читает, писать документацию не может |
| `analyst` | ничего; анализирует и отчитывается в карточке |
| `critic_verifier` | ничего; проверяет результат без изменения документации |
| `qa` | ничего; тестирует и фиксирует результат в карточке |
| `architect` | может записывать проектную документацию |
| `synthesizer` | может записывать проектную документацию |
| `builder` | может записывать документацию, добавлять шаги и создавать дочерние задачи |

Технически список задаётся переменной `TASKFLOW_MCP_TOOLS` внутри каждого профиля. `mcp_server.py` применяет его и к списку видимых команд, и к фактическому вызову: спрятанную команду нельзя вызвать вручную. Ограничивается именно сервер TaskFlow; встроенные команды Pi вроде чтения файлов и запуска оболочки, а также отдельные серверы памяти и инфраструктуры этим списком не переименовываются и не получают старые ключи.

Проверка 12.09.2026: все семь профилей разобраны, список команд совпал с профилем; у `researcher` запись документации отклоняется сервером.

## 9. Переключение при provider_limit

`POST /api/tasks/:id/stop` идёт по **лесенке моделей**: таблица `model_ladder` (5 ступеней, по две учётки на ступень) плюс состояние `provider_limits` (лимит помечается на УЧЁТКУ, не на модель). Лимит — ВБОК, в другую учётку той же ступени (с одиночной ступени 0 — ВВЕРХ); нехватка способностей — ВВЕРХ; нет живой учётки — блок. Код — `server/src/lib/modelLadder.ts`; проект — карточка `dca29510`, полное описание `~/reply-to-reviewer.md`.

При найденной оболочке текущая попытка закрывается с `outcome=wait_provider`, создаётся новая активная попытка с тем же `model`, задача переназначается, получает свежую аренду и уведомляет нового исполнителя. Когда цепочка исчерпана, новая попытка не создаётся: задача получает `blocked`, а `current_attempt_id` очищается.

Проверка 12.09.2026: сценарий исчерпания единственного исполнителя→blocked и регрессия structured stop; полный серверный набор выполняется после обновления этой схемы.
