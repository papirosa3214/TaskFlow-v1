## 1. Почему три этапа, а не один

Секретарь (`ChatScreen.swift`/`ChatViewModel.swift`) сейчas — отдельная,
более старая реализация чата, никак не связанная с движком обычных ролевых
чатов (`RoleChatsScreen.swift`). Отсюда все нынешние жалобы: голосовые
сообщения не в том формате, «печатает» ненадёжно. Городить голосовой режим
поверх этого кода — значит чинить один и тот же класс багов дважды.
Поэтому сначала выравниваем фундамент, потом строим голос на нём.

## 2. Этап 1 — Секретарь на настоящих рельсах (UI + мозги)

Владелец 25.09.2026 уточнил: «те же рельсы, что у остальных агентов»
означает не только одинаковый вид чата, но и то, что чат реально отвечает
живым ИИ — как у ролей. Проверено: сейчас этого нет вовсе (`chat.ts`,
канал `owner`, не содержит ни одного вызова модели или запуска агента).
Единственная «интеллектуальная» часть — фоновый `ownerDraft.ts`, и он
специально спроектирован БЕЗ агента (решение владельца 08.09.2026) —
только для разбора надиктовки задачи в черновик, не для общего разговора.
Поэтому этап 1 — это два куска работы, которые сдаются вместе, одним
результатом («Секретарь отвечает по-настоящему, чат выглядит как у ролей»):

**2.1. UI/транспорт.** Экран комнаты Секретаря перестаёт быть отдельным
`ChatScreen`/`ChatViewModel` и становится тем же кодом, что рендерит
`RoleChatsScreen.swift` (та же лента сообщений, голосовые пузыри
`VoiceMessageBubble`/`RoleChatVoiceController`, «печатает» через тот же
WS-путь, что я сегодня заново подключил для ролей). Карточка задачи
(`SecretaryDraftCard`) остаётся, но условие показа в `ChatBubble.swift`
(`message.fromUserId == Self.secretaryID`) обобщается на любого
отправителя — задел под этап 3.

**2.2. Мозги.** Секретарь получает реальный ИИ-прогон на свои сообщения —
по аналогии с `startChatRun`/`roleRunAccess.ts`, который сегодня уже
подключён для ролей: системный prompt «ты — Секретарь, личный помощник
владельца», доступ к тем же инструментам TaskFlow, ответ реальной моделью,
а не заглушкой. Надиктовка задач (`ownerDraft.ts`) никуда не девается —
это отдельный, уже рабочий путь именно для «наговорил задачу целиком»;
новый прогон — для всего остального (вопросы, обсуждение, что угодно).
Нужно решить на месте: Секретарь становится ещё одной «ролью» в существующей
табле `roles` (тогда почти всё уже готово, просто завести учётку) или
отдельный, специальный путь — уточнится при работе, не блокирует старт.

**Файлы (ожидаемо, уточнится при работе):**
`Sources/Features/Chat/ChatScreen.swift` (скорее всего удаляется),
`Sources/Features/Chat/ChatViewModel.swift` (удаляется или сильно
сокращается), `Sources/Features/Chat/RoleChatsScreen.swift` (комната
получает параметр «это Секретарь» для карточек), `Sources/Features/Chat/ChatBubble.swift`,
`Sources/Features/Chat/SecretaryDraftCard.swift`, роутинг
(`AppRoute.swift`, `RouteDestinationView.swift`), тесты голосового чата;
на сервере — `server/src/routes/chat.ts`, `server/src/roleRouting.ts`,
возможно `server/src/runtime/PiRuntimeAdapter.ts` (переиспользовать
`startChatRun` для канала owner).

**Риск.** Секретарь ходит по каналу `/api/chat?channel=owner` (старый,
одиночный), обычные роли — по `/api/chats` (новый, множественный). Нужно
проверить на месте, тянет ли обобщённый компонент оба канала одним кодом
или потребуется небольшая адаптация на бэкенде тоже — уточнится в процессе,
не блокирует старт.

### 3.1. Технология: Gemini Live API

Проверил свежие данные (сентябрь 2026), а не по памяти:

- **Gemini 3.8 Live** — вышла 15.09.2026, специально для «real-time AI voice
  agents»: двусторонний голосовой разговор, 97+ языков на лету (включая
  русский), умеет **вызывать функции прямо во время разговора** (то есть
  может дёргать инструменты TaskFlow, а не только говорить), поддерживает
  барж-ин (перебить на середине ответа) из коробки.
- **Бесплатный тираж:** free input/output токены поверх платного тарифа —
  редкость для голосовых моделей такого уровня. Платные ставки, если
  превысим бесплатный лимит: **$3 за 1М входных аудио-токенов, $12 за 1М
  исходящих** (≈ $0.005/мин входа, $0.018/мин выхода) — для личного
  использования одним человеком это копейки, лимит вряд ли когда-то
  выберется.
- Для сравнения — если бы решили не использовать Live API, а собирать
  голос вручную: системный `AVSpeechSynthesizer` бесплатен, но звучит
  заметно роботизированно (ты это прямо отклонил); Google Cloud
  Text-to-Speech (не Live, обычный TTS) — 1М символов WaveNet бесплатно
  в месяц, дальше $4/1М — тоже неплохо, но это только голос, распознавание
  и разговорную логику пришлось бы собирать отдельно самим. **Live API
  закрывает и то, и другое одним сервисом.**

### 3.2. Архитектура подключения (открытый вопрос — решить перед стартом)

Ключевая развилка: **где живёт сессия Live API.**

- **Вариант А — прокси через сервер New-Todoist.** Телефон открывает
  WS-сессию к серверу на .110, сервер сам держит сессию с Gemini (ключ API
  хранится в vault, не на телефоне) и прокидывает аудио туда-обратно;
  function-calling обрабатывает сервер теми же внутренними вызовами
  (`app.inject`), что и текстовый чат с ролями сегодня. Плюс: один ключ,
  один слой авторизации, легко логировать/ограничивать. Минус: лишний
  прыжок аудио (телефон → .110 → Google), для реального времени добавит
  задержку (обычно некритично на своей же сети).
- **Вариант Б — телефон напрямую к Google.** Меньше задержки, но ключ
  Gemini пришлось бы либо зашивать в приложение (риск утечки), либо
  выдавать короткоживущий токен с сервера перед каждым разговором
  (Google Live API поддерживает ephemeral tokens для клиентских
  приложений — это штатный путь для мобильных клиентов). Function-calling
  тогда телефон обязан сам исполнять вызовом к `/api/*` — дублирует логику,
  которая уже есть на сервере для ролей.

**Рекомендация:** вариант А (прокси через сервер) — переиспользует то, что
уже наладили сегодня (роль-скоуп токены, `app.inject`, инструменты
TaskFlow), ключ не покидает .110. Но это решение владельца, не моё —
Вариант Б быстрее по отклику, если задержка окажется заметной на слух.

## 4. Этап 2 — карточка задачи в любом ролевом чате (следующий шаг)

Серверная часть, отдельно от iOS. Когда роль во время чата вызывает
`taskflow_create_task` (инструмент уже доступен ролям в чате после сегодняшней
правки `startChatRun`/`roleRunAccess.ts`), сервер должен положить в тот же
`chat_messages` системное сообщение с `task_id` — тогда уже разблокированная
в этапе 1 карточка (`SecretaryDraftCard`, обобщённая) появится сама.
Сейчас этого хука нет нигде: `ownerDraft.ts` (единственный источник карточек
сегодня) специально спроектирован без участия агента (решение владельца
08.09.2026) — для агентского пути нужен новый, соседний механизм, а не
переиспользование `ownerDraft.ts`.
