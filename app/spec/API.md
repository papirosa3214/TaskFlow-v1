# TaskFlow API — контракт для нативного клиента (iOS/SwiftUI)

Документ составлен по факту чтения серверного кода (`server/src/**`), клиентского
слоя запросов (`src/api/**`) и живой схемы БД (`server/taskflow.db`, снята
`sqlite3 ... ".schema"`) — 31.08.2026. Сервер и API НЕ меняются, документ описывает
то, что уже есть, чтобы нативный клиент можно было написать, не читая веб-код.

Везде, где код и `AGENT-API.md` (корень репозитория) расходятся, ниже приведено
фактическое поведение кода, а расхождение вынесено отдельно в раздел
«9. Расхождения с AGENT-API.md». Где что-то не проверено живым запуском —
помечено «не проверено».

## 1. Базовый URL, транспорт, общие правила

- **Порт сервера:** `3001` (Fastify, `server/src/index.ts`, `PORT`/`HOST` из env,
  по умолчанию слушает на всех интерфейсах).
- **Базовый URL для нативного клиента:** `http://192.168.1.110:3001` — это
  дефолт, зашитый в `src/api/client.ts` для нативной сборки (Capacitor
  `isNativePlatform()`); веб-версия в браузере ходит по относительному пути
  через тот же ориджин (dev-прокси Vite). Для SwiftUI-клиента брать
  `http://192.168.1.110:3001` как базу, все пути ниже — с префиксом `/api`,
  кроме WebSocket (`/ws`, без `/api`).
- **HTTP, не HTTPS.** Сервер поднят по обычному http (LAN, не наружу).
  TLS/сертификатов нет — для `URLSession` при необходимости ATS-исключение
  (`NSAllowsArbitraryLoads` для домена `192.168.1.110`, LAN-адрес).
- **CORS** — это исключительно браузерное ограничение
  (`@fastify/cors`, allowlist `http://localhost:5180`, `http://127.0.0.1:5180`,
  `capacitor://localhost` + env `CORS_ORIGINS`). Нативный `URLSession`
  под CORS не подпадает вообще — можно игнорировать этот механизм полностью.
- **Content negotiation:**
  - Обычные JSON-эндпоинты: `Content-Type: application/json`, тело — JSON.
  - Загрузка файлов (вложения задач/комментариев/чата, аватарки, аудио,
    архив надиктовки) — **сырыми байтами, БЕЗ multipart**: тело запроса —
    это сам файл (`Buffer`/`Data`), `Content-Type` — реальный MIME файла,
    имя файла передаётся в query-параметре `?name=<urlencoded>`. Сервер
    (`server/src/index.ts`) явно отключает встроенный текстовый парсер для
    `text/plain` и регистрирует `content-type parser` для `audio/*` и списка
    MIME вложений, чтобы получать `Buffer`, а не строку.
  - `bodyLimit: 25 МБ` — общий лимит Fastify на тело запроса. Вложения задач
    отдельно ограничены 15 МБ на уровне роута (`attachments.ts`).
- **Форма ошибки — везде одна и та же:**
  ```json
  { "error": "человекочитаемое сообщение" }
  ```
  Код ответа — стандартный HTTP-статус (400/401/403/404/409/500). Отдельного
  машиночитаемого кода ошибки нет, парсить нужно по статусу + при
  необходимости по тексту (тексты на русском). Изредка к `error` добавлены
  ещё поля — например, 400 у `POST /api/chat` при отказе роутинга несёт
  ещё `адресуй`/`ваш_текст` (раздел 5.8) — `error` при этом всё равно
  присутствует, просто не единственное поле.
- **Форматы даты/времени** — три РАЗНЫХ формата, не путать:
  - `created_at` / `updated_at` / `completed_at` / `*_at` в таблицах —
    строка SQLite `DATETIME('now')`, вид `YYYY-MM-DD HH:MM:SS`, **UTC, БЕЗ
    суффикса `T`/`Z`**. Это единственная ловушка: `new Date("2026-08-31
12:00:00")` в JS/Swift по умолчанию парсится как ЛОКАЛЬНОЕ время, а на
    деле это UTC. Веб-клиент обходит это самописной `parseSqliteUtc()`
    (добавляет `Z` перед парсингом). Нативному клиенту нужно делать то же:
    интерпретировать эти строки как UTC (например, добавить `Z`/`+00:00`
    перед `ISO8601DateFormatter`, либо свой формат
    `yyyy-MM-dd HH:mm:ss` с явным `TimeZone(identifier: "UTC")`).
  - `due_date` — календарная дата БЕЗ времени, `YYYY-MM-DD` (строка,
    валидируется на реальность календарной даты на сервере).
  - `start_time` — время суток `HH:MM`, **локальное** (не UTC, не привязано
    к таймзоне — это «на какой час дня» ставить блок в календаре), 24-часовой
    формат, валидируется диапазон.
- **Пагинация** — есть только у чата (`GET /api/chat?before=&limit=`,
  курсор — id уже полученного сообщения, `limit` не больше 50, по умолчанию
  тоже 50). Все остальные списки
  (задачи, проекты, метки, уведомления, комментарии, подзадачи) отдаются
  целиком, без пагинации — на объёме личного трекера это осознанно.
- **Фильтры/сортировка** — в основном на стороне клиента (веб грузит список
  целиком и фильтрует в react-query/JS). Серверные query-фильтры,
  которые есть по факту, перечислены у каждого эндпоинта в разделе 5.

## 2. Авторизация и сессия

Сервер принимает ДВА равноправных способа авторизации почти на всех
data-роутах (проверяется `preHandler: authOrApiToken`, `server/src/auth.ts`):

1. **JWT** — заголовок `Authorization: Bearer <jwt>`. Выдаётся при логине,
   живёт **30 дней** (`@fastify/jwt`, дальше не обновляется автоматически —
   истёк — новый логин).
2. **API-токен** — тот же заголовок `Authorization: Bearer <api_token>`.
   Статичный токен вида `tf_...`, хранится в БД **хэшированным (SHA-256)**,
   значение показывается ОДИН раз при выдаче. Только для получения нового
   api-токена (`POST /api/auth/api-token`) обязателен именно JWT — курицей-
   яйцом токен новый токен не выпустить.

Сервер сам разбирает, что ему прислали (JWT или api_token) — клиенту
достаточно всегда слать один и тот же заголовок `Authorization: Bearer <значение>`
для ЛЮБОГО из двух.

### 2.1. Эндпоинты авторизации

| Метод | Путь                                               | Тело запроса                          | Ответ                      | Заметки                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----- | -------------------------------------------------- | ------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| POST  | `/api/auth/login`                                  | `{ email, password }`                 | `{ token, user: ApiUser }` | Рейт-лимит: 5 попыток/мин на пару IP+email. 401 при неверных данных.                                                                                                                                                                                                                                                                                                                                                                                                                 |
| POST  | `/api/auth/register`                               | `{ name, email, password }`           | `{ token, user }`          | **Закрыта по умолчанию** — 403, если в базе уже есть хоть один пользователь И не выставлен env `TASKFLOW_ALLOW_REGISTRATION=1`. На новой пустой базе — открыта (bootstrap первого владельца).                                                                                                                                                                                                                                                                                        |
| GET   | `/api/auth/me`                                     | —                                     | `ApiUser`                  | Требует Authorization. 401 без токена/при невалидном.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| POST  | `/api/auth/api-token`                              | —                                     | `{ api_token: "tf_..." }`  | **Только JWT** (`authMiddleware`, не `authOrApiToken`) — уже имеющимся api-токеном новый не выпустить. Значение показывается один раз, сервер хранит только хэш.                                                                                                                                                                                                                                                                                                                     |
| PUT   | `/api/auth/profile`                                | `{ name?, avatar_color? }` (частично) | `ApiUser`                  | Обновление профиля текущего пользователя.                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| POST  | endpoint для беспарольного LAN-входа (см. auth.ts) | —                                     | `{ token, user }` или 401  | **Для нативного клиента НЕ ПОДХОДИТ.** Сервер пускает только запросы, «похожие на браузер» (проверка заголовков `Sec-Fetch-*`/`Origin`/`User-Agent` на `Mozilla`, см. `looksLikeBrowser()` в `auth.ts`) — `URLSession` их не шлёт, и это осознанное ограничение (беспарольный вход только для LAN-браузера, не для агентов/скриптов — своя дверь для агента отдельная, см. `AGENT-API.md`). Нативному клиенту использовать обычный `POST /api/auth/login` с email/паролем владельца. |

### 2.2. Хранение сессии

- Веб-клиент хранит JWT в `localStorage` под ключом `taskflow_token`
  (`src/api/client.ts`) — для SwiftUI-клиента это НЕ образец, там нет
  localStorage. Рекомендация: **Keychain** (токен живёт 30 дней, это секрет
  уровня пароля, UserDefaults не подходит).
- 401 от сервера — токен истёк/невалиден. У веб-клиента на этот случай есть
  специальная логика (тихая попытка LAN-релогина, потом редирект на экран
  входа) — она **не применима** к нативному клиенту (LAN-вход не сработает,
  см. выше). Нативному клиенту на 401 — сразу разлогинивать и показывать
  экран входа.

### 2.3. Модель доступа (роли и видимость)

Живой код (`server/src/access.ts`) реализует **ЧЕТЫРЕ** роли/круга видимости,
не три, как описано в `AGENT-API.md` (устарело, см. раздел 9):

| Роль                                         | `users.role`                        | `users.type`     | Права                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------- | ----------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Владелец**                                 | `owner`                             | `human`          | Видит и правит всё. Единственный, кто может удалять (задачи/проекты/метки/агентов). Один на систему (Максим).                                                                                                                                                                                                                                           |
| **Оркестратор**                              | `orchestrator`                      | `ai` или `human` | Видит и правит ВСЁ так же, как владелец (полный CRUD), **КРОМЕ удаления** — любой DELETE для этой роли получает `403` (жёстко зашито одной проверкой `deleteForbidden()` в `auth.ts`, действует глобально на все DELETE-роуты, не точечно по каждому).                                                                                                  |
| **Агент**                                    | `agent`                             | `ai`             | Видит ВСЕ задачи/проекты (`seesEveryTask()` возвращает true для любого `type==='ai'`), но писать/менять может только то, что создал сам или на что назначен (`assignee_id` = его id). Не может ничего удалять. Именно для этой роли работают `claim`/`heartbeat`/`state` (агентский протокол) — они требуют `type==='ai'`, человеку `claim` вернёт 403. |
| **Обычный человек** (самозарегистрированный) | `agent` (то же значение роли в БД!) | `human`          | Видит и правит ТОЛЬКО своё (созданное или назначенное на себя) — `seesEveryTask()` для `type==='human'` не-владельца возвращает false. Важно: в БД у него `role='agent'`, отличие от роли «агент» — только в `type='human'`.                                                                                                                            |

Ключевые функции `access.ts`, которые эту модель реализуют:
`isOwner()`, `isOrchestrator()`, `seesEveryTask()`, `visibleScope()`,
`getTaskForRead/Write/OwnerDelete()`, `getProjectForUser/Write/Filing()`,
`getLabelForUser()`, `allLabelsOwnedByUser()`.

**Чужой ресурс, недоступный по видимости, отдаёт `404`, а не `403`** —
сервер не подтверждает даже факт существования чужого объекта.

## 3. Модели данных

Ниже — поля ровно как в живой БД (`server/taskflow.db`, снята `sqlite3 ...
".schema"`) и в ответах API (`src/api/types.ts` — канонические snake_case
интерфейсы, которые сервер реально отдаёт). Где поле — «derived», оно
вычисляется на каждом ответе сервера, не хранится как есть.

### 3.1. User (`users`)

```
id                  TEXT PK (uuid)
name                TEXT NOT NULL
email               TEXT UNIQUE NOT NULL
password_hash       TEXT NOT NULL      -- никогда не отдаётся в API
role                TEXT NOT NULL DEFAULT 'agent'
                     CHECK IN ('owner','agent','viewer','orchestrator')
type                TEXT NOT NULL DEFAULT 'human'  CHECK IN ('human','ai')
avatar_color        TEXT DEFAULT '#A6A6A6'
initials            TEXT DEFAULT ''
status              TEXT DEFAULT 'offline'   -- 'online' | 'offline', см. 3.1.1
api_token           TEXT                     -- хэш, не сырой токен; не отдаётся
created_at          TEXT DEFAULT (datetime('now'))
is_system_bot       INTEGER DEFAULT 0
created_by          TEXT REFERENCES users(id)
avatar_url          TEXT
avatar_url_working  TEXT
avatar_url_blocked  TEXT
last_seen_at        TEXT      -- НЕ отслежен ни в db.ts, ни в migrations.ts,
                               -- добавлен вручную (см. раздел 9)
```

`role` — ЧЕТЫРЕ значения в CHECK-constraint (`owner`, `agent`, `viewer`,
`orchestrator`), но `viewer` по факту нигде не выдаётся и не используется в
логике доступа (не найдено ни одного места, которое его проверяет) — считать
зарезервированным/неиспользуемым, не проверено на 100%.

Ответ API (`ApiUser`, поля из `types.ts`) — то же самое плюс derived-поля,
которые отдаются ТОЛЬКО в `GET /api/agents` (в задачах/комментариях/чате
приходит укороченный набор `*_name/_color/_avatar_url/_initials`, см. 3.9):

```
activity            "working" | "blocked" | null   -- derived
online               boolean                        -- derived, «запрос был < 1 мин назад»
last_action          string                         -- derived, что делает сейчас
last_action_title    string                         -- derived, название задачи
limits                { remaining?: number|string } | null
```

### 3.2. Project (`projects`)

```
id               TEXT PK (uuid)
name             TEXT NOT NULL
color            TEXT DEFAULT '#4A9FD8'
owner_id         TEXT REFERENCES users(id)
created_at       TEXT DEFAULT (datetime('now'))
position         INTEGER            -- ручной порядок, NULL пока не перетащили
pinned           INTEGER DEFAULT 0  -- 0/1, закреплён наверху блока «Мои проекты»
notes_folder_id  INTEGER REFERENCES journal_folders(id) ON DELETE SET NULL
```

В ответе API добавляется derived `task_count: number` (посчитанное число
задач проекта). `pinned` в TS-типе объявлен как `boolean | number` — сервер
фактически шлёт SQLite-целое (0/1), не JS-boolean; клиенту приводить самому.

### 3.3. Label (`labels`)

```
id        TEXT PK (uuid)
name      TEXT NOT NULL
color     TEXT DEFAULT '#FF7A8A'
owner_id  TEXT REFERENCES users(id)
```

Без derived-полей, отдаётся как есть.

### 3.4. Task (`tasks`)

```
id                  TEXT PK (uuid)
title               TEXT NOT NULL
description         TEXT
due_date            TEXT               -- 'YYYY-MM-DD' | NULL
project_id          TEXT REFERENCES projects(id)
priority            INTEGER DEFAULT 1  CHECK BETWEEN 1 AND 4
assignee_id         TEXT REFERENCES users(id)
creator_id          TEXT REFERENCES users(id)
status              TEXT DEFAULT 'active'  CHECK IN ('active','completed')
created_at          TEXT DEFAULT (datetime('now'))
updated_at          TEXT DEFAULT (datetime('now'))
completed_at        TEXT   -- ставится ТОЛЬКО на active→completed, сбрасывается
                            -- в NULL на completed→active, не трогается никакой
                            -- другой правкой. Для задач, завершённых до введения
                            -- поля, забэкфиллено из updated_at.
agent_state         TEXT   -- 'in_progress' | 'blocked' | 'review' | NULL
                            -- НЕЗАВИСИМО от status — см. раздел 7
agent_heartbeat_at   TEXT
position             INTEGER  -- ручной порядок в колонке доски, NULL пока не
                                -- перетащили; не привязан к одному проекту
agent_session_id      TEXT     -- чья сессия ведёт задачу (X-Agent-Session)
start_time            TEXT     -- 'HH:MM' локальное, NULL = задача без времени
duration_min          INTEGER  -- 1..1440
pinned                INTEGER DEFAULT 0
parent_id             TEXT REFERENCES tasks(id) ON DELETE CASCADE
                                -- ⚠ есть только в живой БД, НЕ создаётся ни
                                -- db.ts, ни migrations.ts — см. раздел 9
```

**`priority` — направление подтверждено кодом** (`src/lib/priority.ts`,
единственный канонический источник надписей/цветов в веб-клиенте — меньшее
число важнее):

| `priority` | Ярлык | Название | Цвет                  |
| ---------- | ----- | -------- | --------------------- |
| 1          | P1    | Срочный  | `#E44332` (красный)   |
| 2          | P2    | Высокий  | `#FF9A14` (оранжевый) |
| 3          | P3    | Средний  | `#4A9FD8` (синий)     |
| 4          | P4    | Низкий   | `#A6A6A6` (серый)     |

Отсутствующий/некорректный приоритет на клиенте по умолчанию трактуется как
P4 (серый) — `getPriorityColor()` подставляет цвет P4 для `null`/
`undefined`/значения вне диапазона.

Derived-поля в ответе API (`ApiTask`, `hydrateTask()`/`withAgentStale()`):

```
agent_stale          boolean | undefined  -- agent_heartbeat_at старше 15 минут
                                            -- при непустом agent_state
                                            -- («агент пропал»), пересчитывается
                                            -- на каждом чтении
agent_started_at      string | null        -- момент последнего claim, из журнала
mine                  boolean              -- ТОЛЬКО в GET /api/tasks (список),
                                            -- завязано на текущую сессию
assignee_name/_color/_avatar_url/_initials  -- join с users, только list/detail
project_name/_color                         -- join с projects, только list/detail
labels                ApiLabel[]            -- всегда
subtasks              ApiSubtask[]          -- всегда
children               ApiTask[] | undefined -- только GET /api/tasks/:id, дочерние
                                              -- задачи (parent_id = этот id)
comments               ApiComment[] | undefined  -- только GET /api/tasks/:id
events                 ApiTaskEvent[] | undefined -- только GET /api/tasks/:id
attachments             ApiAttachment[] | undefined -- только GET /api/tasks/:id,
                                                      -- файлы самой задачи (kind='task')
```

**Важно про `agent_stale`:** порог протухания — 15 минут неактивности
(`isStale()` в `agentState.ts`), это ОТДЕЛЬНОЕ число от аренды `LEASE_MINUTES
= 5` (см. раздел 7) — «протух» и «истекла аренда» это разные вещи, не путать.

### 3.5. Subtask (`subtasks`)

```
id                   TEXT PK (uuid)
task_id              TEXT REFERENCES tasks(id) ON DELETE CASCADE
title                TEXT NOT NULL
done                 INTEGER DEFAULT 0
position             INTEGER DEFAULT 0
agent_state          TEXT
agent_id             TEXT REFERENCES users(id)
agent_heartbeat_at    TEXT
result               TEXT      -- отчёт агента, максимум 400 символов (RESULT_MAX)
agent_session_id       TEXT
```

Derived `state` (вычисляется `withSubtaskState()` при КАЖДОЙ отдаче, не
хранится): `"done" | "running" | "pending" | "blocked"`.

### 3.6. Comment (`comments`) и Attachment (`attachments`)

```
comments:
  id, task_id, user_id, text, created_at

attachments:
  id, task_id, comment_id, user_id, file_name, mime, size,
  stored_name (не отдаётся в API — внутреннее имя файла на диске),
  created_at, kind ('task' | 'comment', default 'comment'),
  chat_message_id  -- заполнено, если вложение прицеплено к сообщению чата
```

Ответ `ApiComment` = поля `comments` + join `user_name/_color/_avatar_url/
_initials` + `attachments?: ApiAttachment[]`. `ApiAttachment` в ответе НЕ
содержит самих байтов файла — только метаданные; сами байты — отдельным
запросом `GET /api/attachments/:id`.

### 3.7. Notification (`notifications`)

```
id, user_id, type, task_id, text, read (0/1), created_at, actor_id
```

`type` — свободная строка, встреченные в коде значения: `"assigned" |
"completed" | "commented" | "subtask_created" | "new_task"` (TS-тип держит
именно этот список плюс `| string`, то есть возможны и другие значения —
парсить как открытое перечисление, не закрытое). Ответ добавляет
`actor_name/_color/_avatar_url/_initials` (кто вызвал событие — может быть
`null` у старых записей, созданных до появления поля) и
`user_name/_color/_initials` (получатель, из LEFT JOIN) + `task_title`.

### 3.8. TaskEvent (`task_events`) — журнал задачи

```
id, task_id, actor_id (NULL = системная запись), kind, field,
from_value, to_value, created_at
```

Только INSERT/SELECT сервером, редактировать/удалять через API нельзя.
`kind` — строка вида `"claimed" | "state_changed" | ...` (не закрытый список,
писать как строку). Пишется при: смене `assignee_id`, `due_date`,

## 4. Реалтайм — WebSocket

Единственный канал реалтайма — **WebSocket**, SSE в проекте нет.

- **URL:** `ws://192.168.1.110:3001/ws?token=<JWT-или-api_token>` — эндпоинт
  **вне** префикса `/api` (это `GET /ws`, зарегистрирован отдельно от
  остальных роутов в `index.ts`). Токен передаётся в query-параметре, не в
  заголовке (WebSocket-хендшейк заголовки не всегда доступны клиентским
  библиотекам) — `userId` резолвится сервером из токена на этапе апгрейда
  соединения; подписаться на чужой поток нельзя даже теоретически.
- **Хендшейк:** сразу после подключения сервер шлёт `{"type":"connected"}`.
- **Keepalive:** сервер периодически шлёт `{"type":"ping"}`, клиент должен
  отвечать `{"type":"pong"}` (или сервер сам разрулит — проверено по коду
  частично, не проверено живым соединением). При потере пинг-понга сервер
  закрывает соединение.
- **Ошибки:** `{"type":"error", ...}` — формат тела не унифицирован,
  не проверено исчерпывающе.
- **Присутствие:** пока сокет открыт — `users.status = 'online'`; при
  разрыве — `'offline'` (`addClient()`/`removeClient()` в `ws.ts`). Это
  единственный механизм онлайн-статуса, отдельного heartbeat-эндпоинта для
  «я тут» нет (кроме агентского эндпоинта аренды задачи в разделе 7, который
  про аренду, не про присутствие пользователя).
- **На каждое `task:*`-событие сервер автоматически** дополнительно шлёт
  APNs push для iOS Live Activity/Dynamic Island (`alsoPushToIsland()` в
  `ws.ts`) — нативному клиенту НЕ нужно вручную инициировать пуш, только
  зарегистрировать токен (раздел 5.13).

### 4.1. Полный каталог событий (`type` в сообщении)

Собран по грепу всех `type: "..."` литералов в `server/src/routes/*.ts` и
`ws.ts`. **`AGENT-API.md` перечисляет НЕПОЛНЫЙ список** (только
`task:created/updated/completed/deleted`, `notification:new`) — фактически
их больше:

| `type`             | Когда шлётся                                                                                                                       | Источник         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `connected`        | сразу после апгрейда сокета                                                                                                        | `ws.ts`          |
| `ping` / `pong`    | keepalive                                                                                                                          | `ws.ts`          |
| `task:created`     | создание задачи                                                                                                                    | `tasks.ts`       |
| `task:updated`     | изменение задачи, когда `status` не меняется на `completed`                                                                        | `tasks.ts`       |
| `task:completed`   | изменение задачи, когда `body.status === "completed"` — **тип выбирается ДИНАМИЧЕСКИ по значению**, это не два разных места в коде | `tasks.ts`       |
| `task:deleted`     | удаление задачи                                                                                                                    | `tasks.ts`       |
| `task:state`       | взятие/продление/смена состояния агентской работы над задачей                                                                      | `agent-state.ts` |
| `task:activity`    | живая лента «что делает агент прямо сейчас» (раздел 5.14), в `AGENT-API.md` не описан вообще                                       | `activity.ts`    |
| `notification:new` | создание строки в `notifications` (assign/complete/comment/...)                                                                    | разные роуты     |
| `chat:new`         | новое сообщение чата                                                                                                               | `chat.ts`        |
| `chat:typing`      | индикатор «печатает»                                                                                                               | `chat.ts`        |

Полезная нагрузка каждого `task:*`/`notification:new` события — сама
сущность (`ApiTask`/`ApiNotification`) целиком, в том же формате, что и
REST-ответ — отдельного «дифф»-формата нет, клиент получает полный
свежий объект и заменяет им локальную копию.

`chat:typing` — минимальная нагрузка (кто печатает, в каком канале,
`гаснет_через_мс` — см. раздел 5.8, поле на русском).

### 4.2. Рекомендации по реконнекту (из кода веб-клиента, `src/api/ws.ts`)

Не обязательные требования протокола, а практические грабли, с которыми уже
столкнулся веб-клиент — стоит повторить в нативном:

- Сокет может остаться в состоянии `OPEN`, но фактически быть мёртвым после
  блокировки экрана/сна устройства (полумёртвое TCP-соединение) — нужен
  собственный сторож по факту ВХОДЯЩЕГО трафика (не только `readyState`),
  который форсирует переподключение, если давно не было ни одного сообщения
  (включая `ping`).
- После разрыва и переподключения — стоит явным REST-запросом обновить
  локальный кэш, а не полагаться на то, что WS сам «досоединится» и пришлёт
  пропущенное — сервер не хранит очередь недоставленных событий за время
  разрыва.

## 7. Агентский протокол работы над задачей — подробно

Не входит в обычный сценарий личного iOS-клиента владельца НАПРЯМУЮ (это
интерфейс для агентов-исполнителей), но нативному клиенту нужно КОРРЕКТНО
ОТОБРАЖАТЬ этот протокол (статус агента на карточке задачи, кнопку
«агент застрял», индикатор аренды) — поэтому описан подробно. Полный текст
регламента — `AGENT-PROTOCOL.md` в корне репозитория (не читан этим
проходом целиком — читан только код, который его реализует).

- **`agent_state`** — поле НЕЗАВИСИМОЕ от `status`: пока агент работает над
  задачей, `status` остаётся `"active"` весь срок работы. `agent_state`
  принимает `null | "in_progress" | "blocked" | "review"`.
- **Аренда (`LEASE_MINUTES = 5`)** — код-константа, проверенный факт.
  ⚠ Комментарий в `src/api/tasks.ts` про «15-минутную аренду» — **устаревший
  и неверный**, ориентироваться только на `LEASE_MINUTES=5` в
  `server/src/agentState.ts`. (Отдельно, «протухание» `agent_stale` в
  разделе 3.4 считается по другому порогу — 15 минут без heartbeat — это
  РАЗНОЕ число для РАЗНОЙ вещи, не путать «истекла аренда» и «агент
  протух».)
- **Заявка (`claim`)** — только `type==='ai'` (человеку 403). 409, если
  задача уже арендована другим агентом и аренда ещё жива. 400, если задача
  не в статусе `active` или уже находится в `agent_state='review'`.
- **Матрица переходов** (`canTransition()`, `agentState.ts`) — переход
  состояния через `POST /tasks/:id/state` проверяется по допустимой
  матрице, не любое значение из любого разрешено (например, повторный вход
  в `in_progress` из `review` — самостоятельный переход со своими
  правилами).
- **Обязательный комментарий** (`commentRequiredFor()`) — переходы В
  `blocked`, В `review`, и `review → in_progress` ТРЕБУЮТ непустого
  `comment` в теле запроса — без него сервер отвечает 400.
- **`RESULT_MAX = 400`** символов — ограничение на `result` подзадачи
  (`PATCH /subtasks/:id`).
- **`AGENT_RULES`** (`GET /agent/rules`) — статичный текст-памятка из 8
  пунктов, который сервер отдаёт агенту при работе; полезно нативному
  клиенту показать этот же текст, если он реализует агентскую сторону
  UI, а не только владельческую.

## 8. Особенности реализации веб-клиента — фоновый контекст, НЕ инструкция для нативного клиента

SwiftUI не использует react-query — ключи кэша и инвалидации ниже приведены
как ОБЪЯСНЕНИЕ поведения (что инвалидируется вместе с чем в существующем
клиенте), а не как список, который нужно буквально повторить в Swift.
Нативному клиенту нужен СВОЙ механизм локального кэша/инвалидации
(`@Observable`-модели, Core Data, простой in-memory кэш — решает автор
клиента), но полезно знать логическую связность:

- **Ключи и инвалидации:** списки задач/проектов/меток/уведомлений
  инвалидируются как единое целое при любой мутации внутри области (создал/
  поправил/удалил задачу → инвалидируется весь список задач, а не точечно
  один элемент) — react-query здесь используется довольно грубо, без
  тонких partial-update оптимизаций в большинстве мест.
- **Оптимистичные обновления** встречаются точечно, не универсально:
  drag&drop задач по доске/календарю (`position`/`start_time`) обновляет
  локальный порядок немедленно, до ответа сервера; перемещение заметок/папок
  в дереве дневника — аналогично. Остальные мутации (создание/правка/
  удаление) ждут ответа сервера перед обновлением UI.
- **Периодические опросы (polling):** список агентов (`GET /agents`) и
  статус `agent-service` опрашиваются с интервалом **15 секунд** для
  обновления «онлайн/офлайн»/«что делает сейчас» — WS-событий на этот
  случай недостаточно (`online`/`last_action` — производные от времени,
  не от факта конкретного события).
- **Пагинация** — только у чата, см. раздел 5.8/1.

## 9. Расхождения с `AGENT-API.md`

`AGENT-API.md` в корне репозитория — не полностью актуален относительно
живого кода на 31.08.2026. Все пункты ниже — фактическая проверка кода
ПЕРЕВЕШИВАЕТ текст документа:

1. **Завершение задачи агентом.** `AGENT-API.md` §8.4.3 утверждает: «Завершить

3. **Каталог WS-событий.** `AGENT-API.md` §5 перечисляет только

   `src/api/tasks.ts` — неверен. Код-константа `LEASE_MINUTES=5`

   (задокументированный повторяющийся паттерн проекта, тот же приём уже
   применялся к `avatar_url` в прошлом). **Практическое следствие: на
   свежесозданной с нуля базе (по одному только коду репозитория, без
   копии живого `taskflow.db`) этих двух колонок не будет** — если
   нативный клиент/тестовый стенд поднимается с нуля, а не от копии живой
   базы, `parent_id`/`last_seen_at` не проверено, будут ли они существовать.
7. **`PUT /api/journal/:date`.** Упомянут в устаревшем комментарии
   `index.ts`, но реально НЕ зарегистрирован (грепом подтверждено
   отсутствие роута) — не включать в клиент.

## 10. Что не проверено до конца (честно, отдельным списком)

- Полные тела запросов/ответов `integrations.ts` (Google OAuth) — пути
  подтверждены, формы взяты из клиентских TS-типов, не вычитаны построчно
  из серверного роута.
- `ai.ts`: `/ai/suggest-subtasks`, `/ai/journal-assist`, `/ai/extract-tasks`
  — пути подтверждены, точные поля тела не вычитаны построчно.
- `chat.ts`: логика `routeMessage()` (подбор адресата), webhook для Hermes,
  почасовая «потолочная» тревога — не разобраны в деталях, не относятся к
  контракту клиента напрямую.
- Точный формат сообщения `{"type":"error"}` по WS — не унифицирован в
  прочитанном коде, не проверено живым соединением.
- `GET /api/agent/can-stop` — назначение понятно по имени и контексту
  (гейт «можно ли агенту завершить сессию»), но форма ответа не вычитана
  построчно.
- Ничего из этого не проверялось живым HTTP/WS-запросом к серверу — вся
  спецификация построена по чтению исходного кода и прямому дампу схемы
  БД, без запуска сервиса (по условию задачи сервисы не поднимались).
