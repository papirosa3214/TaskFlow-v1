впрягаются по графу» больше не требует ни одного прямого `curl`. Живая
приёмка на реальной продовой карточке с `task_dependencies` — единственное,
что остаётся: на проде таких карточек ещё нет.

## Проблема

Исполнитель дочерней задачи получает только собственную карточку и не может
надёжно собрать итог, если он зависит от результатов соседних задач. История
конкретной агентской сессии не является источником истины: после перезапуска,
смены исполнителя или недоступности комментариев контекст теряется.

Нужен серверный, версионируемый и ограниченный контекст ветки исполнения.
Он должен восстанавливаться по ID любой задачи и не должен зависеть от того,
какой агент раньше вёл чат.

## Общая цель

Организовать структурированное выполнение работы внутри родительских и
дочерних задач: сервер определяет порядок, каждый участник получает только
необходимый контекст своей части, а итоговая карточка сохраняет проверяемые
результаты и следы проверки. Контекст ветки, admission и персональные слоты
ролей являются частями одной модели, а не независимыми функциями.

## Решение

Расширить существующий конвейер `TaskContext v1` обязательным
`DependencyContextEnricher`.

Graph-зависимости остаются единственным источником порядка выполнения.
`DependencyContextEnricher` читает их только после допуска задачи и добавляет
в `TaskContext v1` первичный контекст её ветки: цель родителя, принятые
решения, статусы и результаты зависимостей. После него существующие
обогатители базы знаний и Мнемозины добавляют внешний справочный материал.
Так агент получает один пакет, но происхождение каждого раздела остаётся
видимым.

## Уже восстановлено

После перехода от trigger/alarm path к серверному in-process runtime перестал
вызываться существующий builder внешнего контекста. Этот разрыв устранён:
непосредственно перед prompt runtime вызывает тот же `TaskContext v1` builder,
который обращается к базе знаний и Мнемозине. Пакет попадает в prompt роли, а
для первого рабочего запуска назначенного исполнителя его краткая сводка
остаётся комментарием в карточке.

Это не заменяет dependency context: текущий восстановленный слой отвечает за
внешние знания, а `DependencyContextEnricher` добавляет результаты родителя
и зависимостей в тот же размеченный пакет.

Первый срез `DependencyContextEnricher` уже читает существующие
`parent_id`, `task_dependencies` и `artifact_versions`: он добавляет корень
ветки, его недавние заметки, а также прямые и транзитивные зависимости с
их state, result и evidence references. Он не меняет граф, не допускает
задачи сам и не подмешивает несвязанные sibling-карточки.

```text
родитель
  цель, решения, context_version
  |
  +-- исследование A -- completed -- summary + artifact
  +-- контракт B ----- completed -- summary + artifact
  `-- интеграция C --- depends_on A,B
       получает snapshot родителя, A и B перед запуском
```

## Контракт launch context

Перед `claim` сервер собирает один `TaskContext v1`. Его новый раздел
`dependency_context` содержит только данные, необходимые для выполнения
текущей задачи:

```json
{
  "task": { "taskId": "integration-c", "contract": "..." },
  "dependency_context": {
    "version": 7,
    "root": {
      "taskId": "parent",
      "goal": "Собрать проверенный итог",
      "decisions": ["Контракт B принят владельцем"]
    },
    "dependencies": [
      {
        "taskId": "research-a",
        "state": "completed",
        "summary": "Проверены источники и ограничения",
        "artifact": { "path": "docs/.../research.md", "verification": "sources checked" }
      }
    ],
    "openQuestions": []
  },
  "knowledge_context": { "sources": [] }
}
```

`dependency_context` не включает полные приватные чаты, токены или результаты задач,
которые не являются предками, прямыми зависимостями либо их необходимыми
предшественниками. Полный текст результата остаётся в артефакте; в snapshot
попадают короткий итог и ссылка.

## Семантика запуска

1. Диспетчер определяет список `depends_on` текущей задачи из существующего
   графа и проверяет его без циклов.
2. Каждое dependency edge имеет политику допуска: `review` для результата,
   готового к сборке, либо `completed` для результата, который обязан быть
   окончательно принят. Для старых edges действует совместимое значение
   `review`.
3. Если хотя бы одна обязательная зависимость не достигла своей политики,
   задача не запускается. Ей присваивается наблюдаемая причина блокировки,
   но не создаётся attempt.
4. Когда последняя зависимость становится допустимой, сервер повышает версию
   контекста корня и допускает задачу к очереди.
5. Непосредственно перед `claim` runtime запускает
   `DependencyContextEnricher`, затем обычные KB/Mnemosyne enrichers, и
   передаёт объединённый `TaskContext v1` отдельными размеченными секциями.
6. Если за время между допуском и `claim` версия изменилась, runtime берёт
   новую версию; attempt сохраняет фактически использованный номер версии
   для аудита.

Родитель-контейнер не становится исполнителем. Для итоговой сборки создаётся
явная дочерняя задача с ролью `synthesizer` или `critic_verifier` и зависимостями
на нужные результаты.

## Персональные слоты ролей

У задачи остаётся один основной исполнитель в существующем `assignee_id`.
Дополнительные специалисты не становятся вторыми исполнителями в общем поле:
для них создаются изолированные slots, например `qa_verifier`,
`critic_reviewer` или `security_reviewer`.

Каждый slot фиксирует назначенную роль, допустимого пользователя, состояние
`waiting | ready | active | submitted | accepted`, собственную Pi-сессию и
свой контекст. Сервер проверяет slot ID и identity роли на каждом входе и
действии. Поэтому QA видит результат и evidence основного исполнителя, но не
может продолжить его рабочую попытку; разработчик не может открыть окно
Критика; посторонняя роль не может попасть ни в один персональный канал.

Вердикт или узкий результат slot-а возвращается как структурированный вход
в общий `TaskContext v1`. Admission следующего шага ожидает только те slots,
которые указаны в политике данной карточки. Общий чат карточки остаётся
журналом, но не заменяет персональные рабочие окна.

## Оркестратор и `collaboration plan`

Slots сами по себе отвечают только на вопрос «кто и в каком окне выполняет
узкую работу». Они не должны превращаться в набор постоянных ревьюеров для
каждой карточки. Выбор ролей, их порядок, обязательность и перестройка по
результатам принадлежат живому оркестратору.

`collaboration plan` -- это версионируемый ориентированный граф внутри одной
карточки. Он материализует выбранный профиль в slots и их зависимости, но не
заменяет `task_dependencies`: последние по-прежнему задают порядок между
разными задачами дерева.

Каждая версия плана содержит:

- профиль (`single_executor`, `research`, `delivery`, `full_cycle`, `manual`)
  и причину выбора;
- nodes: slot key, роль, обязательность, ожидаемый результат, входы и
  допустимые состояния;
- edges: условия старта (`accepted`, `submitted`, `artifact_ready`) и
  разрешённый параллелизм;
- решение оркестратора: кто и почему предложил, подтвердил или изменил план;
- snapshot контекста, на котором было принято решение.

Первый план формирует оркестратор из цели, типа работы, риска, родительского
контекста и уже известных внешних зависимостей. Владелец может принять
предложение, выбрать более простой профиль или отредактировать до запуска.
В режиме автоприменения оркестратор создаёт только разрешённые политикой
плана slots; сервер всё равно валидирует роли, циклы и права доступа.

Во время работы оркестратор читает структурированные результаты завершённых
slots и может выпустить следующую версию плана: добавить Архитектора при
технической неопределённости, Дизайнера при изменении пользовательского
сценария, повторный QA после исправления или новую дочернюю задачу для
самостоятельного блока. Завершённые результаты и предыдущая версия не
перезаписываются. Изменение обязано иметь причину и становится событием
общего журнала.

Типовой полный цикл выглядит так:

```text
Исследователь -> Аналитик -> +-> Архитектор -+
                              |                +-> Исполнитель -> QA -> Критик
                              +-> Дизайнер ----+
```

Это пример, а не правило для каждой карточки. Для серверной миграции обычно
не нужен Дизайнер; для UX-работы Архитектор может быть необязательным;
простая задача сохраняет единственного исполнителя. Роли выбираются по
профилю и фактической неопределённости, а не автоматически «для всех».

## Данные и API

Минимальная серверная модель:

- `task_dependencies` остаётся единственным источником порядка выполнения;
  новая таблица связей не создаётся.
- Для корневой задачи добавляется монотонный `task_context_version`.
- Для каждого завершённого узла сохраняется структурированный result record:
  `summary`, `artifact_path`, `verification`, `open_questions`.
- `DependencyContextEnricher` собирает `dependency_context` на чтении,
  а не хранит копии полных веток и не обращается к KB/Mnemosyne.
- В attempt сохраняется `task_context_version`; это позволяет
  воспроизвести, по какой версии контекста был запущен агент.

В MVP отдельный публичный endpoint context не добавляется. Runtime использует
внутренний builder, поэтому прежний API карточек не меняется. Внешнему агенту
контекст доступен только в сформированном launch packet.

В первой версии решения владельца и интегратора фиксируются в существующем
описании/результате задачи по утверждённой серверной схеме. Отдельный редактор
решений в iOS не входит в этот этап: он не нужен для корректного запуска.

## План реализации

### Этап 1. Аудит и миграция

В `/home/maksim/Проекты/New-Todoist/server` проверить фактические таблицы,
маршруты и call sites существующих `task_dependencies`, admission и
`TaskContext v1`. Добавить обратимую SQLite-миграцию для version и result
record, без изменения исторических карточек.

Критерий: существующие деревья и одиночные задачи читаются без нового поля;
версия нового корня начинается с `1`.

### Этап 2. `DependencyContextEnricher`

Создать изолированный server-side enricher, который получает task ID,
находит корень, вычисляет транзитивные обязательные зависимости и добавляет
строго типизированный `dependency_context` в `TaskContext v1`. Enricher
отклоняет ссылку вне дерева и цикл; к внешним базам знаний не обращается.

Критерий: unit-тесты подтверждают состав root/dependencies, исключение
несвязанных соседей и стабильную сортировку по dependency order.

### Этап 3. Результат зависимости и policy edges

Добавить единый валидатор структурированного результата при переходе узла в
`review`/`completed` и хранение policy `review | completed` на dependency edge.
Старый строковый result продолжает работать и нормализуется в `summary`, чтобы
не ломать действующих агентов.

Критерий: задача с policy `review` допускается после review предшественника,
с policy `completed` ждёт принятия; зависимость вне дерева и цикл отклоняются.

Первый фундамент введён server-side migration `073_task_dependency_policy`:
`task_dependencies.policy` (`review`/`completed`, по умолчанию `review` —
на живой базе edges пока нет, поведение никого не меняет). `unmetDependencyIds`
учитывает policy: `review` допускает уже на `agent_state='review'`,
`completed` ждёт полного `status='completed'`; полностью завершённая
зависимость закрывает любую policy. `PUT /api/tasks/:id/dependencies`
принимает необязательный `policies` для отдельных edges, обратная
совместимость с плоским `depends_on_task_ids` сохранена. Добавлены
audit-события `dependency_context_updated` (запись edges),
`dependency_context_blocked` (отказ `/claim`) и `dependency_context_used`
(dependency_context реально подставлен в prompt роли). Отдельный
структурированный валидатор результата не понадобился: `artifact_versions`
уже хранит result и evidence, `dependencyContext.ts` читает их напрямую —
старый строковый result проходит без изменений. 604 серверных теста и
`tsc` зелёные, сервис перезапущен, health ok. Версионирование корня
(`task_context_version`) остаётся для этапа 4.

### Этап 4. Admission и runtime

Встроить dependency gate перед созданием attempt. При незавершённых
зависимостях создать понятный blocked event без запуска агента. Перед
`claim` добавить `DependencyContextEnricher` первым в существующий pipeline,
затем сохранить объединённый `TaskContext v1` в prompt/runtime packet и
зафиксировать использованную версию в attempt.

Критерий: интегратор не запускается раньше A/B, после их завершения получает
их итог и артефакты, а повторный admission не создаёт второй attempt.

Dependency gate и `DependencyContextEnricher` перед `claim` уже введены в
этапах 1-3. Из оставшегося сделано: migration `074_task_context_version`
добавила `tasks.context_version`, растёт на корне дерева (новый модуль
`runtime/taskContextVersion.ts`) при каждом переходе задачи ветки в
review/completed; `dependencyContext.ts` отдаёт реальную версию вместо
хардкода `1`. Использованная версия фиксируется не отдельной колонкой на
`attempts`, а в payload уже существующего события `dependency_context_used`
— решение осознанно упрощено: колонка на `attempts` потребовала бы правок
в пяти разных местах создания attempt ради данных, которые и так читаются
из `task_events`. Живой E2E с реальным интегратором (A/B → C) остаётся:
на проде пока нет карточек с настоящими `task_dependencies`.

### Этап 5. Наблюдаемость и E2E

Добавить audit events: `dependency_context_updated`,
`dependency_context_blocked`, `dependency_context_used`. Провести живой
закрытый сценарий: A и B завершаются, C собирает их артефакты, после чего
родитель допускается существующей логикой `admitParentAfterChildren()`.

Критерий: из attempt и task event видно, почему задача была заблокирована,
какую версию она использовала и где лежат результаты предшественников.

Закрыт. Три audit-события введены в этапах 3-4. Живой закрытый сценарий —
тестом в `inProcessRun.test.ts` ("A и B завершаются — C реально получает
их итог в контекст запуска"), не unit-вызовом `buildDependencyContext`
напрямую: A и B проходят настоящий runtime-путь (`claim` → шаг → auto-review
→ приёмка владельцем PATCH), C запускается через `runRoleInProcess`, и тест
проверяет разом все три части критерия — причину, версию и результаты — по
факту, как их увидел бы реальный запуск. `admitParentAfterChildren()` не
трогали: он про существующий parent-child admission, к dependency graph
отношения не имеет, конфликтов не возникло.

### Этап 6. Персональные slots специалистов

Добавить `task_role_slots` как отдельную серверную модель поверх
существующего единственного `assignee_id`. Зафиксировать slot role,
назначенного участника, state machine, требуемый результат и отдельный
session/attempt. Все чтения, действия и Pi-запуски проверяют право роли на
конкретный slot; доступ к обычной карточке сам по себе этого права не даёт.

Критерий: основной исполнитель, QA и Критик имеют независимые рабочие окна;
никто не может открыть или выполнить действие в чужом slot-е; verdict QA/
Критика становится проверяемым входом в admission следующей задачи.

Первый server-side фундамент уже введён migration `070_task_role_slots`:
создание доступно владельцу/оркестратору, участник выводится из канонической
role-учётки, а state machine и сдача evidence проверяются сервером. Отдельный
Pi-session key и узкие инструменты для slot-а уже подключены: slot не видит
инструменты назначения, смены состояния задачи или чужих результатов; он
сдаёт итог только через свой slot API.

### Этап 7. Версионируемый `collaboration plan`

Добавить план как серверную сущность с неизменяемыми revision records и
графом nodes/edges. Каждая новая редакция хранит основание: ручное решение
владельца, предложение оркестратора или реакцию на результат slot-а.
`task_role_slots` остаётся runtime-проекцией утверждённой версии, а не
конкурирующим источником порядка.

Критерий: для одной карточки можно прочитать текущую и предыдущую версии
графа; сервер отклоняет цикл, неизвестную роль и изменение уже принятого
результата.

Первый фундамент этапа реализован server-side migration
`071_task_collaboration_plans`: таблицы plan, node и edge хранят неизменяемое
содержимое revisions. Владелец или оркестратор может создать draft через
`POST /api/tasks/:id/collaboration-plans`; только владелец утверждает его
отдельным endpoint-ом. При утверждении новой revision предыдущая approved
становится `superseded`. Проверки роли, ключей, связей и отсутствия цикла
выполняются до записи графа. Этот этап пока не создаёт runtime slots: черновик
и даже утверждённый plan не может запустить роль сам по себе.

### Этап 8. Первичное планирование оркестратором

Добавить оркестратору инструмент предложения плана. Он получает цель,
родительский `TaskContext`, тип задачи и риск, выбирает профиль и формирует
черновик roles/dependencies. До утверждения новый граф не запускает roles.
Владелец может подтвердить, упростить или вручную изменить черновик.

Критерий: одна и та же входная карточка получает наблюдаемое предложение с
объяснением; простой профиль не создаёт лишние roles, полный -- строит
исследование, анализ, архитектуру/дизайн, реализацию и проверки по правилам.

Первый безопасный проход реализован как `POST
/api/tasks/:id/collaboration-plans/propose`. Параметр `profile: auto`
выбирает template по цели и описанию карточки: `single_executor`, `research`,
`delivery` или `full_cycle`. Последний включает все семь ролей. Endpoint
создаёт только наблюдаемый `draft`, который всё ещё должен утвердить владелец;
он не назначает исполнителя, не materialize-ит slots и не запускает Pi.
Это bootstrap для живого оркестратора, а не замена его содержательного
решения эвристикой.

### Этап 9. Адаптация плана и admission slots

После сдачи slot-а оркестратор получает его структурированный результат через
`TaskContext v1` и при необходимости предлагает следующую revision. Server
admission запускает slot только после выполненных edges текущей утверждённой
версии; независимые nodes могут идти параллельно. Сбой рабочего slot-а не
меняет состояние основной карточки.

Критерий: добавленный по ходу Архитектор блокирует только зависящий от него
слот; повторный QA получает новую работу Исполнителя; основной исполнитель и
специалист не могут случайно изменить состояние друг друга.

Первый admission для утверждённой revision реализован migration
`072_collaboration_plan_slot_admission`. При утверждении plan materialize-ится
в slots с ключами `p<revision>_<node>` и ссылкой на plan/node. Корневые nodes
становятся `ready`, остальные -- `waiting`. Плановый slot нельзя вручную
перевести в `ready` и нельзя запустить из `waiting`: сервер проверяет все
входящие edges. После `submitted` или `accepted` он сам открывает только
следующие nodes, чьи conditions выполнены. Обычные вручную созданные slots
сохраняют прежнюю state machine.

Дополнительно основной исполнитель не обходит ранние фазы: `/claim` читает
текущий approved plan и отказывает с `409`, пока транзитивные предшественники
его role_key не `accepted`. QA и Критик не входят в этот gate, поскольку они
следуют за реализацией.

Переходник сдачи основной попытки в node плана реализован (этап 4):
`advancePrimaryPlanSlot` (`server/src/lib/collaborationPlanAdmission.ts`)
находит узел approved plan по role_key исполнителя и переводит его slot в
`submitted`/`accepted`, вызывая существующий `unlockReadySlots`. Подключено
во всех точках, где основная попытка реально уходит в review (обычный
`/state`, авто-review по закрытию последнего шага в `tasks.ts`/`subtasks.ts`)
и в единственной точке `status='completed'`. Обычный исполнитель работает
через `/claim`+`/state`, а не через slot API — без моста его узел плана
не сдвигался бы никогда, и QA/Критик вечно ждали бы событие, которого нет.
Проверено E2E-тестом: builder сдаёт задачу — qa-node сам открывается в
`ready`.

### Этап 10. Журнал и интерфейс карточки

Показать в карточке краткий граф: текущую revision, активные и ожидающие
roles, причину блокировки и решения оркестратора. Ручная правка доступна
владельцу до запуска и как создание новой revision после запуска; скрытые
персональные окна остаются закрытыми для непричастных ролей.

Критерий: из карточки и audit events понятно, почему роль запущена, чего она
ждёт, по какому контексту сформирован план и кто изменил его последним.

- iOS (LOCK-246): `Sources/Core/Models/CollaborationPlan.swift`,

## Проверки

- Одинокая задача: `DependencyContextEnricher` формирует пустой
  `dependency_context` и не вызывает KB/Mnemosyne сам.
- A и B независимы: могут стартовать параллельно.
- C зависит от A/B: до завершения обеих blocked, после получает оба итога.
- Зависимость вне дерева, отсутствующий ID и цикл: admission атомарно
  отклоняется без attempt.
- Повторная доставка события и повторный admission: без дублирования attempt.
- Перезапуск runtime: новый агент восстанавливает тот же snapshot по task ID.
- Артефакт отсутствует: `dependency_context` явно сообщает об этом, а executor не
  выдумывает результат.
