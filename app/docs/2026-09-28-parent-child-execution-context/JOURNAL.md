# Журнал: контекст ветки задач

## 2026-09-28

### Зафиксировано

- Подтверждена исходная проблема: контекст конкретной агентской сессии не
  может быть источником данных для интеграционной дочерней задачи.
- Найдена существующая основа: dependency graph и `TaskContext v1`.
- Первоначально рассматривался отдельный `ExecutionBranchContext` для
  результатов внутри task tree; это решение заменено ниже расширением
  `TaskContext v1`.
- Создан план в `README.md` этой папки.

### Решение владельца

- Не создавать отдельный `ExecutionBranchContext` и отдельный публичный API
  на первом этапе.
- Расширить существующий `TaskContext v1` обязательным
  `DependencyContextEnricher`.
- Graph-зависимости определяют порядок и не могут быть заменены результатами
  KB/Mnemosyne. После допуска задачи enricher берёт результаты её ветки,
  затем обычный конвейер добавляет внешний справочный контекст.
- Авторитетный пакет собирается непосредственно перед `claim`, а не только
  при назначении, чтобы не передавать устаревшие результаты предшественников.
- Общая цель расширена: структурированное выполнение родительских и дочерних
  задач включает не только порядок и контекст, но и персональные slots
  специалистов. Основной исполнитель остаётся единственным `assignee_id`;
  QA, Критик и другие роли входят только в свои изолированные server-side
  slots с отдельной Pi-сессией и правами.

### Статус реализации

#### Восстановлен базовый `TaskContext v1` для нового runtime

- Установлено, что старый `server/scripts/trigger.py` собирал TaskContext,
  но его журнал перестал обновляться 27 сентября в 14:04. Новый серверный
  `inProcessRun.ts` запускал роль без этого шага.
- В каноническом server checkout с явного разрешения владельца добавлен bridge
  `server/scripts/task_context_bridge.py` и его TypeScript-обёртка
  `server/src/runtime/taskContextBridge.ts`.
- Перед запуском каждой роли runtime снова собирает `TaskContext v1` через
  прежние KB/Mnemosyne enrichers и добавляет размеченный пакет в prompt.
  Для первого рабочего запуска назначенной роли его краткая человеческая
  сводка публикуется комментарием в карточке.
- Reviewer/reply режимы получают пакет только в prompt: это не создаёт
  лишних системных комментариев и не требует прав автора задачи.

#### Ещё не выполнено

#### Начат этап `DependencyContextEnricher`

- Добавлен server-side builder, который читает существующие `parent_id`,
  `task_dependencies` и последнюю `artifact_versions` зависимой карточки.
  В `TaskContext v1` передаются корень ветки, его последние заметки, прямые
  и транзитивные предшественники, их state/result и короткие ссылки на
  evidence. Несвязанные siblings не включаются.
- Builder вызывается прямо перед in-process prompt и передаёт snapshot в
  уже существующий Python bridge; KB/Mnemosyne остаются отдельным слоем
  того же пакета.
- Unit-контракт использует реальную versioned SQLite schema и подтверждает:
  root, порядок `direct -> transitive`, result/evidence и исключение
  несвязанного соседа. Весь адресный набор: 14 TypeScript tests и 15 Python
  tests passed; TypeScript build passed.
- На живой базе на момент проверки нет строк `task_dependencies`, поэтому
  production-проверка не меняла карточки и пока ожидает первую естественную
  ветку с явными dependencies.

#### Начат этап персональных slots

- Добавлена migration `070_task_role_slots`: у задачи может быть несколько
  изолированных slots поверх единственного основного `assignee_id`. Slot
  фиксирует роль, каноническую учётку участника, обязательность, state,
  result и evidence.
- Server API разрешает создавать slot только владельцу/оркестратору. Его
  видят только владелец, оркестратор и назначенная роль; даже основной
  исполнитель карточки не может прочитать или перевести QA-slot. State
  machine: `waiting -> ready -> active -> submitted -> accepted`.
- Адресный тест создаёт задачу с назначенным Разработчиком и QA-slot:
  Разработчик получает `403`, QA сдаёт evidence, владелец принимает итог.
  Совместно с context-тестами: 4 TypeScript tests passed; build passed.

#### Изоляция рабочего runtime slots

- Каждый рабочий slot теперь получает отдельный ключ Pi-сессии
  `taskId + role + slotId`; попытка основного исполнителя не продолжается в
  окне специалиста и наоборот.
- Для slot-а runtime выдаёт только чтение карточки, поиск в базе знаний и
  сдачу собственного результата. Инструменты claim, смены состояния
  карточки, шагов и чужих результатов недоступны.
- Запуск slot-а не передаётся в обычный workflow handoff основной задачи.
  Адресные TypeScript-тесты и `npm run build` прошли; сервис перезапущен и
  health endpoint подтвердил рабочее состояние.

### Решение владельца: полноценный конвейер внутри задачи

- Цель расширена с «добавить QA/Критика» до мультиагентной работы внутри
  одной родительской или дочерней карточки. Исследователь, Аналитик,
  Архитектор, Дизайнер, Исполнитель, QA и Критик являются равноправными
  кандидатами для slots.
- Набор ролей не должен автоматически навязываться всем задачам и не должен
  быть привязан к одной галочке авторевью. Вместо неё вводится профиль
  совместной работы и формируемый из него граф.
- Оркестратор -- живой автор и адаптер графа: он предлагает первоначальный
  план, анализирует результаты и предлагает новую version при изменении
  неопределённости. Диспетчер/сервер не принимает содержательных решений,
  но строго исполняет утверждённый план, изолирует slots и сохраняет аудит.
- Следующий архитектурный этап назван `collaboration plan`: версии графа,
  nodes/edges, причины решений, первичное планирование и контролируемая
  перестройка без перезаписи завершённых результатов.

#### Начат этап `collaboration plan`

- В server migration `071_task_collaboration_plans` введены три таблицы:
  revision плана, его nodes и направленные edges с condition старта.
  Версия хранит профиль, обоснование, версию контекста, автора и факт
  утверждения.
- Владелец и оркестратор создают только draft-план; утверждает его только
  владелец. Утверждение новой ревизии переводит прошлую approved в
  `superseded`, содержимое исторических nodes/edges не переписывается.
- Новый API валидирует известные роли, лимиты, уникальность slot keys и edges,
  ссылки только на nodes плана и отсутствие циклов. Адресный тест создаёт
  план `Исследователь -> Архитектор`, отклоняет цикл и проверяет замену
  утверждённой версии. Всего с соседними context/slots тестами: 5 tests
  passed; `tsc` passed.
- Миграция применена в рабочей БД, `taskflow-server.service` перезапущен,
  health endpoint ответил `ok`. Пользовательские карточки для проверки не
  создавались и не менялись.

#### Первичное предложение плана

- Добавлен endpoint `POST /api/tasks/:id/collaboration-plans/propose` для
  владельца и оркестратора. `profile: auto` выбирает минимальный template из
  текста карточки; явный профиль остаётся возможен.
- `full_cycle` включает Исследователя, Аналитика, Архитектора, Дизайнера,
  Разработчика, QA и Критика с направленными зависимостями. Endpoint всегда
  сохраняет только `draft`, поэтому не может сам утвердить, назначить или
  запустить роль.
- Адресный тест подтверждает автоматическое предложение полного цикла для
  смешанной UX/API-задачи; вместе с tests plan/slots: 3 tests passed,
  `tsc` passed. Сервис перезапущен, health endpoint ответил `ok`.

#### Materialization и admission slots

- Migration `072_collaboration_plan_slot_admission` связала runtime slot с
  конкретными `collaboration_plan_id` и `plan_node_key`. Утверждение revision
  создаёт отдельный slot для каждого node; ключ содержит номер revision, так
  что новая версия не перезаписывает историю старой.
- Корневые roles становятся `ready`, зависимые -- `waiting`. Плановый slot
  запускается только из `ready`; ручной перевод waiting-slot в ready получает
  `409`, пока не выполнены все входящие edges.
- После `submitted` либо `accepted` сервер перепроверяет waiting-slots и
  переводит в `ready` только действительно разблокированные. Проверенный
  сценарий: Исследователь -> Архитектор; до принятия результатa Архитектор
  не допускается, после -- автоматически готов к запуску.
- 3 адресных tests plan/slots и `tsc` прошли; migration применена в рабочей
  БД, сервис перезапущен, health endpoint ответил `ok`.

#### Admission основной попытки

- `POST /api/tasks/:id/claim` теперь читает текущий approved plan и вычисляет
  транзитивных предшественников для role_key назначенного исполнителя. Пока
  хотя бы один из них не `accepted`, основная попытка получает понятный `409`
  и attempt не создаётся.
- Gate не ждёт nodes после основной реализации: QA и Критик не создают
  дедлок до старта Разработчика. Карточки без approved plan не меняют
  поведение.
- `tsc` прошёл, сервис перезапущен, health endpoint ответил `ok`. Нужен
  отдельный переходник сдачи основной попытки в node плана, чтобы после неё
  автоматически открыть QA.

#### Policy `review`/`completed` на dependency edge и audit-события

- Server migration `073_task_dependency_policy` добавила `task_dependencies.policy`
  (`review`/`completed`, по умолчанию `review`). На живой базе edges на момент
  миграции не было — поведение существующих карточек не изменилось.
- `unmetDependencyIds` (`server/src/enricher.ts`) стал policy-aware: `review`
  допускает предшественника уже на `agent_state='review'`, `completed` ждёт
  `status='completed'`. Первая версия условия молча ломалась через тройную
  логику SQL (`t.agent_state = 'review'` при `NULL` даёт `NULL`, а не `false`,
  и гасило весь `WHERE` через `NOT`) — поймано красными тестами, исправлено
  через `COALESCE(t.agent_state, '')`.
- `PUT /api/tasks/:id/dependencies` принимает необязательный `policies`
  (`{taskId: policy}`) поверх прежнего `depends_on_task_ids`; неизвестное
  значение отклоняется `400`. Обратная совместимость проверена: старые тесты
  с плоским списком id прошли без изменений.
- Audit-события через существующий `logEvent`/`task_events`:
  `dependency_context_updated` при записи edges, `dependency_context_blocked`
  при отказе `/claim` (с списком неудовлетворённых id), `dependency_context_used`
  при фактической подстановке `dependency_context` в prompt роли
  (`inProcessRun.ts`).
- Отдельный «единый валидатор структурированного результата» не понадобился:
  `artifact_versions` (result + evidence_json) уже структурирован и
  `dependencyContext.ts` читает его напрямую; старый строковый result проходит
  без изменений.
- Проверено: 604 серверных теста (в т.ч. 4 новых адресных на policy и
  audit-событие блокировки) и `tsc` — зелёные; `taskflow-server.service`
  перезапущен, health ok, `PRAGMA table_info` подтвердил колонку `policy`.
- Не сделано: монотонный `task_context_version` на корне ветки (нужен для
  этапа 4, чтобы attempt мог зафиксировать использованную версию) и живая
  приёмка на карточке с реальными `task_dependencies` — таких карточек на
  проде пока нет.

#### Версионирование корня и мост основной попытки в collaboration plan

- Использованная версия фиксируется не отдельной колонкой на `attempts`

  одного поля избыточно), а в payload уже существующего audit-события
  `dependency_context_used`: `{version, dependencies}`.
- Переходник основной попытки: `advancePrimaryPlanSlot`
  (`server/src/lib/collaborationPlanAdmission.ts`) — обычный исполнитель
  работает через `/claim`+`/state`, а не slot API, и без моста его узел

  пройденное состояние назад), пишет `primary_plan_slot_advanced` и зовёт
  `unlockReadySlots` (экспортирован из `routes/task-role-slots.ts`, раньше
  был приватным).
- Подключено в трёх точках `review` (`routes/agent-state.ts` — обычный
  `/state`; `routes/tasks.ts` и `routes/subtasks.ts` — авто-review по
  закрытию последнего своего шага) и в единственной точке
  `status='completed'` (`routes/tasks.ts` PATCH — других мест, где
  `status` становится `'completed'`, в кодовой базе нет).
- E2E-тест `primaryPlanSlotBridge.test.ts`: approved план `builder → qa`
  (edge `submitted`); builder сдаёт через `/claim`+`/state review` — его
  slot уходит в `submitted`, qa-slot сам открывается в `ready`, событие
  записано, версия контекста выросла; после `PATCH status=completed`
  build-slot доходит до `accepted`. Отдельный тест: без approved plan мост
  не пишет ничего.
- Проверено: 606 серверных тестов и `tsc` — зелёные; `taskflow-server.service`
  перезапущен, health ok, `PRAGMA table_info` подтвердил `context_version`.

#### Автостарт роли при готовности slot'а

- Разрыв между замыслом и кодом: `unlockReadySlots()`
  (`routes/task-role-slots.ts`) при выполнении условий графа переводила
  `task_role_slot` из `waiting` в `ready` и писала событие `role_slot_ready`
  — и всё. Реальный старт роли (`runRoleInProcess`) был реализован только
  вручную, отдельным `POST /api/task-role-slots/:slotId/run`: владелец,
  оркестратор или сам участник slot'а должен был сам его дёрнуть. Ни один из
  вотчеров (`scripts/*_watch.py`) про `task_role_slots` не знал. То есть
  граф строился и слоты открывались по порядку, но роль в них не «впрягалась
  сама».
- Тело `/run` (проверка `ready` → `active` → `runRoleInProcess` →
  `role_slot_started`, либо откат в `ready` + ошибка) вынесено в общую
  `startSlotRun(slotId, actorId)`. `unlockReadySlots` стала `async`: для
  каждого только что открытого slot'а сразу вызывает `startSlotRun` —
  в своём `try/catch`, чтобы неудача одного (например, недоступна модель) не
  останавливала открытие соседних независимых веток; на неудаче — новое
  событие `role_slot_autostart_failed`, slot остаётся в `ready`, ручной
  `/run` — рабочий fallback. `await` прокинут по всей цепочке вызовов:
  оба места в `task-role-slots.ts`, `advancePrimaryPlanSlot()` (ставшая
  `async`) и её 4 вызывающих места в `tasks.ts`/`subtasks.ts`/
  `agent-state.ts`. В `agent-state.ts` вызов лежал внутри синхронного
  колбэка `db.transaction()` (better-sqlite3 не умеет в async-транзакции) —
  вынесен наружу через флаг, `await` — сразу после коммита транзакции.
- Тесты: `primaryPlanSlotBridge.test.ts` и `task-collaboration-plans.test.ts`
  создают реальный `collaboration_plan` и доводят slot до `ready` — без мока
  они бы дёрнули настоящую модель. Добавлен `vi.mock` на `runRoleInProcess`
  (лёгкая заглушка, резолвится сразу) в обоих файлах; два ассерта обновлены
  под новое поведение (slot, который раньше просто открывался, теперь ещё и
  сам стартует). Новый адресный тест в `task-role-slots.test.ts`: QA-slot
  открывается по графу после сдачи builder'а и без единого ручного `/run`
  доходит до `active`, `runRoleInProcess`-мок реально вызван с нужными

### Следующее действие

Живая приёмка на реальной продовой карточке с настоящими
`task_dependencies` и с реальным `collaboration plan`, прошедшим весь путь
(автопредложение → утверждение владельцем → автостарт по графу) —
появится с первым естественным сценарием. Живой оркестратор, который сам
анализирует результаты завершённых slots и предлагает следующую revision
`collaboration plan` по их итогам, — это уже не код, а поведение/инструменты
роли-оркестратора, не серверная фича. Кнопка утверждения в приложении и
автостарт корневого slot'а — сделаны (LOCK-249, см. выше).
