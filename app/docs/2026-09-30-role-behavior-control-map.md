# Карта управления поведением ролей TaskFlow

Дата сверки: 30.09.2026. Это инвентаризация, не изменение поведения.

## Главное

Постоянная личность роли в текущем in-process runtime задаётся ровно двумя
частями: системной инструкцией роли и общей политикой локального запуска.
Всё остальное либо выбирает модель/исполнителя, либо добавляет контекст одного
запуска, либо жёстко запрещает действие на сервере.

`roles.prompt` имеет приоритет над `scripts/role-prompts/<role>.md`.
Пустое значение в базе возвращает роль к файлу. На момент сверки семь основных
ролей читают fallback-файлы; только Секретарь имеет непустой промпт в базе.

## Рычаги, которые действительно действуют

| Поверхность | Где владелец её видит | Что меняется | Когда действует | Фактический статус |
| --- | --- | --- | --- | --- |
| Инструкция роли | Настройки → Команда → тап по роли → поле «Инструкция» | `roles.prompt`; непустой текст перекрывает файл fallback | Каждый новый запуск задачи и каждый новый ход чата | **Постоянный характер роли. Главный рычаг.** |
| Сброс инструкции | Там же → «Сбросить на файл» | `roles.prompt = NULL` | Следующий запуск/ход | Возвращает `scripts/role-prompts/<role>.md` |
| Включение роли | Настройки → Команда → «Включить/Отключить роль» | `roles.enabled` | Подбор, запуск и видимость доступной роли | Меняет доступность, не текст личности |
| Модель роли | Настройки → Команда → профиль роли → «Основная модель» | `scripts/role-routing.yaml`, `models.<role>` | Новый запуск задачи и чата | Меняет модель, а значит стиль/способности, но не системную инструкцию |
| Задача и лента | Карточка задачи: название, описание, шаги, последние комментарии, зависимости, артефакты плана | launch-context и текст пользовательского задания | Только конкретный запуск | **Очень сильный временный контекст**, но не изменение личности |
| Чат с ролью | Вкладка «Чат» → комната | Последние сообщения комнаты + сохранённая Pi-сессия для пары чат/роль | Следующий ход именно в этой комнате | Влияет на разговор; новая комната/сессия не меняет базовую инструкцию |
| Назначение / @упоминание | Карточка задачи или чат | Выбирает, какая роль получит задачу/ответит | Конкретное событие | Меняет исполнителя, а не характер ролей |
| Семантический подбор | Скрытый серверный слой `role_embeddings` | Теги и векторы выбирают наиболее подходящую роль | Автоподбор задачи/ответа в чате | Меняет адресата. В UI редактирования нет; таблица правится seed-скриптом |
| Правила жизненного цикла | Серверный код `agentState.ts` | Матрица claim/state/review, heartbeat, обязательные комментарии и т.п. | Немедленно, независимо от промпта | **Жёсткие запреты сервера**: роль не может их отменить своим промптом |
| Общая политика среды | Серверный код `inProcessRun.ts` → `LOCAL_EXECUTION_POLICY` | Правила работы на `.110`, доступные пути, запреты обхода системы | Каждый запуск задачи и чат-ход | Общая добавка к системному промпту всех ролей |
| Инструменты TaskFlow | Серверный код `inProcessRun.ts` и `roleRunAccess.ts` | Список встроенных tool-вызовов и серверная авторизация роли | Каждый запуск | Меняет возможности, а не словесную личность |

## Окна, которые легко принять за настройку роли, но это не она

| Окно / запись | Что кажется | Что происходит на самом деле |
| --- | --- | --- |
| Настройки → Приложение (телефон и сервер) → редактируемые «Системные промпты» | Будто это общий характер команды | Это отдельные пользовательские слои для разбора диктовки в задачи, Дневника, расшифровки действий и постановки задач. Промпт ролей они не меняют. |
| Настройки → Команда → «Навыки», «Инструменты», «Права» в профиле роли | Будто эти строки редактируют способность роли | Сейчас это преимущественно диагностика/показ профиля. В текущем in-process запуске `resourceLoader` возвращает пустые skills, prompts и AGENTS files. |
| `users.prompt`, `users.model`, `agent_mcp_servers`, `agent_skills`, permissions в generic API `/api/agents/:id/*` | Будто это альтернативный редактор личности роли | Записи могут сохраняться, но текущий запуск ролей читает `roles.prompt` и `role-routing.yaml`, а не эти поля. На момент сверки в `agent_mcp_servers` и `agent_skills` живых записей нет. Это **декоративные/устаревшие ручки для ролей**, пока runtime не будет подключён к ним. |
| `~/.pi/agent/taskflow-profiles/*.json` и `role_skills` | Будто это подключённые навыки и MCP текущего агента | Профили читаются для карточки/диагностики; старый внешний MCP-путь не подключается к текущему in-process runtime. Не считать их действующим способом поменять поведение. |
| `synthesizer` в profile/role_skills | Будто это живая роль | В текущей таблице `roles` такой роли нет. Следовательно, её профиль и skills не делают её запускаемой ролью. |

## Текущая живая конфигурация ролей

| Роль | Источник инструкции сейчас | Навыки, показанные профилем | Особенность |
| --- | --- | --- | --- |
| researcher | fallback-файл | research, sources | Роль включена |
| analyst | fallback-файл | analysis, reasoning | Роль включена |
| critic_verifier | fallback-файл | review, verification | Роль включена |
| architect | fallback-файл | architecture, design | Роль включена |
| builder | fallback-файл | implementation, sql | Роль включена |
| qa | fallback-файл | testing, validation | Роль включена |
| designer | fallback-файл | accessibility, mobile_design, web_design | Роль включена |
| secretary | `roles.prompt` в базе | — | Единственная роль с DB-override инструкции |

Все основные роли используют `pi_runtime`; в текущем `role-routing.yaml` у них
задана модель MiniMax-M3. Секретарь существует в `roles`, но не в текущем
routing-файле: сервер подставляет значения по умолчанию для роли, которой нет
в YAML.

## Как реально собирается запуск

```
системная инструкция роли (DB или fallback-файл)
  + LOCAL_EXECUTION_POLICY
  + задача/комментарии/зависимости/артефакты плана
  + текст текущего задания
  + для чата: история комнаты и сохранённая сессия
  -> модель из role-routing.yaml
  -> серверные проверки действий и доступные инструменты
```

Важное следствие: чтобы переписать «сознание» одной роли, нужен редактор
`Инструкция` в «Команде». Чтобы направить её в рамках одной работы, достаточно
карточки/комментария или чата. Чтобы изменить то, что она физически может
сделать, нужны кодовая политика, инструменты и серверные проверки — не промпт.
