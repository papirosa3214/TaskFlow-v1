# Сравнение первичных предложений

## Короткий вывод

За основу стоит брать **предложение B** как контрактную спецификацию, а из
**предложения A** — забрать прикладную детализацию шаблонов, минимальные
контуры и риски ошибочной классификации. Ни один документ не следует
переносить в исполнение без ревью конкретных графов.

| Аспект | Предложение A | Предложение B | Рекомендация |
| --- | --- | --- | --- |
| Каталог | 10 понятных операционных сценариев | те же 10, с ID и версиями | сохранить общий каталог, выбрать стабильные ID B |
| Артефакты | очень конкретные: `brief.md`, ADR, отчёт QA | строгая модель type/format/required fields/version | типы и валидацию B + человекочитаемые примеры A |
| Контекст | «передавать узко», описан в таблицах узлов | отдельный `context_packet`, accepted artifacts и evidence | принять B |
| Gate-ы | понятные `submitted` / `artifact_ready` / `accepted` | уточняет различие и запрещает считать `accepted` глобальным стартом | принять B без изменений смысла |
| Условные роли | описаны текстом и минимальным вариантом | формализованы `activation_rule`, `enabled_when`, валидатором | принять B |
| Подбор | правила, теги, embeddings, исключения | правила сначала отсекают, затем семантика ранжирует и объясняет | принять B; embeddings не принимают решение сами |
| Безопасность эволюции | новая версия и owner review | immutable run snapshot, шаблонный валидатор и запрет скрытой замены DAG | принять B |
| План MVP | T05, T03, T01, T08 как возможные первыми | T03, T05, T01, T04 и причины пилота | общие первые три оставить кандидатами; четвёртый выбрать отдельно |

## Что особенно ценно в предложении A

- В каждом шаблоне есть понятное «когда не выбирать»; это нужно сохранить в
  selection-контракте как отрицательные признаки.
- Есть минимальные версии: они не дают маленькой задаче превратиться в
  процесс из семи агентов.
- Артефакты названы конкретно и проверяемо. Именно такие названия должны
  отображаться на рёбрах мобильного графа.
- Риски ошибочной классификации — хороший материал для будущей оценки
  качества подбора.

## Что особенно ценно в предложении B

- Чётко отделены template version, run snapshot и revision работающего
  плана.
- Артефакт имеет версию, evidence, допущения, открытые вопросы и статус;
  это делает handoff проверяемым, а не «роль что-то написала в чате».
- Условный узел — не просто опциональная роль в тексте, а часть валидируемой
  схемы. После его отключения граф обязан оставаться ацикличным и полным.
- YAML содержит достаточно данных для хранения, проверки, подбора и
  последующего универсального рендеринга.

## Добавлено после проверки вставленных ответов

В двух вставленных текстах были идеи, которых не было в исходных файлах и
которые нужно сохранить в выжимке:

- Для итераций нужны статусы `rejected` и `revision_requested`, лимит
  доработок, тайм-ауты и эскалация владельцу; иначе шаблон описывает только
  идеальный проход.
- Селектор должен уметь честно отказаться: при отсутствии подходящего
  шаблона запросить уточнение или предложить ручной план, а не выбрать
  семантически близкий вариант без объяснения.
- Принятый артефакт должен иметь объявленную совместимость с другими
  шаблонами: например, PRD продуктовой фичи может стать входом документации.
- Каталог следует измерять по успешным стартам, длительности run и
  отклонённым артефактам по ролям. Предлагаемые пороги similarity — лишь
  гипотеза для калибровки, не готовое правило.
- Обязательность QA в малом графе — не решённое противоречие: одна подборка
  считает его неубираемым для продуктовой фичи, другая допускает условный
  узел. Это решение владельца, а не правило, которое надо зашить сейчас.

## Расхождения, которые надо решить владельцу

| Шаблон | Расхождение | Нельзя молча выбрать |
| --- | --- | --- |
| UX-концепт | A начинает с Дизайнера, исследование опционально; B вводит Аналитика перед Дизайнером | зависит от того, обязателен ли product brief для UX-задач без бизнес-неопределённости |
| API-интеграция | A: Исследователь → Архитектор; B: Исследователь + Аналитик → Архитектор | решить, когда контракт и требования достаточно формализованы без Аналитика |
| Баг/регрессия | A использует Исследователя для RCA; B — Аналитика после QA | уточнить специализацию RCA: техническое расследование или структурирование влияния/приоритета |
| Техдолг | A: Архитектор → Разработчик → QA; B добавляет параллельный аудит Разработчика и Аналитика | определить, нужен ли отдельный discovery-контур в малом рефакторинге |
| Инфраструктура | A называет роль «DevOps(Разработчик)» | оставить каноническую роль `Разработчик`, а инфраструктурную специализацию записывать в node title/skill contract |
| Релиз | В обоих вариантах возможны фиксы между QA и решением о выпуске | требуется явный цикл revision или отдельный remediation-subgraph, а не неявная обратная стрелка |

## Проверки перед первой реализацией

1. У каждого input на ребре есть source artifact и потребительский контекст.
2. Все ветки после применения activation rules остаются DAG.
3. `accepted` имеет явного субъекта: владелец, QA или Критик; система не
   подменяет предметное принятие техническим статусом.
4. Артефакт можно физически приложить/сохранить и включить в launch packet,
   а не только назвать в YAML.
5. Тестовый набор содержит графы: одна цепочка, fan-out/fan-in, отключённый
   условный узел, два параллельных узла, и новую revision.
6. Универсальный мобильный renderer получает только нормализованные nodes,
   edges, состояния, артефакты и gate-ы — без специальных `if role ==` или
   `if template == full_cycle`.

## Непринятые предположения

- Каталог из десяти шаблонов не считается обязательным объёмом MVP.
- Семантический подбор не означает автоутверждение или автостарт.
- Предложенные форматы артефактов — гипотезы до проверки на реальных
  задачах; они могут оказаться слишком тяжёлыми для коротких работ.
- Оркестратор пока не получает право незаметно менять работающий план.
