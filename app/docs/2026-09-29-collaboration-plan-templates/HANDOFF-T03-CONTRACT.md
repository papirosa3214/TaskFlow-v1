## Зачем эта работа

Базовый серверный DAG уже умеет запускать независимые задачи параллельно,
удерживать зависимую задачу и передавать ей результат предшественников. T03
добавляет поверх этого не новый scheduler, а воспроизводимый выбор ролей,
артефактов и условий внутри одной продуктовой работы.

## Основание

- Базовый контракт берём из предложения B: строгие артефакты, условия включения
  ролей и immutable revision.
- Из предложения A сохраняем ясные причины выбора/невыбора и понятные
  человекочитаемые артефакты.
- Существующий `TaskContext v1` и `DependencyContextEnricher` остаются
  единственным способом передать результаты предшественников следующей роли.

## Предлагаемый контракт T03/1.0

### Применимость

Шаблон предлагается, когда есть новая ограниченная пользовательская или
бизнес-возможность с проверяемыми acceptance criteria. Он не выбирается для
исследования необходимости функции (T01), подтверждённого дефекта (T05) или
работы, где главным результатом является внешний API-контракт (T04).

### Узлы и выходы

| Узел | Роль | Вход | Обязательный выход |
| --- | --- | --- | --- |
| A1 | Аналитик | постановка, ограничения, существующие данные | `feature_spec`: scope, out_of_scope, правила, AC, NFR, analytics events, open questions |
| H1 | Архитектор, только по триггеру | `feature_spec` | `architecture_decision`: варианты, решение, последствия, rollout/rollback |
| D1 | Дизайнер, только по триггеру | `feature_spec`, дизайн-система | `feature_ux_spec`: экраны, state matrix, доступность, UX-copy |
| V1 | Разработчик | `feature_spec` и включённые H1/D1 | `implementation_pack`: изменения, build ID, миграции, тесты, deployment notes |
| Q1 | QA, только по триггеру | `implementation_pack`, `feature_spec`, UX-спека при наличии | `feature_test_report`: AC → результат → evidence, defects с severity |

### Рёбра и gate-ы

**Обновлено 29.09.2026:** владелец участвует только в approve плана
(старт); все остальные переходы — `artifact_ready`, не `accepted`. Подробно
и с обоснованием — [дизайн T03](t03-product-feature/T03-ARTIFACT-CONTRACT-DESIGN.md#gate-ы-t03).

| От → к | Артефакт | Gate |
| --- | --- | --- |
| A1 → H1, если H1 включён | `feature_spec` | `artifact_ready` |
| A1 → D1, если D1 включён | `feature_spec` | `artifact_ready` |
| A1 → V1 | `feature_spec` | `artifact_ready` |
| H1 → V1, если H1 включён | `architecture_decision` | `artifact_ready` |
| D1 → V1, если D1 включён | `feature_ux_spec` | `artifact_ready` |
| V1 → Q1, если Q1 включён | `implementation_pack` | `artifact_ready` |

### Триггеры условных узлов

- H1 обязателен при кросс-сервисном, контрактном, миграционном или существенном
  NFR-изменении.
- D1 обязателен при новом либо существенно изменяемом пользовательском пути.
- Q1 обязателен для пользовательского, интеграционного или
  регрессионно-опасного изменения.
- Критик в T03/1.0 не включается автоматически.

Минимальный маршрут: `A1 → V1`. Отсутствие H1, D1 или Q1 фиксируется в
`feature_spec` вместе с причиной.

## Поведение при неидеальном проходе

- Артефакт может быть `rejected` или `revision_requested`; следующий узел не
  стартует до выполнения gate-а.
- Лимит возвратов, тайм-аут роли и маршрут эскалации владельцу задаются в
  revision плана, а не скрытой логикой исполнителя.
- Если селектор не видит подходящего шаблона, он возвращает объяснимый отказ
  и предлагает ручной план, а не подменяет T03 ближайшим вариантом.

## Критерии приёмки первого инкремента

1. Из утверждённого T03 создаётся DAG A1/V1 и только оправданные H1/D1/Q1.
2. Невключённый условный узел не оставляет висячих рёбер и не меняет порядок
   остальных ролей.
3. V1 получает только объявленные входные артефакты A1/H1/D1 через
   существующий `TaskContext v1`.
4. Q1 не стартует без `implementation_pack` в состоянии `artifact_ready`.
5. Мобильный экран отображает nodes, edges, артефакты и gate-ы revision без
   ветвления по имени T03 или роли.
6. Все события запуска и использованная версия контекста остаются аудируемыми.
