# Управление всеми источниками инструкций ролей

Статус: проект решения для согласования, 30.09.2026. Владелец подтвердил, что нужен редактор всех действующих текстовых инструкций. Это расширяет прежний этап, в котором редактировалась только личность роли.

## Зачем

В «Команде» владелец должен видеть и менять инструкции, которые действительно получает модель. Старый текст, дополнительная чат-обёртка или серверное правило не должны оставаться скрытыми. Показ и запуск используют один источник. Успех — изменение в интерфейсе отражается в следующем соответствующем ходе модели и подтверждается тестом реальной сборки контекста.

## Выбранный подход

Предлагается серверный каталог инструкций: дефолты извлекаются из действующего runtime, настройки владельца хранятся в БД. Каждый путь запуска получает текст через общий resolver; тот же resolver питает редактор.

Альтернативы: редактировать исходники прямо с телефона — связывает настройку с деплоем и рестартом; добавить отдельные пользовательские дополнения — оставляет устаревший hardcode действующим. Каталог с заменой эффективного текста даёт нужный контроль и сохраняет возврат к исходному значению.

## Экран

«Настройки → Команда → роль → Контекст и инструкции». Разделы:

| Вкладка | Редактируемые блоки |
| --- | --- |
| Роль | Личная инструкция: существующий roles.prompt, fallback и сброс |
| Общее | Общая политика среды и текстовые правила работы с TaskFlow |
| Задача | Первое задание, продолжение, ответ на комментарий, поиск документации |
| План | Задание собственного шага и требования сдачи артефакта |
| Проверка | Задание проверяющего и формат вердикта |
| Чат | Обёртка обычного чата; для Секретаря его собственная обёртка и быстрые ответы |
| Контекст | Правила обращения с найденными знаниями, памятью и проектом; сведения об источниках динамических данных |
| Возможности | Реальные инструменты, skills/AGENTS, модель, ограничения и различия путей запуска |

У Секретаря дополнительно видны текстовые инструкции голосового пути и внутренних модельных операций (например, разбор запроса сводки). Тексты встроенных tools и дополнительные runtime-инструкции показываются отдельными блоками в «Возможностях» с пометкой, можно ли заменить их описательный текст.

Для каждого текстового блока показываются: эффективный текст; исходный текст; источник; режимы применения; область изменения («вся команда» или конкретная роль); версия; когда применяется. Сохранение явно сообщает количество затронутых ролей для общего правила. Системный селектор и редакторы без визуальной имитации нативных компонентов. Состояния загрузки, ошибки и несохранённых правок явные.

Три действия: «Сохранить», «Отменить правки», «Вернуть исходное». История изменений позволяет восстановить предыдущий текст. Вкладка будущего типа остаётся видимой старому клиенту.

## Приоритеты и хранение

Для нового текстового блока: override конкретной роли → общий override команды → дефолт runtime. Не каждый блок допускает все три области: каталог описывает допустимые scope, чтобы личная инструкция одной роли не стала общей.

Личность сохраняет существующий приоритет roles.prompt → fallback-файл → минимальная инструкция роли. Второго хранилища личности не создаём.

Для остальных блоков — таблица версионированных overrides, уникальная пара scope/layer_id, автор и время изменения; журнал прежних значений. Хранится текст или явное состояние отключения. Пустой текст не означает случайный сброс: интерфейс различает «отключить текстовый блок» и «вернуть исходное». Проверка версии предотвращает молчаливую перезапись конкурентных изменений.

Плейсхолдеры taskId/taskTitle/roleTitle/history/userText и прочие объявлены каталогом конкретного шаблона. Сервер проверяет неизвестные и обязательные поля, размер текста и отсутствие управляющего исполнения. Шаблон подставляет данные как текст, без eval. Структура tool schema и формат обязательного машинного JSON остаются программным контрактом; рядом показывается пояснение, почему они обязательны.

## Одна сборка для показа и запуска

Обычная задача, продолжение, план, проверка, ответ на комментарий и чат получают тексты из общего каталога. Сборка возвращает также manifest использованных блоков и версий. В фактическом запуске фиксируется manifest, чтобы было понятно, какая версия использовалась.

Новый запрос запуска получает свежую версию. Уже выполняющийся ход не прерывается. Сохранённая сессия не сбрасывается автоматически; UI предупреждает, что прежние ответы и инструкции могут оставаться в истории, и отдельно показывает источник этого влияния. Для чат-процесса требуется проверить и явно определить системный промпт Pi, локальные/global AGENTS, skills, extensions и MCP-инструкции. Нельзя показать только user-пакет и назвать его полным системным контекстом.

Задачи и чат могут иметь разные реализации runtime, но не разные скрытые источники управляемых правил. Возможности и список инструментов вычисляются по фактическому режиму, а не по декоративным строкам профиля.

Тексты правил, повторно возвращаемые моделью через taskflow_rules, claim/state и MCP, используют тот же источник, что редактор. Описания инструментов входят в каталог: их текст можно изменять, имена, параметры и обработчики выполняются по программному контракту.

## Что текстовая правка не меняет

Авторизация, матрица состояний, обязательные поля артефакта, выдача токенов, доступные обработчики tools и маршрутизация модели остаются отдельными механизмами. Их текущие значения и происхождение видны в «Возможностях». Замена инструкции не объявляется изменением этих механизмов.

Динамические данные карточки, память, найденные документы, история чата и предыдущая сессия не превращаются в редактируемые настройки роли. Их источники и правила добавления видны; фактическое содержимое конкретного запуска — отдельный просмотр с правами на эту карточку/чат. Этот этап фиксирует manifest постоянных инструкций, не реализует полный инспектор конкретного запуска.

## API

Расширяется GET /api/roles/:role/runtime-context: groups, blocks, source, modes, change_scope, editable, effective_text, default_text, version, placeholders и действующие runtime capabilities. Секреты, токены и временные MCP-файлы не выдаются.

PATCH настройки блока и DELETE сброса доступны только владельцу. PATCH требует ожидаемую версию; конфликт — 409 с текущей версией, без потери локального черновика. Общий scope меняет блок команды явно, роль scope — только указанную роль. Возврат предыдущей версии создаёт новую запись истории, не стирает журнал.

## Первичные находки

1. builder.md требует внешний конверт ok/output/artifacts/error/next_hint/needs_human; этот текст действует и в чате, где сервер уже снимает конверт. Нужно разделить требование результата работы и человеческого чат-ответа.
2. builder.md и qa.md ссылаются на старые поля консультации и HTTP-сценарии. До удаления проверить существование соответствующих данных и инструментов; ссылка на старую спецификацию сама по себе не доказательство, что механизм мёртв.
3. LOCAL_EXECUTION_POLICY жёстко задаёт среду .110 и локальную работу. Это может быть правильно для текущих ролей, но должно быть видно и редактируемо, с указанием области действия.
4. Чат запускается через отдельный Pi RpcClient, задачи — через createAgentSession с собственным resourceLoader. Полную эквивалентность источников нельзя утверждать без проверки Pi default system prompt и автообнаружения ресурсов.
5. У Секретаря отдельный prompt в secretaryReply.ts с обязательными быстрыми ответами; прежняя универсальная вкладка «Чат» этого не учитывает. Есть отдельные голосовые инструкции и модельный разбор сводки.
6. Список MCP tools чата читается из profile JSON, а задачи используют taskflowTools. Прежнее утверждение, что профили вообще не участвуют, слишком широкое: для chat roleRunAccess они участвуют в выборе инструментов.

Эти находки не доказывают причину всех неудачных ответов ролей. Это проверенные источники влияния и кандидаты на исправление после раскрытия эффективного контекста.

## Порядок работы

1. Закончить инвентаризацию, включая tool descriptions, MCP instructions, Pi defaults и специальные пути Секретаря. Отметить каждый источник как подключённый, неиспользуемый или ещё не проверенный.
2. Подключить каталог и настройки к runtime без изменения исходных дефолтов. Тесты подтверждают сохранение поведения без overrides.
3. Расширить существующий iOS экран до редактора и связать его с теми же блоками. Снять XCUITest attachments по accessibility; действующий вход не менять ради теста.
4. Отдельным обозримым набором изменений исправить устаревшие тексты ролей. Показать владельцу diff по каждой роли и режиму до применения к live настройкам.
5. Выложить после решения владельца и проверить реальные пути задачи/чата с manifest. Сборка и unit-тесты не заменяют такую проверку.

## Приёмка

- Изменение каждого блока влияет на реальную сборку соответствующего режима, включая секретарские пути, descriptions и MCP rules; просмотр показывает ту же версию.
- Изменение одной роли не затрагивает другую; общий override меняет перечисленные роли. Сброс и восстановление работают.
- Не-владелец не сохраняет настройки. Конкурентное сохранение возвращает 409. Неизвестные плейсхолдеры отклоняются.
- Все прежние источники учтены manifest; неподтверждённые ресурсы отмечены, а не скрыты.
- Имена/schema tools, права и бизнес-переходы не изменяются от редактирования текста.
- Ошибки загрузки/сохранения не теряют черновик. Достижимость вкладок проверена XCUITest.
- Историческая ветка c0f9bbc используется как исходная работа, не перетирает последующие изменения main. Старые документы остаются по прежним ссылкам; новая точка входа — этот документ и индекс рядом.
