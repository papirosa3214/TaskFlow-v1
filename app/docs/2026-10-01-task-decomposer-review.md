## Кто создаёт карточки сейчас

- Секретарь — пользовательский вход, но не единственный создатель. Голосовой `agents/secretary-voice/worker.py:create_task_via_api` отправляет полный текст в `/secretary/tasks`.
- `src/lib/ownerDraft.ts:submitOwnerTaskText` вызывает `src/routes/ai.ts:structureDictationToCards`, затем `createDraftCards`: родитель, шаги, дочерние карточки; прикладывает исходный текст. Режим automatic допускает дерево при отсутствии вопросов. `createDraftFromText` использует тот же структурировщик для файлов/текста.
- Внутренние роли имеют инструмент `taskflow_create_task` (`scripts/mcp_server.py`, доступ в `src/runtime/roleRunAccess.ts` зависит от конфигурации). Это отдельный путь создания, поэтому улучшение только Секретаря не охватит все карточки.
- `src/routes/dispatch.ts:applyIntakeToNewTask` обрабатывает уже созданную карточку с учётом режима владельца и назначения. Родители-контейнеры не исполняются.
- `src/routes/task-collaboration-plans.ts` хранит draft/approved планы с role_key и рёбрами. Approve связывает существующие подзадачи через source_subtask_id либо создаёт обычные subtasks. Это не обязательно дочерние tasks с parent_id.

Рекомендация, запись карточки, назначение и запуск должны оставаться разными событиями.

## Что исправить

1. `calculate_schedule` (строка 444) и `validate_planner` (563) смешивают возможность разделить работу и безопасность параллельного запуска. Неизвестная совместимость запрещает split вообще. Отдельные задачи допустимы и при последовательной работе: ограничивать одновременность, а не самостоятельное отслеживание. Учитывать ограничение ресурса отдельно от зависимости результата.
2. Вариантов представления недостаточно: single_card_checklist / split_suggested / ask_before_split. Для TaskFlow добавить различение шагов-чек-листа, исполняемых подзадач одной карточки в collaboration plan и самостоятельных дочерних карточек. Выбор отдельной роли не требует отдельной карточки.
3. Роли заданы свободным текстом, а выбранные имена проверяются наличием подстроки во входе. Это не проверка существования, доступности или полномочий. Требуется серверный каталог ролей, устойчивые role_key/ID и проверка возможностей. В примере названы два участника команды, но третьему потоку рекомендован ещё один аналитик: сведение должен иметь явно согласованного ответственного, которым может быть один из этих двух.
4. `_validate_metadata` (486) проверяет подстроку вместо смысла. Нормализованная дата из «завтра» не проходит; упомянутый в отрицании проект или агент может пройти. Нужны исходный фрагмент, тип решения (explicit/resolved/suggested), timezone и каталог ID. Упоминание имени не означает назначение.
5. Поля прототипа не являются серверной схемой: metadata.project не project_id, priority здесь строка, а MCP принимает число; selected_agent_name не assignee_id; depends_on использует локальные W1. Нужны адаптер и постоянное отображение локальных ключей в серверные узлы.
6. Нет серверной идемпотентности, транзакционной записи, версий анализа и проверки устаревшего контекста. source_record_id лишь копируется в JSON. Повторная доставка не должна создавать второй комплект карточек. Существующий claimDraftForParsing в task-intake.ts следует сохранить.
7. Несколько последовательных модельных запросов: классификация, рекурсивные проходы, зависимости, планировщик. С max_nodes=40 возможно до примерно 43 запросов; timeout=90 секунд задан на запрос, общего бюджета нет. Для простого поручения нужен короткий путь, общий deadline/бюджет, сохранение промежуточного результата и понятная обработка сбоя.
8. `_parallel_plan` и `_root_card_stream` (772, 613) при отказе от split сворачивают потоки в whole_task, теряют их зависимости и назначения. Полезно сохранять аналитический граф независимо от выбранного отображения.
9. Чувствительные данные лишь помечаются: полный raw_transcript и provided_context всё равно уходят провайдеру, описание может повторять секрет. sensitive_labels не обеспечивает удаления данных. Нужен отдельный механизм обработки секретов, если контур принимает их.
10. Проверки JSON и фразы о недоверенных данных не доказывают смысловую корректность и устойчивость к prompt injection. Тест проверяет наличие предупреждения в промпте, а не поведение реальной модели. Нужны сценарии отрицаний, исправления поручения, отсутствующих материалов, повторной доставки, смены контекста и реального каталога ролей.

## Предлагаемый поток

Сообщение/текст → определение намерения с контекстом диалога → черновик постановки → проверяемые результаты → выбор представления → граф зависимостей и ограничений ресурсов → подбор существующих ролей → валидация → сохранение draft → существующий допуск/approve → исполнение.

Рекурсивная декомпозиция может предложить дерево кандидатов; окончательный граф должен строиться по выбранным единицам исполнения. Статические волны годятся для объяснения плана, но готовность во время исполнения определяется конкретными зависимостями, артефактами и доступностью ресурсов, без ожидания всей волны.

Первая точка подключения — общий структурировщик за structureDictationToCards, с сохранением ownerDraft и intake. Для внутренних ролей нужен тот же сервис подготовки предложения; API записи должен проверять серверный контракт и права, а не автоматически переосмысливать каждую уже готовую карточку. Для существующей карточки — предложение collaboration plan, по возможности на её существующих subtasks, без дублирования в дочерние tasks.

Это предложение архитектуры, не выполненная интеграция. Решение о реализации остаётся отдельным действием владельца.
