# Миграция iOS на агентскую модель AgentProfile → Pi → Model

Дата: 18.09.2026. Коммит: `0ae7f6b4`.

Приложение переведено с модели «исполнитель = `ApiUser`» на серверный фасад
ролей: **Задача → Агент (AgentProfile/роль) → Статус → Модель → Результат**.
Pi остаётся runtime под агентом и в обычном UI не показывается.

Что переведено:

| Экран | Было | Стало |
| --- | --- | --- |
| Команда (`AgentsScreen`) | `GET /api/agents` (`ApiUser`) | `GET /api/roles` (`RoleProfile`) |
| Карточка роли (`AgentRow`) | модель/провайдер/токен учётки | primary + упорядоченные fallback, промпт, tools, скиллы, права, текущая задача |
| Карточка задачи (`TaskForm`) | `agents: [ApiUser]` | роли + «Автоматически» (`owner_selected_role`) |
| Работа агентов | строка задачи | + «Роль · модель» |
| Настройки → ИИ | одна строка в локальные модели | «Модели и провайдеры» (сервер) и «На устройстве» (локально) |
| Настройки → Сервер | — | Pi Runtime status, Service Accounts |

## Осознанные расхождения со спекой

Это не недоделки, а решения, принятые по факту серверной реализации
(источник истины — TaskFlow Server). Зафиксированы, чтобы не выглядели
случайностью.

### 1. «Команда» читает `/api/roles`, а не `/api/runtime/profiles`

Спека перечисляет DTO `AgentProfile` (эндпоинт `/api/runtime/profiles`).
Но этот эндпоинт отдаёт профиль **без текущей задачи**: `current_task`
считается только в `/api/roles` (`server/src/routes/roles.ts`). Спека
фасада Pi в каноническом репозитории сервера прямо закрепила контракт
`/api/roles` за UI.

Поэтому экран «Команда» работает на `RoleProfile` из `/api/roles`, а
`AgentProfile`/`/api/runtime/profiles` оставлены как DTO рантайма и
используются там, где роль не нужна (например, статус Pi).

### 2. Роли server-defined: создать новую роль из приложения нельзя

Спека §6 предполагает, что «+ Новый агент» создаёт `AgentProfile`. На
сервере список ролей фиксирован (`ROLE_NAMES` в `roleRouting.ts`), а
`AgentProfile` — это фасад над существующими ролями, а не новая сущность с
эндпоинтом создания. Создавать роль из клиента нечем.

Поэтому форма создания из «Команды» убрана, а старая механика
`ApiUser` + API-токен не удалена, но переехала в
**Настройки → Сервер → Service Accounts** и больше не называется агентом.
Если на сервере появится создание профилей — форма вернётся в «Команду».

### 3. prompt / tools / skills роли — только чтение

В карточке роли эти разделы показываются, но не редактируются. Причина: у
серверного фасада нет на них write-ручек — промпт читается из файла
`role-prompts/<role>.md`, скиллы из таблицы `role_skills`, tools из
профиля Pi (`taskflow-profiles/<role>.json`). Старые правки через
`/api/agents/:id` писали в `users.prompt` и другие источники, которые фасад
не читает, то есть правили бы «не тот» источник и расходились с реальным
исполнением.

Редактируется только политика моделей — `PUT /api/runtime/routing/:role`
(primary + упорядоченные fallback), у неё серверная ручка есть.

## Что осталось за рамками фазы

- `AttemptLadderView` не менялся: он уже читает реальные ступени с сервера
  (LOCK-145), выдумывать новый блок не требовалось.
- Промпт/tools/skills — редактирование, если сервер заведёт ручки.
- Создание роли — если сервер разрешит нефиксированный список ролей.
