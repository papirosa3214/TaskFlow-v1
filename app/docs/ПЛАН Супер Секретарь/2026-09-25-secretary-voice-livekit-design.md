## Почему LiveKit, а не голый WebSocket

Голый WS до телефона (исходный Вариант А) требовал бы писать самим:
устойчивость к плохой сети, переподключение, детект пауз в речи для
барж-ина. LiveKit Agents-фреймворк уже решил это и имеет готовый плагин под
Gemini Live — вместо самодельной обвязки нужна в основном конфигурация.
Разведка 25.09.2026 (WebSearch, форасофт/LiveKit docs): официальный Swift
SDK есть (`livekit/client-sdk-swift`, iOS/macOS/visionOS через SwiftPM),
`livekit-agents` — Python и Node/TS, vendor-neutral (можно подключить любой
LLM/STT/TTS, в т.ч. Gemini Live как speech-to-speech).

## Владелец подтвердил на этапе брейнсторминга (25.09.2026)

1. Мозг голоса — **Gemini Live**, не локальный STT/LLM/TTS (закрытый вопрос
   «зачем LiveKit» — транспорт, не замена мозга).
2. LiveKit-сервер — **LiveKit Cloud** для быстрого старта, самохостинг на
   .110 — отдельным решением потом, если понадобится.
3. Мостик Gemini↔LiveKit — **отдельный Python-процесс на .110**
   (`livekit-agents` + готовый Gemini Live-плагин), инструменты дёргает
   HTTP-вызовами к существующим `/api/*` (тот же путь, что уже использует
   `mcp_server.py` для ролей), не напрямую `app.inject`. Причина: у
   Python-плагина под Gemini Live обкатка лучше, чем у Node/TS-версии
   `livekit-agents`; отдельный процесс не рискует уронить боевой
   TypeScript-сервер экспериментальной голосовой фичей.

## Архитектура

```
iPhone (LiveKit Swift SDK)
   │  WebRTC (аудио-трек микрофона)
   ▼
LiveKit Cloud (комната)
   │  auto-dispatch воркера в комнату
   ▼
Python-воркер на .110 (livekit-agents + Gemini Live plugin)
   │  bidi audio + function-calling
   ▼
Gemini Live API (Google)
   │  вызов инструмента (function call)
   ▼
Python-воркер → HTTP → TaskFlow-сервер (Node, .110) → /api/* (тот же путь, что у ролей)
```

## Компоненты

- **LiveKit Cloud** — проект, API key/secret. Хранение: vault на .110 (тот
  же приём, что `TASKFLOW_AGENT_TOKEN`), НЕ на телефоне.
- **Python-воркер на .110** (новый процесс, не часть Node-сервера) —
  `livekit-agents`, подписан на dispatch для комнат Секретаря; сессия с
  Gemini Live через встроенный плагин; function-calling транслирует в
  HTTP-запросы к `/api/*` с сервисным токеном `u-secretary` (тем же, что
  уже поднят на `role → agent` в миграции `061_secretary_role`).
- **TaskFlow-сервер (Node)** — один новый эндпоинт (например,
  `POST /api/secretary/voice-token`): владелец аутентифицирован как обычно,
  сервер минтит короткоживущий LiveKit room-токен (`AccessToken` с
  LiveKit SDK, серверный секрет не покидает .110) и отдаёт его телефону.
- **iOS** — новый экран режима голоса (LiveKit Swift SDK, `LiveKitClient`
  через SwiftPM): подключается комнатным токеном, публикует микрофон,
  проигрывает трек воркера. Индикатор «слушаю / думаю / говорит Секретарь»,
  кнопка выхода в обычный текстовый чат (§3.3 плана — без изменений).
  Барж-ин: касание экрана или начало речи обрывает ответ — штатно
  поддерживается Gemini Live через LiveKit-плагин, iOS ничего специально не
  реализует сверху.

## Поток данных

1. Владелец открывает голосовой экран → iOS запрашивает room-токен у
   TaskFlow-сервера.
2. iOS подключается к комнате LiveKit Cloud, публикует аудио-трек
   микрофона.
3. LiveKit Cloud авто-диспатчит Python-воркер в эту комнату.
4. Воркер стримит аудио в Gemini Live, получает аудио-ответ и/или вызов
   инструмента.
5. При вызове инструмента — HTTP-запрос к `/api/*` на .110, результат
   возвращается в разговор Gemini как ответ на function call.
6. Аудио-ответ Gemini публикуется воркером как трек в комнату → iOS
   проигрывает.

## Отказы

- **Воркер упал** — LiveKit видит разрыв участника комнаты; iOS показывает
  «Секретарь отключился», а не зависает молча. Воркеру нужен systemd-юнит с
  автоперезапуском на .110 — это «настройка» по правилу 13.1
  (`~/.claude/CLAUDE.md`): в одном заходе с поднятием воркера завести
  автоматического проверяющего, который ловит именно тихий отказ (воркер
  запущен, но не принимает dispatch/не отвечает), не просто «процесс жив».
- **Сеть у телефона моргнула** — переподключение штатно в LiveKit Swift SDK;
  если не восстановилось — откат в обычный текстовый чат с Секретарём
  (тот же `chat-secretary`, этап 1 уже сделан).
- **Gemini недоступен / лимит** — воркер шлёт статусное текстовое сообщение
  в комнату (LiveKit data-канал), iOS показывает ошибку явно, не тишину.
- **LiveKit room-токен истёк** — iOS запрашивает новый у сервера перед
  повторным подключением, без падения на глазах владельца.

## Проверка (порядок, от дешёвого к дорогому)

1. Воркер заходит в тестовую комнату LiveKit Cloud и отдаёт эхо своего же
   входного аудио — без Gemini вообще. Подтверждает, что транспорт и
   dispatch воркера живые, прежде чем подключать что-то платное/сложное.
2. Подключить Gemini Live-плагин, прогнать разговор без вызова инструментов
   (просто «привет» → голосовой ответ).
3. Прогнать разговор с вызовом инструмента (например, создание тестовой
   задачи через голос) — проверить, что HTTP-путь к `/api/*` и результат
   долетают обратно в разговор.
4. Живая проверка на iPhone (не в симуляторе — микрофон симулятора
   ненадёжен для голосового ввода): полный разговор, барж-ин, разрыв сети.

## Не входит в этот дизайн (осознанно)

- Самохостинг LiveKit — отдельное решение, если Cloud окажется тесен или
  нежелателен по приватности; в этом дизайне не рассматривается.
- Полностью локальный голосовой пайплайн (свой STT/LLM/TTS без Gemini) —
  отклонено владельцем 25.09.2026 на этапе вопросов.
- Перенос карточки задачи (`SecretaryDraftCard`) в голосовой режим — по
  плану (§4/этап «карточка») это уже отдельно сделанная функция текстового
  чата; в голосовом режиме её визуальный аналог не проектируется в этом
  заходе.
