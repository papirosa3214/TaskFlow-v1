# Паспорта серверных уведомлений: обязательный реестр и контекст диагностики

**Статус:** проектирование — реализация не начата  
**Дата:** 29 сентября 2026 года  
**Контур:** `.110`, `~/infra-ops`, `~/Проекты/New-Todoist/server`,
`~/Проекты/taskflow-уведомления`

## Проблема

Серверные уведомления могут создавать диагностические задачи с недостаточным
контекстом: из текста неясно, какой наблюдатель сработал, что он измеряет,
где находится его код/лог, что является нормой и как подтвердить исправление.
Агент начинает с ручной археологии, а задача блокируется или получает
непроверенный итог.

Уже есть черновой `~/infra-ops/notification_passports.json` с 15 записями.
В нём для части источников указаны владелец, units, файлы, check source, логи,
симптомы и команда проверки. На 29 сентября файл не добавлен в Git, не
проверяется в поставке и не используется при создании диагностического
контекста.

## Цель

Любое серверное уведомление должно вести к точному, воспроизводимому
диагностическому контексту. Агент, принявший задачу, сразу знает:

1. что это за источник и зачем он существует;
2. какую метрику/состояние он проверяет и какая норма;
3. где владелец, unit, код, log и state;
4. как безопасно проверить симптом и какой результат означает исправление;
5. по какой неизменяемой версии этой инструкции был создан инцидент.

## Не-цели

- Не заменять `journalctl`, application logs и evidence-файлы одним новым
  журналом.
- Не посылать пользователю отдельное зелёное уведомление на каждый успешный
  запуск watcher.
- Не менять существующее правило: критичные отказы идут отдельным сигналом,
  остальное — в человеческий дайджест.
- Не давать агенту автоматическое право на перезапуск, удаление данных или
  изменение сетевых маршрутов только потому, что в паспорте есть команда.

## Решение

### 1. Канонический реестр

`notification_passports.json` становится версионируемым источником правды в
репозитории `~/infra-ops`. Каждая запись имеет стабильный машинный `source_id`;
человеческое название можно менять без разрыва связи с уведомлениями.

Минимальный контракт записи:

```json
{
  "schema_version": 1,
  "source_id": "taskflow-secretary-voice-watch",
  "title": "Голосовой Секретарь: доступность",
  "purpose": "Рано обнаружить, что голосовой worker не сможет ответить.",
  "owner": {
    "repo": "/home/maksim/Проекты/New-Todoist",
    "units": ["taskflow-secretary-voice-watch.timer", "taskflow-secretary-voice-watch.service"],
    "files": ["server/scripts/secretary_voice_watch.py"]
  },
  "observation": {
    "metric": "HTTP-ответ Gemini через xray и доступность worker",
    "normal": "HTTP 200 и worker отвечает",
    "cadence": "каждые 15 минут"
  },
  "evidence": {
    "logs": ["journalctl --user -u taskflow-secretary-voice-watch.service --since -24h"],
    "state": ["/home/maksim/Проекты/New-Todoist/server/secretary-voice-watch.state.json"]
  },
  "triage": {
    "symptoms": [{"match": "HTTP 400", "meaning": "Проверить geo/маршрут xray; не менять ключи."}],
    "verify_command": "systemctl --user is-active taskflow-secretary-voice-watch.timer",
    "expected_after_fix": "Следующий прогон возвращает HTTP 200 и обновляет state."
  },
  "notification": {"source_aliases": ["taskflow-secretary-voice-watch"], "severity": "critical"},
  "review": {"reviewed_at": "2026-09-29", "reviewed_reason": "initial migration"}
}
```

Команды в паспорте — диагностические и read-only по умолчанию. Любое
восстановительное действие описывается как кандидат на решение владельца,
а не выполняется агентом автоматически.

### 2. Неизменяемый снимок в инциденте

`alert_send.py`/`rendezvous.py` передают стабильный `source_id`. Когда
уведомление содержит тревогу и создаётся диагностическая задача, backend
разрешает этот ID в реестре и прикладывает snapshot:

- `source_id`, хеш и версию паспорта;
- назначение, наблюдение, норму и фактический симптом;
- owner, units/файлы, логи/state;
- безопасную первичную проверку и ожидаемый критерий исправления.

Снимок сохраняется в evidence/контексте задачи, а не читается заново при
каждом открытии. Поэтому последующая смена паспорта не переписывает
историческое основание инцидента.

Карточка уведомления остаётся краткой. Полный паспорт получает агент в
структурированном контексте до первого действия. В финальном результате
обязательно записывается фактическая команда/проверка и её результат.

### 3. Обязательность и актуальность

Новый `validate_notification_passports.py` запускается локально и в CI.
Он:

1. проверяет JSON schema, уникальность `source_id` и отсутствие секретов;
2. сверяет declared unit/file/log paths с реальными файлами в checkout или
   на `.110` в ночном режиме;
3. строит inventory из systemd units и списка emitter’ов (`alert_send`,
   `rendezvous`, watcher scripts) и сообщает источники без паспорта;
4. проверяет aliases: каждый `source` из уведомления должен однозначно
   разрешаться в паспорт;
5. в diff-проверке требует обновить passport или его `review` при изменении
   watcher, unit или наблюдаемой метрики.

Если новый watcher/emitter не описан, поставка блокируется. Если изменён
контур существующего наблюдения без обновления/явного review его паспорта,
поставка также блокируется.

Ночной read-only audit на `.110` сверяет установленный набор units и
emitter’ов с реестром. При расхождении он создаёт одно понятное server
notification с перечнем отсутствующих/устаревших паспортов. Повторные
идентичные расхождения дедуплицируются.

### 4. Миграция текущего задела

1. Добавить существующий файл в `infra-ops` под Git и привести к schema v1.
2. Проверить все 15 записей против фактических unit, script и log paths.
3. Собрать inventory всех systemd watcher/report/sync units и emitter’ов.
4. Завести отсутствующие паспорта или исключения с причиной и сроком;
   бессрочных исключений нет.
5. Включить validation в локальный workflow и CI в warn-only режиме.
6. После зелёной миграции включить blocking mode.
7. Подключить snapshot к diagnostic task и провести живой controlled
   failure/restore для одного некритичного источника.

## Поток данных

```text
watcher / report / service monitor
  └─ source_id + human summary
        ↓
alert_send.py → rendezvous.py → durable notification evidence
        ↓ тревога
diagnostic task creation
  └─ passport lookup → immutable passport snapshot
        ↓
agent context: symptom + location + safe diagnosis + success criterion
        ↓
verified resolution linked to the same source_id/passport hash
```

## Ошибки и безопасное поведение

| Ситуация | Поведение |
| --- | --- |
| Уведомление с неизвестным `source_id` | Evidence не теряется; создаётся отдельный критичный сигнал «паспорт отсутствует», diagnostic task получает явную причину отсутствия контекста. |
| Паспорт невалиден или содержит путь вне разрешённых корней | Поставка/CI блокируются; ночной аудит фиксирует нарушение без исполнения команды. |
| Старый инцидент с источником без паспорта | Не переписывается; карточка показывает, что снимок недоступен, и ведёт к raw evidence. |
| Уведомление доставлено, но TaskFlow недоступен | `rendezvous` остаётся durable source evidence; snapshot добавится при последующей обработке, не теряя исходный timestamp. |
| Изменился паспорт после инцидента | Новый инцидент получает новый hash; старый использует сохранённый snapshot. |

## Проверка

До production-code каждая часть разрабатывается через red-green-refactor:

1. тест валидатора падает на новом watcher без паспорта;
2. тест падает на неверном alias/несуществующем unit;
3. тест создания diagnostic task падает без сохранённого passport snapshot;
4. тест подтверждает, что исправление паспорта не меняет снимок старой
   задачи;
5. integration-test подтверждает: уведомление известного источника создаёт
   агентский контекст с диагнозом, логами и проверкой нормы;
6. controlled live rehearsal подтверждает raw evidence → задача → snapshot
   → проверенный итог, без отправки ложной тревоги пользователю.

Критерий готовности: изменение watcher без актуального паспорта нельзя
поставить; агент по новому server-notification не ищет вручную владельца,
логи и норму; итог содержит проверяемое доказательство восстановления.
