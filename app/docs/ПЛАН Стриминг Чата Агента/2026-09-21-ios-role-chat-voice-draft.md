# Чаты с ролями: голос, сборка задачи и привязка

## Клиент

- После замечания владельца оба чата используют один `ChatVoiceComposer`, который повторяет `idleComposer` / `recordingComposer` / `previewComposer` из `VoiceMessageLabScreen`: слева круглая кнопка вложений, справа капсула с `waveform`; удержание иконки 0,18 с начинает запись. Во время записи капсула морфится через `matchedGeometryEffect(id: "voiceComposerPill")` и показывает красную волну, таймер и стоп. После остановки появляется превью с отменой, воспроизведением, длительностью и отдельной кнопкой отправки. Анимация — `spring(duration: 0.32, bounce: 0)`, при Reduce Motion — короткая линейная.
- Оба экрана используют `VoiceRecorder` и `ParakeetVoiceTranscriber` из `VoiceMessageLab`. Пузырь записи и воспроизведение также общие с прототипом.
- В комнате чата после стопа запись остаётся в превью. Parakeet обновляет локальное состояние `pending` → `ready` / `failed`; только явная кнопка отправки передаёт её в ленту. Затем клиент загружает `.m4a` и отправляет сообщение с `attachment_ids` и распознанным текстом. При неудачной отправке остаётся кнопка повтора в ленте.
- При открытии истории аудиовложение скачивается через авторизованный `GET /api/attachments/:id`, после чего показываются воспроизведение, длительность и текст под аудио.
- `chats.task_id` выводится как переход к карточке задачи. Кнопка «Собрать задачу» отправляет `POST /api/chats/:id/draft`.

## Контракт с серверным воркером

1. `POST /api/chats/attachments?name=<имя>`: тело файла сырыми байтами; ответ `{ "attachment": { "id": "…", … } }`. Это **фактический** контракт живого `server/src/routes/chats.ts` на 21.09.2026, такой же, как `/api/chat/attachments`. Multipart там сейчас не разбирается. Общий серверный валидатор `attachments.ts` отклоняет `audio/mp4` (415), поэтому клиент временно отправляет `.m4a` как `application/octet-stream` и узнаёт голос по имени. Серверному воркеру нужно разрешить `audio/mp4`/`audio/x-m4a` и согласовать переход на корректный MIME.
2. `POST /api/chats/:id/messages`: `{ "text": "расшифровка или пустая строка", "attachment_ids": ["id"] }`; ответ `{ "message": { …, "attachments": […] } }`. Пустой текст допустим при наличии аудио.
3. Предлагаемый ответ `POST /api/chats/:id/draft`: JSON с `task_id` или `task: { id }`, если карточка уже создана; для фонового разбора допустимы `draft_id` и `status`. Клиент показывает «Задача собирается…» и ждёт `task_id` в `GET /api/chats/:id`. Кнопка отправляет пустой JSON-объект.
4. `GET /api/chats` и `GET /api/chats/:id` возвращают `task_id` для привязки комнаты к карточке.

## 26.09.2026 — мгновенное схлопывание волны записи

Причина найдена в общем `VoiceRecorder`, который реально используется `RoleChatVoiceController`: уровень сначала отсекался при средней громкости ≤ −38 дБ, затем `VoiceActivityGate` ожидал два отсчёта ≥ 0,18. При нулевом результате цикл каждые 40 мс сбрасывал `smoothedLevel` в ноль и умножал всю историю `waveform` на 0,08. Следующая тихая пауза стирала историю ещё раз. Это независимый дефект от паузы `TimelineView` при Reduce Motion.

Для записи добавлен отдельный `VoiceWaveform.recordingLevel`: непрерывное отображение громкости от −60 до 0 дБ без временного фильтра, быстрая реакция на первый отсчёт и постепенное затухание (коэффициент спада 0,12 каждые 40 мс). Записывающий цикл больше не стирает историю. Код уровня живого звонка, кнопки, ползунок завершения и запись аудиофайла не изменены этой правкой.

Проверка: старый код воспроизводит ноль для −45/−35 дБ; регрессионные тесты `testRecordingMeterRespondsToFirstQuietSpeechSample`, `testRecordingMeterReleasesSmoothlyThroughBriefPause`, `testRecordingMeterTracksSpeechPauseAndNextSyllable` — 3/3, 0 ошибок (`/tmp/taskflow-recording-meter-fix.xcresult`). Debug-сборка для физического iPhone — `BUILD SUCCEEDED`. Реакцию на настоящий микрофон телефона следует проверить в чате во время записи, включая паузы между словами.
