# Живая лента шагов роли в чате — Design

## Goal

Пока роль (`researcher/builder/qa/architect/designer/...`) отвечает в чате
владельцу, окно этого чата ощущается как окно сессии именно с этой ролью:
вместо статичных точек «печатает» видно, что роль делает прямо сейчас
(читает файл, правит код, выполняет команду, ищет) — по мотивам
референсного компонента `AgentActivityFeed.swift`.

## Scope

- Только живая лента — без истории. Закрыл чат и открыл заново — прошлые
  шаги не восстанавливаются, видно только то, что происходит сейчас (если
  роль всё ещё отвечает).
- Только шаги (какой инструмент сейчас используется). Токен-стриминг текста
  самого ответа роли — отдельная будущая задача, не в этом объёме.
- Только тет-а-тет: владелец и ровно одна роль в одном чате (`RoleChat`,
  `kind` ≠ `"group"`). В групповом `RoleChat` (несколько ролей сразу) лента
  шагов НЕ показывается — там всё остаётся как сейчас, точки «печатает».
  Причина: несколько параллельных лент в группе — не то, что нужно
  владельцу.
- Область — именно чат с ролью (`RoleChatsScreen`/`RoleChatRoomScreen`,
  таблица `role_chats`/`chat_sessions`), НЕ экран «Работа агентов»
  (`AgentWorkScreen`) и не старый канал `owner`/`agents` из `ChatViewModel`
  — это другой, отдельный серверный путь запуска роли (`startChatRun`, а не
  `startRun`), и в этой задаче трогаем только его.
- Автоматическое создание/закрепление 1:1-чата с каждой ролью заранее (чтобы
  список чатов был сразу заполнен для всех ролей) — сознательно ВНЕ этой
  задачи, отдельная тема на потом (владелец подтвердил 26.09.2026). Сейчас
  чат с ролью создаётся как и сегодня — вручную, кнопкой «Создать чат».
- Источник данных — событийный поток рантайма роли внутри `startChatRun`
  (`PiRuntimeAdapter.ts`). Название рантайма нигде в этой фиче наружу (в
  терминологии, в переменных фичи, в UI) не всплывает — деталь реализации
  одного файла, а не понятие фичи. Понятие фичи — «роль».

## Architecture

**Сервер — важное отличие от первой версии этой спеки.** Исходно предполагал
цеплять эту фичу к `startRun` (запуск роли на карточке задачи) — неверно:
окно чата с ролью запускается ДРУГОЙ функцией, `startChatRun`, у которой
сейчас вообще нет слушателя событий хода — `promptAndWait(...)` просто
блокируется до готового текста, все промежуточные события рантайма
отбрасываются.

Сигнал «печатает» для чата с ролью уже устроен подходящим образом
(`server/src/routes/chats.ts`, функция `typing(active)` рядом с вызовом
`startChatRun`): перед стартом хода шлётся `chats:typing { chat_id, user_id,
name, active: true }` всем участникам чата (`broadcastToUsers`), после хода
— `active: false`. Это и есть точка расширения:

1. В `StartChatRunInput` добавляется необязательный колбэк
   `onStep?: (tool: string) => void`.
2. Внутри `startChatRun` добавляется `client.onEvent(...)` (которого сейчас
   там нет) — при событии начала вызова инструмента (есть имя инструмента)
   вызывается `onStep(toolName)`.
3. В `chats.ts` этот колбэк передаётся как `onStep: (tool) => typing(true,
   tool)` — в СУЩЕСТВУЮЩУЮ функцию `typing` добавляется необязательный
   второй параметр `tool?: string`, который просто ложится доп. полем в тот
   же самый `chats:typing`-бродкаст.

Никакого нового типа WS-события не заводим — расширяем существующее поле в
существующем сообщении. Сервер отдаёт голое имя инструмента строкой, без
интерпретации — подпись и иконку выбирает клиент.

**iOS-клиент.** В разборе `chats:typing` (клиентский эквивалент —
`RealtimeEvent.roleChatTyping`) добавляется необязательное поле `tool`.
Там, где сейчас в `RoleChatRoomScreen` рендерится индикатор «роль
печатает» по этому событию — при наличии `tool` показывается строка шага
(иконка + короткая русская подпись, по мотивам `AgentActivityFeed`), при
отсутствии — как сейчас, анимированные точки. Таблица
`имя инструмента → подпись/иконка` — маленькая, статическая, на клиенте:
`read`→«Читает», `edit`→«Правит», `bash`→«Выполняет команду»,
`grep`/`glob`→«Ищет», всё незнакомое → «Работает». Групповой `RoleChat`
получает те же `chats:typing`-события (сервер их не фильтрует по типу
чата), но его экран продолжает рендерить только точки — различие чисто в
презентации, без серверной логики маршрутизации по типу чата.

## Safety / edge cases

- Реконнект WS посреди хода роли — лента просто пустая до следующего
  события; ожидаемо, раз истории нет по замыслу.
- Неизвестное имя инструмента — общая подпись «Работает», не падаем и не
  показываем сырую строку из рантайма пользователю.
- Ход оборвался без финального `chats:typing active:false` (краш, отмена) —
  `typing(false)` и сегодня стоит в `finally` вокруг `startChatRun`, так что
  это уже покрыто существующим кодом, менять не нужно.
- Несколько ролей отвечают одновременно в групповом чате — сюда не
  относится: лента шагов в группе не рендерится по замыслу (см. Scope), это
  не «краевой случай», а обычное поведение группового чата.

## Testing

- Сервер: юнит-тест на то, что `onStep`-колбэк из `startChatRun` вызывается
  на событии начала вызова инструмента и не вызывается на посторонних типах
  событий; отдельно — что `typing(true, tool)` кладёт поле `tool` в
  бродкаст, а `typing(false)` — нет.
- iOS: разбор `RealtimeEvent.roleChatTyping` с полем `tool` и без него (+
  битый payload → прежнее поведение, ничего не роняем); снэпшот-тест новой
  строки-шага на паре инструментов (конвенция репозитория —
  `SnapshotTests`).
- Живая проверка перед сдачей — кадром симулятора на реальном 1:1-чате с
  ролью (`CLAUDE.md` проекта: «проверка правок интерфейса — кадром
  симулятора, не на глаз»).

## Отложено (не в этой задаче)

- Токен-стриминг текста самого ответа роли (не только шагов).
- Автоматическое создание/закрепление 1:1-чата с каждой ролью заранее.
